# P3-3.11 — bm-meta Volume Runtime 与固定 LBA 元数据引擎集成

## 目标

把固定 LBA 元数据对象的打开、WAL 恢复、Reader Session、Reader Recovery 和请求入口纳入一个可重试的 Volume 生命周期。运行时不允许在依赖未就绪时接收 I/O，也不允许在后台恢复线程或元数据 I/O 尚未停止时释放底层设备。

实现位于 `internal/metastore/volume_runtime.go`：

- `VolumeRuntimeManager`：管理多个 Volume 的激活、停用和 Daemon Shutdown。
- `VolumeRuntimeBackend`：把设备、sanlock、WAL、Reader Session、SAN Fencing 和 DM I/O Drain 的平台实现注入运行时。
- `VolumeRuntimeMetadata`：强制 `Store`、`ReaderTable`、`PersistentArena` 属于同一个 Volume，并共享同一个 `*Store`。
- `ReaderRecoverySupervisor`：每个已激活 Volume 一个恢复 worker；启动前执行既有的 `ValidateProduction()`。

## 激活顺序

### Read-Write Owner

1. 打开元数据块设备。
2. 获取该 Volume 的分布式 Owner Lease。旧 Owner 的 fencing/takeover 必须在该调用成功返回前完成。
3. 在 Owner Lease 保护下恢复固定 LBA WAL。
4. 打开固定 LBA `Store`，构建 WAL committer、`ReaderTable` 和 `PersistentArena`。
5. 构建并启动 Reader Recovery Controller；生产校验要求真实 sanlock probe/coordinator、cluster-safe committer、SAN fencer、Persistent Arena 和 metadata I/O drain provider。
6. 最后开放数据路径请求。

### Read-Only Reader

1. 打开元数据块设备。
2. 刷新并打开在线一致的固定 LBA Store（不允许 RO 节点自行执行可能写设备的 Owner WAL Recovery）。
3. 构建共享 Store 的 Reader Table / Persistent Arena。
4. 获取 Reader Slot sanlock lease，注册本节点 SCSI PR key，并持久化 Reader Generation。
5. 启动 Reader Recovery Controller。
6. 最后开放只读请求。

`OpenMetadata` 和 `JoinReader` 由 backend 实现，必须复用仓库现有的 Store、WAL、ReaderTable、PersistentArena 和 ReaderSession；不能创建第二份 Store 或使用进程内锁替代共享协调。

## 停用顺序

1. `StopRequests`：停止接收新请求。
2. `ReaderRecoverySupervisor.Deactivate`：取消并 join 当前 Volume 的 recovery worker。
3. `DrainMetadataIO`：等待本地 DM / metadata I/O 队列中所有可能引用旧 metadata page 的 I/O 完成。
4. `ReaderSession.CloseDrained(ctx, true)`：注销本地 PR key、持久化 Reader Closed、释放 Reader Slot lease。
5. `CloseMetadata`：关闭 WAL/committer 及其他 metadata 资源。
6. 释放 Owner Lease（RW）。
7. 关闭元数据设备。

任一步失败都会停止后续释放动作，保留 runtime 以便再次调用 `Deactivate` 重试。特别是 Drain 失败时，不会关闭 Reader Session、Store、WAL、Owner Lease 或设备。

激活期间如果请求入口部分启用后返回错误，也复用完整停用路径，不能假设没有 I/O 被接收。激活回滚中若资源释放失败，同样保留 runtime，避免丢失仍然打开的设备或 Lease 句柄。

## Backend 必须满足的生产契约

- `OpenDevice`：返回实现随机读写、Flush/FUA 语义和正确容量检测的真实块设备句柄；不能把 regular file 当作 SAN 生产设备。
- `AcquireOwnerLease`：必须是分布式 sanlock Owner Lease，并保证旧 Owner fencing/takeover 已完成。
- `RecoverWAL`：使用固定 LBA superblock 中的 AG/WAL 几何，在 Owner Lease 保护下完成 redo recovery；不能在 RO 节点上执行。
- `OpenMetadata`：打开同一设备上的固定 LBA Store，构建 cluster-safe WAL committer、Reader Table 和持久化 Arena；验证 Volume ID、页区域不重叠和 Reader Slot 布局。
- `JoinReader`：RO 模式必须使用 sanlock Reader Slot lease + SCSI PR registration + 持久化 Reader record，并提供 lease-loss fail-stop 回调。
- `BuildReaderRecovery`：返回对应 Volume 的 `ReaderRecoveryController`；其 `ValidateProduction` 必须通过。
- `DrainMetadataIO`：必须覆盖本节点数据路径中可能持有旧 metadata page 引用的全部 I/O。SCSI PR PREEMPT AND ABORT 不能代替本地 DM queue drain。
- `CloseMetadata`：关闭所有 metadata 子资源，但不提前关闭由 Manager 单独持有的 device 句柄。

## 当前交付边界

本阶段完成的是可测试的 Runtime 生命周期编排和 backend contract，不等于已经具备可直接部署的完整 SAN daemon。

当前仓库仍缺少真实部署适配器来提供：
- Linux block-device open / BLKGETSIZE64 / flush 保障；
- 生产环境 Volume Owner Lease、Reader Slot 资源配置和 sanlock lockspace provisioning；
- 生产 SAN PR key 管理、所有 multipath path 的 fencing 验证；
- 与 BlockMesh DM target 对接的请求 admission / stop / global metadata I/O drain；
- 根据实际 Pool Superblock、AG 和 Volume Descriptor 构造 WAL / Reader Table / Arena 的 daemon 配置。

因此 `cmd/bm-meta` 仍是 JSON/WAL 本地演示程序，没有把这个 Manager 接成 SAN 生产入口。不得用 `FileDevice`、`MemoryLease`、`NoopFencer` 或空实现的 Drain provider 冒充生产 backend。真实设备上的多节点 SAN 验证仍需在目标环境完成。

## 验证

`volume_runtime_test.go` 覆盖：
- RO JoinReader、Recovery、EnableRequests 和反向释放顺序；
- RW Owner Lease 先于 WAL Recovery；
- Drain 失败时保留所有底层资源，并允许后续重试；
- WAL Recovery 失败时按依赖顺序回滚 Owner Lease 和设备；
- Recovery worker 在关闭 metadata 资源之前完成退出。
