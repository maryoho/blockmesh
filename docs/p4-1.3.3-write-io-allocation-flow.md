# BlockMesh 一次写 I/O 的完整处理流程：从 DM BIO 到新物理块分配

> 适用范围：P4-1.2 内核 bm 字符设备 / Request Ring / Metadata Service，以及 P4-1.3 BMPOOL03 COW Mutation Executor。
>
> 本文描述当前代码实现的主路径。函数名以 `main` 分支为准。部分步骤跨越内核态与用户态，并非普通的同进程函数调用。

## 1. 总体流程

当上层文件系统向 BlockMesh DM 设备提交一个写 BIO，且该 BIO 涉及尚未分配的逻辑块时，主路径如下：

```text
上层文件系统 / 应用
    |
    | WRITE BIO
    v
DM Target: bm_map()
    |  校验 OwnerEpoch / Gate，计算逻辑块范围
    |  构造 OpAllocateZeroPublish 请求
    v
内核全局字符设备: bm_queue_submit()
    |  建立 Pending BIO 记录
    |  发布 Kernel Request Ring
    v
/dev/blockmesh poll 唤醒 Metadata Service
    |
    v
Device.Run()
    |  QueueMemory.Drain()
    v
DynamicPoolRuntimeProcessor.Process()
    |  ResolveRequest() 校验 Runtime / Owner / Epoch
    v
executeAllocateZeroPublish()
    |  串行化 Runtime mutation
    v
PoolAllocator.AllocateZeroPublishTxn()
    |  AG 分布式锁、幂等检查、读取旧 Mapping
    |  Bitmap 分配规划、Arena 页面预留
    |  新块清零、旧块完整 4MiB COW 复制
    v
B+Tree PutBatchWithReservedArenaPages()
    |  COW 页面构造
    |  Bitmap + Mapping + Idempotency + Retire + Root
    v
PersistentArena / AG WAL 原子提交
    |
    v
Metadata Service Completion Ring
    |  返回新 Mapping / RootGeneration
    v
内核 bm_consume_completions()
    |
    v
bm_finish_pending()
    |  根据 Mapping 计算物理扇区
    |  将原始 BIO 提交到底层 LUN
    v
底层 SAN LUN 完成 BIO
    |
    v
bm_end_io() -> 上层
```

需要严格区分三个完成点：

1. **物理块分配完成**：分配器已经规划了新物理块并完成必要的数据准备。
2. **Mapping 持久化完成**：Bitmap、Mapping 和 Root 的事务已经提交，Completion 可以返回新映射。
3. **用户数据 BIO 完成**：内核将原始 BIO 提交到底层 LUN，底层数据写入完成并向上层返回。

Metadata Service 返回分配成功，只代表第二个阶段已经完成，不代表第三个阶段已经完成。

## 2. DM Target 接收 BIO

代码位置：

- `kernel/dm-blockmesh/dm-blockmesh-target.c`

入口：

```c
static int bm_map(struct dm_target *ti, struct bio *bio);
```

### 2.1 请求准入检查

`bm_map()` 首先检查当前 Target 的运行状态：

- Target 是否已经 fenced。
- RW 模式是否具有有效 OwnerEpoch。
- RW Gate 是否打开。
- RO 模式是否具有有效 ReaderEpoch / RootGeneration，以及请求是否符合只读限制。

通过准入检查后，记录当前 epoch，并增加 `inflight_bios`。该计数用于后续 Fence / Drain，确保关闭请求准入后能够等待已进入 Target 的 BIO 排空。

### 2.2 逻辑地址转换

DM Target 将 BIO 的扇区地址转换成 BlockMesh 的逻辑块地址。当前分配粒度为 4MiB：

```text
BM_UAPI_BLOCK_SECTORS = 8192
8192 sectors * 512 bytes = 4MiB
```

请求可能只覆盖一个逻辑块的一部分，也可能跨越多个逻辑块。Target 计算：

- `logical_start`：起始逻辑块。
- `sector_offset`：BIO 在第一个 4MiB 块中的扇区偏移。
- `block_count`：BIO 覆盖的逻辑块数量。

例如，4KiB 写请求通常只涉及一个 4MiB 逻辑块；8MiB 写请求可能涉及两个逻辑块。

### 2.3 操作类型选择

主要操作类型：

| BIO 类型 | UAPI 操作 | 处理目的 |
|---|---|---|
| READ | `BM_UAPI_OP_LOOKUP_BATCH` | 查询 Mapping |
| WRITE | `BM_UAPI_OP_ALLOCATE_ZERO_PUBLISH` | 分配或 COW 并发布 Mapping |
| DISCARD | `BM_UAPI_OP_DISCARD` | 删除逻辑 Mapping，进入延迟回收 |
| FLUSH | 对应 Flush 操作 | 同步数据和元数据 |

写请求还会生成 128-bit `idempotency_key`，用于分配事务重试。

最后调用：

```c
bm_queue_submit(...);
```

提交成功后，`bm_map()` 返回 `DM_MAPIO_SUBMITTED`。此时原始 BIO 被挂起，尚未提交到底层数据设备。

## 3. 内核 bm 字符设备与 Request Ring

代码位置：

- `kernel/dm-blockmesh/bm_chrdev.c`

入口：

```c
int bm_queue_submit(...);
```

### 3.1 Pending BIO

内核为请求创建 `bm_pending`，保存原始 BIO 和完成后重新提交 BIO 所需的信息，包括：

- 原始 BIO 指针。
- 底层 `block_device`。
- Request ID、Queue Generation。
- 逻辑起始块和块数量。
- DM Target 底层区域起始扇区。
- BIO 在逻辑块内的扇区偏移。
- 请求身份和 epoch 等上下文。

请求通过 `(queue_generation, request_id)` 与后续 Completion 关联。

### 3.2 发布 Request Ring

内核将固定宽度 UAPI Request 写入该 Target 对应的 Queue Request Ring，然后使用 release 语义更新 producer tail，并唤醒字符设备等待者。

Request Ring 满时不能覆盖尚未消费的请求；内核返回重试状态，由 DM 块层重新调度 BIO。

该路径是共享内存 Ring 通信，不是每个 BIO 都通过同步 ioctl 将整个请求传给用户态。

## 4. Metadata Service 消费请求

代码位置：

- `internal/metaservice/device_linux.go`
- `internal/metaservice/ring.go`

主要入口：

```go
func OpenDevice(path string, p Processor) (*Device, error)
func (d *Device) Run(ctx context.Context) error
func (q *QueueMemory) Drain(ctx context.Context, p Processor, limit int) (consumed, produced int, err error)
```

### 4.1 建立字符设备会话

Metadata Service 打开 `/dev/blockmesh`，通过 ABI ioctl 校验协议版本和结构尺寸，枚举内核创建的 Queue，执行 Queue Setup，并 mmap 以下共享区域：

- Request Control。
- Request Ring。
- Completion Control。
- Completion Ring。
- Mapping Payload。

服务通过 poll 等待请求和 Queue 变化通知。

### 4.2 Drain 请求

`Device.Run()` 在请求可读时调用 `QueueMemory.Drain()`。

`Drain()` 读取 Request Ring head/tail，校验 Ring 状态和请求记录，解码 UAPI Request，然后调用：

```go
result, err := p.Process(ctx, req)
```

Processor 是从传输层进入存储运行时的权限边界。

## 5. Runtime 校验与分配执行器

代码位置：

- `internal/metaservice/dynamic_pool_processor.go`
- `internal/metaservice/dynamic_mutation_executor.go`
- `internal/dynamicruntime/manager.go`

### 5.1 Processor 分派

入口：

```go
func (p *DynamicPoolRuntimeProcessor) Process(
    ctx context.Context,
    req uapi.Request,
) (Result, error)
```

对 `OpAllocateZeroPublish`，先通过：

```go
p.manager.ResolveRequest(...)
```

解析并校验当前请求所属的 Runtime。校验内容包括 Volume / Node / Boot 身份、Runtime 状态、OwnerEpoch，以及请求所需的读写权限和 Generation 条件。

内核 Gate 与用户态 Runtime 校验是两层不同的防护：前者控制 BIO 是否进入请求路径，后者确保 Metadata Service 只允许当前有效 Runtime 执行元数据操作。

### 5.2 Mutation Executor

入口：

```go
func (p *DynamicPoolRuntimeProcessor) executeAllocateZeroPublish(...)
```

执行器对同一个 Volume 的 mutation 串行化，重新确认 Runtime 实例仍然有效，检查 RW Owner Lease 和 OwnerEpoch，然后计算稳定的 allocation fingerprint。

Fingerprint 排除传输层 Request ID、Queue Generation 和当前 Owner 身份信息，使同一个持久化操作在重试或 Owner 接管后仍可识别为同一操作。

随后调用：

```go
rt.Allocator.AllocateZeroPublishTxn(ctx, rt.Owner, allocator.AllocateRequest{...})
```

## 6. PoolAllocator 分配新物理块

代码位置：

- `internal/allocator/pool_allocate.go`
- `internal/allocator/dynamic_bitmap_txn.go`

入口：

```go
func (a *PoolAllocator) AllocateZeroPublishTxn(
    ctx context.Context,
    ownerLease lock.Lease,
    req AllocateRequest,
) (AllocateResult, error)
```

### 6.1 校验并获取 AG 锁

分配器读取并校验 Dynamic Superblock、Volume Descriptor、Pool / AG 几何信息和 Owner 状态，然后获取 Volume 所属 AG 的分布式锁。

等待 AG 锁期间可能发生 Owner 切换，因此获得锁后还需要重新验证相关元数据和 Owner 状态。不能只依赖本机 mutex 来保护 SAN 多节点分配。

### 6.2 幂等检查

分配器根据 Idempotency Key 查询持久化幂等索引：

- 如果记录存在且 fingerprint 相同，返回之前提交的物理映射，不重复分配。
- 如果 key 相同但 fingerprint 不同，拒绝请求。
- 如果记录不存在，继续分配。

### 6.3 读取旧 Mapping

分配器读取本次逻辑块范围的旧 Mapping，逐块记录是否已映射以及原物理块号。

这一步决定新块的数据准备方式：

| 逻辑块状态 | 新物理块准备方式 |
|---|---|
| 原来没有 Mapping | 新块清零 |
| 原来已有 Mapping | 新块清零后，将旧物理块完整 4MiB 复制到新物理块 |

当前写路径采用完整块 COW，而不是直接覆盖已有物理块。这样，即使上层 BIO 只覆盖 4KiB，也能保留同一个 4MiB 逻辑块内未被本次 BIO 覆盖的其他数据。

### 6.4 Bitmap 分配规划

入口：

```go
func PlanDynamicBitmapAllocation(
    r io.ReaderAt,
    sb format.DynamicSuperblock,
    ag uint32,
    count uint32,
) (uint64, []metastore.PageImage, error)
```

该函数根据 AG 几何信息定位 Bitmap Region，读取并校验 AG Bitmap Descriptor 和 Bitmap 数据，扫描连续空闲块，将候选块对应的 bit 在内存 after-image 中置为已分配，并更新 Descriptor 序列号和校验值。

例如，若找到从物理块 2000 开始的三个连续空闲块：

```text
分配前：2000=0, 2001=0, 2002=0
规划后：2000=1, 2001=1, 2002=1
```

**此时只是生成 Bitmap after-image，并没有单独把 Bitmap 作为已提交状态发布到磁盘。** 它必须和 Mapping、幂等记录及新 Root 一起进入后面的 WAL 事务。

### 6.5 预留 Arena 页面

分配器为 Idempotency Record，以及需要时的 Data Retire Record，向 PersistentArena 预留页面。

预留页面只是事务资源，不代表记录已经提交可见。其最终生效必须与 B+Tree Root 的 WAL 发布一致。

## 7. DataView 数据准备：清零与 COW

代码位置：

- `internal/allocator/zero.go`
- `internal/allocator/pool_allocate.go`

### 7.1 清零新物理块

入口：

```go
func ZeroBlocks(
    ctx context.Context,
    dev DataDevice,
    physicalStart uint64,
    count uint32,
) error
```

`ZeroBlocks()` 对新分配的完整物理块写零，并调用 DataDevice.Sync()。当前以 1MiB 为写入缓冲粒度，覆盖完整的 4MiB 块。

清零必须覆盖完整分配单元，不能只清零本次 BIO 覆盖的扇区，否则可能暴露旧数据。

### 7.2 复制旧数据

对于原来已经有 Mapping 的逻辑块，分配器调用：

```go
copyPhysicalBlock(ctx, dev, source, destination)
```

将旧物理块完整 4MiB 复制到新物理块。对于混合范围中的未映射块，新块保持清零状态。

### 7.3 数据先于 Mapping 持久化

完成清零和复制后，对 DataView 执行 Sync。必须满足：

```text
新块清零 / COW 复制持久化
              happens-before
Bitmap + Mapping + Root WAL 发布
```

这样，其他请求看到新 Mapping 时，新物理块的初始内容已经持久化。MetadataView 和 DataView 是同一个父 LUN 上的不同逻辑区域，不代表使用两块独立设备。

## 8. Bitmap、Mapping 和 Root 的统一 WAL 事务

代码位置：

- `internal/btree/tree.go`
- `internal/btree/cow.go`
- `internal/metastore/store.go`
- `internal/wal/journal.go`

B+Tree 更新入口：

```go
t.PutBatchWithReservedArenaPages(
    updates,
    reservation,
    arenaPages,
    bitmapImages,
)
```

随后进入：

```go
t.publishCOWWithReservedPages(...)
t.publishCOWWithWAL(...)
```

事务中包含：

1. Bitmap after-image：新物理块标记为已分配。
2. Mapping COW 页面：逻辑块映射到新物理块。
3. Idempotency Record 及索引：持久化请求指纹和分配结果。
4. Data Retire Record（如有）：记录被 COW 替换的旧物理块，等待 Reader Generation 安全回收。
5. 新 B+Tree Root / Generation 及 Arena 生命周期信息。

底层通过 PersistentArena 的提交入口和 AG WAL 提交 after-image。WAL 的核心入口为：

```go
func (j *Journal) CommitImages(images []metastore.PageImage) error
func (j *Journal) Commit(updates []PageUpdate) error
```

事务的目标是保持 Bitmap、Mapping、索引记录和 Root 的原子可恢复性：恢复后只能看到事务前的旧状态，或事务提交后的新状态，不能出现 Mapping 已发布但 Bitmap 仍认为该块空闲的半提交状态。

如果 WAL 返回错误且无法确定事务是否已经持久提交，执行器必须 fail closed：Poison Runtime、停止新的 DM 请求准入，并在重新激活前执行 WAL Recovery 和幂等记录核对。不能把结果未知的物理块直接释放并重新分配。

## 9. Completion Ring 返回 Mapping

代码位置：

- `internal/metaservice/ring.go`
- `internal/metaservice/device_linux.go`

分配器成功返回新映射和 RootGeneration 后，Processor 将其包装成 Metadata Service Result。

`QueueMemory.Drain()` 将 Mapping 写入 Completion Payload，再写入 Completion Ring，使用原子操作发布 Completion tail。随后服务通过 `BM_IOC_KICK` 通知内核消费完成项。

Completion 通过 Request ID 和 Queue Generation 与原始 Pending BIO 对应。成功的数据 BIO 必须携带有效 Mapping；错误、过期 generation、格式错误或不匹配的 Completion 必须 fail closed。

## 10. 内核接收 Completion 并提交原始 BIO

代码位置：

- `kernel/dm-blockmesh/bm_chrdev.c`

主要入口：

```c
static long bm_ioctl(...);
static int bm_consume_completions(struct bm_queue *q);
static void bm_finish_pending(
    struct bm_pending *p,
    const struct bm_uapi_completion *completion,
    const struct bm_uapi_mapping *mapping);
```

### 10.1 Completion 校验

`bm_consume_completions()` 校验 Completion 版本、长度、Queue Generation、Request ID、状态码、Payload 边界和 Mapping 数量，然后取出对应的 Pending BIO。

不匹配、过期或格式错误的完成项不能被用于提交 BIO。

### 10.2 计算物理扇区

`bm_finish_pending()` 根据 Completion 返回的 Mapping，计算 BIO 对应的物理块号，再结合 DM Target 底层区域起始扇区和原始 BIO 的块内偏移，得到最终物理扇区。

必须验证：

- Mapping 覆盖原始 BIO 的完整逻辑块范围。
- 物理块和扇区计算不溢出。
- 目标扇区位于该 DM Target 配置的底层设备范围内。
- Completion 的 OwnerEpoch 等身份信息与 Pending 请求一致。

### 10.3 提交原始 BIO

验证通过后，内核将原始 BIO 的目标设备和扇区更新为新物理位置，然后调用：

```c
bio_set_dev(bio, p->bdev);
bio->bi_iter.bi_sector = phys_sector;
submit_bio_noacct(bio);
```

**这里才是原始用户写 BIO 真正提交到底层 SAN LUN 的位置。**

底层 BIO 完成后，DM Target 的 `bm_end_io()` 处理完成状态并减少 `inflight_bios`，最终向上层返回成功或错误。

## 12. 架构约束与性能关注点

### 12.1 当前写路径是完整 4MiB COW

对已有 Mapping 的写请求会分配新物理块并复制完整 4MiB，然后发布新 Mapping。它保护了未被本次 BIO 覆盖的数据，但会引入写放大和额外的读写流量。后续性能测试需要分别测量小块随机写、顺序写和覆盖写。

### 12.2 分配成功不等于用户数据写入完成

完整顺序是：

```text
新物理块分配
    -> 新块清零 / 旧数据复制
    -> Bitmap + Mapping + Root 持久化
    -> Completion 返回 Mapping
    -> 原始 BIO 写入实际数据
    -> 底层 BIO 完成
```

因此监控和错误处理必须区分元数据分配事务成功与实际用户数据 I/O 成功。

### 12.3 每个写请求涉及内核 / 用户态往返

当前写请求需要 Request Ring、Metadata Service 处理、Completion Ring 和内核重新提交 BIO。后续可以优化批量处理、AG 并发、COW 写放大和数据路径开销，但不得破坏 OwnerEpoch / Fencing、WAL 原子性、幂等重放和 Reader Generation 安全约束。

### 12.4 当前验收边界

软件实现和 CI 通过不等于生产 SAN 验收完成。仍需真实环境验证：

- SAN 双节点并发和 Owner 接管。
- multipath 路径丢失、恢复和设备 flush 行为。
- WAL 各关键阶段断电 / 崩溃注入。
- 内核 5.15 DM BIO 端到端运行。
- 小块随机写、顺序写、混合读写和高并发性能。
- COW、Bitmap、WAL 和 Completion 各阶段的延迟分布。
