# P3-3.12.3.7 — SCSI PR path-scoped registration lifecycle

This phase hardens reader registration and Owner fencing for multipath LUNs.

## Path-scoped key model

Each configured `PRPath` is a component device plus the local initiator key
registered through that component path. Keys may differ across component
paths. For example:

| Component path | Local initiator key |
|---|---:|
| /dev/sda | 0xa1 |
| /dev/sdb | 0xb2 |

The local key for /dev/sda is checked and used only on /dev/sda. The fencer
must not require 0xa1 to appear on /dev/sdb, or vice versa. This matches the
registrar's path-scoped REGISTER operations.

The target NodeID/BootID resolver returns all keys belonging to that old
initiator instance. The fencer checks each target key on every component path,
uses that path's local key for PREEMPT AND ABORT, and verifies every target key
is absent from every component path. It also verifies that each new Owner's
local key remains registered on its own path.

## Registration transaction

`SCSIPRRegistrar.RegisterReader` now follows this sequence:

1. Validate the complete path/key set.
2. Read every component path and determine whether its local key is already
   registered. Any unreadable path aborts before any mutation.
3. Register only missing keys, one on each corresponding path, with APTPL.
4. Verify each path-scoped key.
5. If a registration command fails or verification fails, unregister every
   key this invocation attempted to create, in reverse order, and verify its
   absence. Pre-existing keys are not removed.

A command error is treated as an ambiguous outcome: the target may have
committed the registration even though the initiator did not receive a
successful response. Therefore the current path is included in rollback
before issuing REGISTER. Rollback uses a bounded cleanup context independent
of caller cancellation. Cleanup failures are joined with the original error
and must be treated as an operator-visible partial-state condition.

## Fencing preflight and ordering

Before any PREEMPT AND ABORT, the fencer verifies that every local key is
registered on its own configured component path. A missing or unreadable
local path key aborts before fencing starts, preventing avoidable partial
fencing caused by a broken local key map.

After preflight, the fencer performs PREEMPT AND ABORT for each discovered
target key on every path where that key is present. Final verification checks:

- the current Owner's path-local key is still present on its own path;
- each target key is absent from every successfully queried component path;
- any command or path failure returns an error (never interpreted as absence).

A successful function return still means only that the configured component
paths were queried and the target registration keys were absent. It does not
replace old-owner I/O drain, sanlock ownership, reservation-holder/type
validation, OwnerRecord CAS, durable OwnerEpoch publication, or DM fail-stop.

## Tests

Fake-runner tests cover:

- different local keys on different component paths;
- no cross-path requirement for local keys;
- local-key preflight before any PREEMPT operation;
- all-path target-key absence verification;
- preflight failure before registration mutation;
- rollback after a later-path registration failure, including ambiguous
  command outcome handling;
- successful register/unregister lifecycle.

These tests do not exercise real SCSI targets, HBA behavior, multipath
topology, APTPL persistence, or controller failover. Repeat the P3-3.12.3.6
qualification procedure on a disposable LUN with the actual target and every
component path before production use.
