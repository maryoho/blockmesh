# P3-3.12.3.13 — Owner Fencing durable recovery, crash restart and Epoch monotonicity

## Objective

Qualify recovery from process/host interruption at the Owner takeover publication
boundaries. The SAN OwnerRecord is the durable identity of the last Owner;
BMDVOL02 OwnerEpoch is the durable metadata fencing epoch; sanlock serializes
the recovery transaction; SCSI PR fences the prior initiator. A restarted
process must reconstruct state from SAN bytes, never from volatile process
memory, and must fail closed when the durable identity cannot be trusted.

## Recovery invariants

1. A new process reopens both 4 KiB OwnerRecord slots and selects the valid
   record with the greatest record generation.
2. A torn inactive-slot write cannot destroy the previous valid copy. If both
   copies are invalid/nonzero, recovery fails with
   `ErrSANOwnerRecordCorrupt`; it must not infer an Owner identity.
3. A failed OwnerRecord Sync is an ambiguous commit. The caller must abort
   activation and release its sanlock lease. The next owner reloads the slots
   and fences whichever complete identity is actually present.
4. Once an OwnerRecord has been durably published, any later failure (PR
   RESERVE, verification, sanlock loss, process crash) leaves that identity
   available for the next takeover to fence.
5. The next OwnerEpoch is strictly greater than both the current BMDVOL02
   descriptor OwnerEpoch and the durable OwnerRecord Epoch:
   `next = max(descriptorEpoch, ownerRecordEpoch) + 1`.
6. Epoch arithmetic never wraps. If the maximum durable epoch is
   `math.MaxUint64`, takeover fails with `ErrOwnerEpochExhausted`.
7. The BMDVOL02 descriptor publication remains a separate cluster-safe WAL
   transaction. A crash after OwnerRecord publication but before descriptor
   publication is recovered by taking the maximum of the two durable epochs.
8. Missing OwnerRecord with descriptor OwnerEpoch > 1 remains a hard error:
   the system cannot safely identify/fence the previous initiator.
9. No recovery path opens DM write admission. The normal runtime must complete
   WAL recovery, descriptor OwnerEpoch publication, Reader/metadata recovery,
   and the guarded DM prepare/enable sequence under a still-valid sanlock
   lease.

## Added qualification tests

### SAN OwnerRecord restart tests

`internal/volume/owner_recovery_test.go` reconstructs a new
`SANOwnerRecordStore` over the same SAN-device byte image to model process
restart. It verifies:

- the highest durable record generation is selected after restart;
- a torn inactive slot falls back to the previous valid copy;
- a subsequent update after recovery advances from the valid copy;
- two corrupt nonzero slots fail closed rather than returning an empty store.

### Owner takeover crash-point test

The test injects a lost PR RESERVE response after OwnerRecord publication.
The first coordinator must fail and release its sanlock lease while leaving the
new durable Owner identity intact. A second coordinator, with a fresh store
handle, must fence and drain that identity before publishing the next epoch.
This models the ambiguous PR command completion boundary; it does not execute
a real SCSI PR command.

### Epoch monotonicity matrix

Tests cover both possible ordering discrepancies:

- OwnerRecord Epoch ahead of descriptor OwnerEpoch (crash after identity
  publication, before descriptor publication);
- descriptor OwnerEpoch ahead of OwnerRecord Epoch (recovery/repair case).

The next epoch must be one greater than the maximum. A near-overflow case
verifies that the coordinator does not wrap the uint64 Epoch.

## Crash-point recovery table

| Crash point | Durable state expected | Recovery rule |
|---|---|---|
| Before OwnerRecord write | Previous record remains authoritative | Fence previous identity; allocate next epoch |
| During inactive-slot write | Previous valid slot remains readable | Ignore torn copy; do not activate from corrupt-only state |
| OwnerRecord write completed, Sync response lost | Either old or new complete slot may be durable | Reload both slots; fence the selected identity |
| OwnerRecord Sync completed, before PR RESERVE | New OwnerRecord is durable | Fence that identity, then advance Epoch |
| PR RESERVE may have succeeded, response lost | New OwnerRecord is durable; PR outcome uncertain | Fence its initiator identity on every path before next activation |
| PR verified, before descriptor OwnerEpoch WAL commit | OwnerRecord may be ahead of descriptor | Use max(record, descriptor)+1 |
| Descriptor OwnerEpoch WAL commit completed | Both records describe completed takeover epoch | Next takeover advances beyond both |
| Both OwnerRecord copies corrupt | No trustworthy previous identity | Fail closed; require offline/operator recovery |

## Verification

GitHub Actions executes:

- `go test ./...`
- `go test -race ./...`
- `go vet ./...`

These are deterministic Go tests over memory-backed SAN device images and
simulated sanlock/PR components. They verify restart logic and state-machine
ordering, not physical persistence.

## Qualification still required on the target platform

Before production qualification, run the following on a dedicated test LUN
with the deployed Linux 5.15.131 kernel, actual array, two initiators, and the
full multipath path inventory:

1. Cut power or terminate the host/process at every crash point in the table.
2. Include array/controller failover and cache-protection/flush failure cases.
3. Reboot both nodes independently and verify that no local file, PID,
   heartbeat, process memory, or stale DM table can override the SAN record.
4. Inspect both OwnerRecord pages and both BMDVOL02 descriptor copies after
   each injection; record generation, Epoch, CRC, WAL sequence and flush
   evidence.
5. Verify PREEMPT AND ABORT and reservation holder/type on every path, then
   verify the old initiator cannot write.
6. Verify no new DM write gate opens until the durable descriptor Epoch and
   sanlock/PR proofs agree.

A memory-backed test passing is not evidence of power-loss durability, SAN
array cache persistence, SCSI PR behavior, or real two-node fencing.
