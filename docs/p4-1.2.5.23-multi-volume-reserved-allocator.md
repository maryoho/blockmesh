# P4-1.2.5.23 — Multi-Volume Reserved Metadata Allocator

## Overview

The BMPOOL03 Reserved region can be managed by a persistent page bitmap instead of assigning all pages to Volume descriptor slot 0.

The allocator uses:
- Two 4KiB checksummed allocator headers at the beginning of Reserved.
- A one-bit-per-4KiB-page allocation bitmap after the headers.
- A contiguous first-fit allocator for each Volume's Arena and optional Lifecycle pages.
- The existing NodeTable Volume Descriptor pair for each Volume slot.
- A cluster-safe Dynamic WAL transaction to publish bitmap pages, the inactive allocator header, and both initial Volume Descriptor copies.

The allocator must be formatted on a newly formatted Pool before any Volume Descriptor/Arena pages are published. Legacy BMPOOL03 Pools without the allocator remain readable through the existing descriptor path.

## Allocation

`FormatDynamicVolumeAllocator` scans the Reserved region and refuses non-zero content. It persists a matching format marker before initializing the bitmap, then publishes both allocator headers. `RecoverDynamicVolumeAllocatorFormat` resumes only a matching interrupted initialization.

`AllocateVolume` reserves Arena plus Lifecycle pages, verifies the target descriptor slot is unused, checks Volume ID uniqueness, and publishes the allocation bitmap/header and both descriptor copies in one cluster-safe WAL transaction.

## Release and fencing

`ReleaseVolume` requires a `DynamicVolumeFencingProof` implementation. The proof must establish that all initiators for the Volume are fenced for the exact Volume ID and OwnerEpoch. A timeout, expired heartbeat, or boolean assertion is not accepted.

The transaction clears both descriptor copies and releases the page bitmap allocation. If the fencing proof is unavailable or fails, the pages remain allocated.

## Current boundaries

- Allocation is contiguous and first-fit; fragmented multi-extent Arena allocation is not implemented.
- The allocator's bitmap geometry is bound to the MetadataBytes/ReservedOffset generation used to format it. A metadata growth workflow must explicitly migrate/expand this allocator before opening it against a larger Reserved region.
- Existing legacy slot-0 Arena expansion remains a legacy path; it must not be mixed with the new Reserved allocator until a coordinated GrowVolume/allocator-expansion operation is used.
- Fenced release is implemented as an API contract; production wiring to the platform's all-path SCSI PR/Fencer proof is part of Owner/Fencing integration.

## Validation

Tests cover dual-header formatting/open, multiple independent Volume reservations, descriptor visibility, duplicate Volume ID rejection, non-overlap, fenced release/reuse, bitmap CRC validation, non-empty-region refusal, and format-marker recovery.
