# P3-3.12.3.8 — SCSI PR Reservation state verification

This phase extends the read-only `bm-san-qualify` evidence workflow from
registration-key absence to active Persistent Reservation state verification.

## What is verified

The collector already executes `sg_persist --in --read-reservation` on every
explicitly supplied multipath component path. It now parses and persists:

- whether a reservation is present;
- reservation holder key;
- reservation scope, when reported;
- SCSI PR type code and canonical name;
- whether the type is an All Registrants type (7 or 8);
- whether the response was completely and unambiguously parsed.

Supported PR type codes are 1, 3, 5, 6, 7 and 8. The parser accepts the
human-readable `sg_persist` type names and a numeric `type=` representation.
Unknown/vendor-specific types and ambiguous/multiple holder keys remain
unparsed; they are never guessed.

## Verify expected Owner reservation

Collect a fresh evidence file after the takeover operation, using the same
explicit all-path procedure documented in P3-3.12.3.6. Then run:

```bash
./bm-san-qualify verify-reservation \
  --evidence node-b-after-takeover.json \
  --holder-key 0x0123456789abcdef \
  --type 6
```

The expected holder key must be the trusted PR key assigned to the new Owner
identity. The type must match the deployment's configured reservation type;
the example uses type 6 (Exclusive Access, Registrants Only), matching the
current SCSI PR fencer default.

The JSON report includes the common WWID and each component path's observed
device, WWID, reservation-present flag, holder key, type/name and parse status.
The command exits successfully only when every path has a readable, parsed
reservation with the expected holder key and expected type.

## Fail-closed interpretation

- **PASS:** all supplied paths resolve to the same non-empty WWID and report
  the expected active reservation holder key and type.
- **FAIL:** a path reports no reservation, a different holder key, or a
  different reservation type.
- **INCONCLUSIVE:** a reservation query fails, parsing is incomplete, a path
  has no WWID, or the multipath path coverage is not verified.
- Conflicting WWIDs or duplicate/empty evidence paths are rejected.

The command only evaluates the JSON evidence captured by `collect`; it does
not issue RESERVE, REGISTER, PREEMPT AND ABORT, or any other mutating command.
It does not make a live query during verification, so evidence must be
collected immediately after the operation being qualified and retained with
its timestamps and raw command output.

## What this does not prove

A matching PRIN READ RESERVATION response is necessary evidence, not a complete
RW-safety proof. It does not prove sanlock exclusivity, OwnerRecord CAS,
durable OwnerEpoch publication, old-node I/O exclusion, old DM queue drain,
WAL recovery correctness, or that the DM target admits requests only after all
those conditions. All multipath paths must remain accessible and agree.
Production acceptance still requires the two-node fault-injection procedure
on the actual SAN target, HBA and multipath stack with a disposable LUN.
