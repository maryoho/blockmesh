# P4-1.3.4.3 — Request Deadline, Cancellation and Idempotent Retry

## Request deadline

The metadata service applies a configurable per-request timeout at the queue consumer boundary. `ServiceConfig.RequestTimeout` defaults to 30 seconds; zero in the service configuration selects the default, while the low-level `OpenDeviceWithTimeout` API accepts zero to disable the deadline. A negative timeout is rejected.

Each request receives a child context. The service cancels it after processing and propagates parent shutdown cancellation. The allocator already checks the context while waiting for the distributed AG lock, during zero/copy work, and immediately before metadata publication. Long-running data operations must continue to check the context at bounded intervals.

## Completion semantics

- A request canceled before its metadata transaction begins or before publication is known not committed; it may be retried with the same idempotency key.
- A successful transaction returns its committed result even if the caller's deadline expires immediately afterward. A known commit must never be converted into a timeout error.
- An ambiguous WAL publication error is `allocator.ErrAllocationOutcomeUnknown`. The runtime is poisoned and deactivated; recovery replays the AG WAL and reopens the persistent tree before the same key can be retried.
- A retry with the same key and canonical fingerprint resolves the durable Idempotency Record and returns the original allocation/discard result. Reusing a key with a different fingerprint is rejected.

Transport identity (`RequestID`, `QueueGeneration`, node/boot identity and OwnerEpoch) is not part of the durable mutation fingerprint, so a retry can survive queue recreation and Owner takeover. The queue generation is still checked before publishing a completion.

## Scope and ABI

No request ABI layout change is made in this stage. Deadline policy is configured by the metadata service; cancellation is conveyed through Go contexts from queue draining into the Processor and allocator. This keeps the fixed 128-byte request ABI compatible with the existing kernel module.

## Validation

The ring tests verify that a per-request deadline and parent cancellation reach the Processor and produce retry completions. Existing allocator crash-recovery tests cover committed WAL outcomes, uncommitted intent recovery, replay of the same idempotency key, and prevention of duplicate physical allocation.
