# P4-1.2 — Fixed-width UAPI and queue contract

## Scope and implementation boundary

This increment defines the byte-level Linux 5.15 kernel/userspace ABI: fixed-width little-endian records, ioctl numbers, mmap offsets, bounded ring sizing, request correlation, and generation-bound cancellation/reset semantics. The C header is kernel-facing; internal/uapi is the Go reference encoder/decoder and queue-lifecycle contract. One node-wide character device is shared by all DM Targets; each Target owns a distinct Queue Context.

This increment implements Go codecs and validation for GET_ABI, SETUP_QUEUE and CANCEL payloads, mmap layout calculation, and a concurrency-safe completion correlator. It does NOT register a character device, map ring pages, submit DM BIOs through the queue, or connect the metadata service to SAN-backed metadata. The DM target therefore remains the existing linear remapper. This is still an ABI/control-protocol foundation, not a live data-path transport.

## Wire records

| Record | Bytes | Purpose |
|---|---:|---|
| Ring control | 64 | Shared indices, ring size and generation |
| Request | 128 | Identity, operation, logical range and idempotency key |
| Completion | 64 | Request correlation, status and payload reference |
| Mapping | 24 | Logical/physical block run |
| Setup ioctl | 80 | Ring order, generation and mmap offsets |
| Cancel ioctl | 40 | Request ID and queue generation |
| ABI info | 64 | Version, record sizes, limits and feature bits |

All multibyte fields are little-endian. UUIDs are binary 16-byte values. Version and exact size are present in request/completion records. Reserved fields must be zero. Logical and physical block numbers use the allocator's 4MiB block unit. Mapping payload length must equal mapping_count * 24; non-success completions cannot carry payload.

## Queue layout

One service process owns the exclusive node-wide device session. Ring size is 1 << ring_order, where 4 <= ring_order <= 10. The five page-aligned offsets below are queue-local offsets. For a shared `/dev/blockmesh` FD, userspace encodes each mmap byte offset as `(queue_id << 44) | queue_local_offset`; queue IDs are monotonic, non-zero 19-bit values and are never reused during a module lifetime. The low 44 bits carry the local offset, and the high 19 bits select the queue. This gives each queue a disjoint 16TiB virtual-offset window without allocating that address space. The five queue-local offsets are:

| Offset | Region | Producer | Consumer |
|---:|---|---|---|
| 0x00000000 | Request control | Kernel | Service |
| 0x00010000 | Request ring | Kernel | Service |
| 0x00040000 | Completion control | Service | Kernel |
| 0x00050000 | Completion ring | Service | Kernel |
| 0x00060000 | Mapping payload slots | Service | Kernel |

For every supported ring order, Layout() verifies that the request ring ends before completion control and completion ring ends before payload. Payload reserves MaxBatch mapping records per ring slot. Total mmap size is page aligned. Rings are SPSC. Producer writes the entry/payload then publishes tail with release ordering. Consumer loads tail with acquire ordering, reads the entry, then publishes head after consumption. Kernel owns request indices; userspace owns completion indices. The other side must never write an index it does not own. Shared indices require smp_load_acquire/smp_store_release in kernel and matching atomics in userspace.

## ioctl lifecycle

1. GET_ABI negotiates version, record sizes and limits.
2. The service opens `/dev/blockmesh` once (exclusive opener), enumerates Target-created queues with NEXT_QUEUE, and calls SETUP_QUEUE for each Queue ID. The kernel attaches the service session and returns queue ID, offsets, generation and limits. Userspace validates every returned offset against Layout() plus the queue-ID encoding before mmap.
3. Service mmaps all regions, validates dimensions, then drains requests.
4. CANCEL is reserved in this increment and returns EOPNOTSUPP; the kernel request registry and cancellation state machine are deferred until request submission is implemented. The Go Correlator remains a reference model only.
5. RESET_QUEUE advances the generation and clears the currently attached ring memory. It does not yet cancel queued BIO work or synthesize terminal completions because BIO submission is not implemented.
6. Service FD close detaches all queues, advances their generations, invalidates outstanding requests and wakes waiters. Target removal destroys only that Target's queue; VMA references defer memory release. Teardown must not wait indefinitely for userspace.

Request correlation key is (queue_generation, request_id). Correlator rejects duplicate in-flight IDs, ignores completions for cancelled requests, stale generations, unknown IDs and duplicate completions. Reset clears all pending IDs and requires a different non-zero generation. IDs must not wrap within a generation.

## Identity and failure behavior

Each request carries VolumeID, NodeID and BootID UUIDs. Mutations and FLUSH require OwnerEpoch; allocation/discard also require a 128-bit idempotency key. RO lookups carry ReaderEpoch and RootGeneration; RW lookups carry OwnerEpoch. Queue generation is transport fencing, not a replacement for OwnerEpoch, sanlock, or SCSI PR fencing.

Disconnect, timeout, malformed completion, queue exhaustion, or generation mismatch are fail-closed. The target must not reuse a cache generation after service restart and must never fall back to linear I/O. A stale OwnerEpoch response cannot reopen the DM write gate.

## Validation boundary

Go tests cover serialization, fixed sizes, reserved fields, identity/epoch/idempotency requirements, completion payload constraints, mmap bounds at every ring order, setup-offset validation, and completion correlation across cancellation/reset. They do not validate C compiler layout, kernel mmap lifetime, SMP ordering, Linux 5.15 DM teardown, or SAN fencing. The kernel endpoint patch must add sizeof/offsetof static assertions and compile against supported 5.15 kernel headers before ABI qualification. P4-1.2.1 adds the global misc character device, Target-owned Queue Context registry, exclusive service FD, GET_ABI/NEXT_QUEUE/SETUP_QUEUE/RESET_QUEUE handlers, queue-scoped mmap, VMA references, registry-change EPOLLPRI, and aggregate request EPOLLIN scan. A service restart detaches and drops the old queue memory object; old VMAs retain their old pages and cannot alias the new generation's mapping. Request production from DM BIOs, completion consumption, cancellation registry, and metadata-service transport remain deferred. The current kernel build is compile qualification against Linux 5.15 headers; it is not runtime validation of mmap, poll wakeups, Target teardown, or actual DM BIO traffic. The device currently provides queue lifecycle and shared-memory mapping primitives, not a functional BIO data path.


## P4-1.2.2 — Kernel Request Ring and BIO handoff

The kernel is now the Request Ring producer. DM map() captures each supported BIO, builds a fixed-width request, registers its pending BIO by (queue_generation, request_id), copies the ring slot, and publishes the producer tail with release ordering. The service observes requests through aggregate poll(). A full ring returns DM_MAPIO_REQUEUE; an unconsumed entry is never overwritten.

The service publishes a Completion Ring entry and invokes BM_IOC_KICK(queue_id). The kernel consumes completion entries with acquire/release index ordering, matches the exact request ID and queue generation, then submits the original BIO to the mapped underlying block device. A completion is accepted only with one contiguous mapping covering the BIO's complete logical block range. Non-OK, malformed, stale, unknown, or unsupported multi-extent completions fail closed. Unmapped reads are not zero-filled in this increment and therefore fail closed rather than exposing stale data.

The DM table now requires five arguments: <device> <start_sector> <volume_uuid_hex32> <node_uuid_hex32> <boot_uuid_hex32>. Stable Volume/Node/Boot identities are copied into every request. Requests use the current OwnerEpoch; RO ReaderEpoch/RootGeneration admission is not implemented yet. Writes require the existing Owner gate. Flush is submitted as a metadata operation; discard and write-zeroes are represented as metadata mutations.

Queue reset, service FD close, and Target destruction abort pending BIOs before releasing ring memory. Target drain counts all submitted BIOs, not only writes. Cancellation remains unsupported. The mapping handoff currently supports one contiguous mapping per BIO; splitting a BIO across physical extents, zero-filling unmapped reads, RO reader views, and runtime qualification remain subsequent work.


Completion payload ownership is tied to the completion slot: payload_offset must equal (completion_head & (ring_entries - 1)) * MaxBatch * sizeof(mapping). The kernel copies the single supported mapping record before releasing the queue lock, so reset/disconnect cannot invalidate a mapping while it is being consumed. Completion publication must store the new tail with release semantics before issuing BM_IOC_KICK.


The matching Go UAPI package exports FeatureRequestRing, FeatureCompletionKick, and IoctlKick. The Linux ioctl value is _IOW('B', 0x05, uint32). A completion with no mapping is valid only for FLUSH or an error; a successful data BIO requires exactly one 24-byte mapping record. Flags and reserved fields must be zero.

The physical mapping returned by the service is additionally constrained to the Target's configured underlying extent `[start_sector, start_sector + target_length)`, not merely to the full backing block device. This prevents a malformed or stale completion from redirecting a BIO into another region of the same LUN.


# P4-1.2.3 — Metadata Service Ring Consumer and Completion Producer

This increment adds the Go-side SPSC ring consumer/completion producer and Linux
`/dev/blockmesh` transport. The service negotiates GET_ABI, enumerates queues
with NEXT_QUEUE, attaches each queue with SETUP_QUEUE, maps the five regions,
waits for POLLIN/POLLPRI, drains requests, publishes completions, and calls
BM_IOC_KICK. Queue discovery is repeated on POLLPRI so newly created DM Targets
are attached without restarting the service.

The ring pump validates the queue generation and request correlation identity,
reserves completion capacity before invoking the metadata Processor, validates
the returned single contiguous mapping, writes the mapping payload and completion
record, publishes completion tail, then advances request head. Go sequentially
consistent atomics provide at least the acquire/release ordering required by the
kernel SPSC protocol. Malformed requests without a usable request ID/generation,
corrupt indices, invalid mappings, and transport errors fail the service closed;
closing the exclusive character-device FD causes the kernel to abort outstanding
BIOs.

Processor is intentionally an explicit authority boundary. Its implementation
must validate VolumeID/NodeID/BootID, OwnerEpoch or ReaderEpoch/RootGeneration,
and mutation idempotency against the active SAN-backed runtime. The
AllocateZeroPublish contract requires data zeroing to complete before the
mapping is durably published. Flush must durably flush metadata. This commit
does not wire the demo JSON Engine or NoopFencer into the live kernel service.
The production Pool runtime still needs a concrete mapping/allocator adapter and
the zero-before-publish transaction; no command-line production service is
advertised until that adapter exists.

Logical DISCARD returns a metadata-only completion. The kernel completes the
original discard BIO without issuing an early physical discard, because the
old physical extent may remain visible to RO readers until Reader Generation
advances and fencing permits reclamation. Physical reclamation/discard remains
owned by the retire/reclaim path.

Validation in this increment is unit-level ring/ABI testing plus Linux build
coverage. It does not prove runtime mmap/poll behavior or real SAN operation.


The wire ABI continues to represent a batch of up to MaxBatch mappings. The current Linux DM BIO handoff only consumes one contiguous Mapping per BIO; the P4-1.2.3 ring pump enforces that narrower runtime capability without weakening the ABI codec.

The Linux service reconciles the queue registry on each POLLPRI notification and unmaps userspace VMAs for Target Queues that have been destroyed. The kernel VMA reference keeps pages safe until the service drops those mappings.
