# P4-1.3.5.5 — Pool bootstrap lifecycle integration

The lifecycle backend now connects `bmctl pool create` to
`poolinit.Initialize`. The operation:

1. Requires the device path to be explicitly listed in `discovery_devices`.
2. Resolves a stable WWID/serial and selects only configured SCSI PR paths
   with the same identity.
3. Acquires a distributed sanlock Pool Owner resource derived from that ID.
4. Rejects foreign PR registrations/reservations, registers the local
   initiator, establishes and verifies its reservation on every configured
   path, and revalidates that reservation through the Pool initialization
   phases.
5. Initializes/resumes the BMPOOL03 Bootstrap, dynamic Metadata/Data views,
   bitmap geometry and Reserved Volume catalog.
6. Releases the temporary bootstrap PR reservation and local registrations
   before releasing the sanlock lease.

A fully initialized Pool create is idempotent: the backend validates its
Bootstrap, Superblock and Reserved allocator and returns the existing catalog
entry without attempting to take over an active Pool.

## Recovery boundary

The Bootstrap format does not yet persist a complete previous Pool Owner
identity. Therefore an interrupted bootstrap that leaves a foreign PR
registration is deliberately rejected. It must not be force-preempted using
guessed keys or a volume-scoped drain helper. A same-initiator retry can
resume when only the configured local registrations/reservation remain.
Cross-node interrupted-bootstrap recovery requires a durable Pool Owner
record and a Pool-scoped drain/fencing workflow; this is a remaining item,
not silently treated as supported.

The sanlock resource is based on the device WWID/serial, not the local device
path. All configured SAN paths selected for the Pool must resolve to the same
identity. Validate this behavior on the target multipath and direct-iSCSI
devices before production use.

## Destructive-operation confirmation

`bmctl pool create <name> <device>` requires the operator to type the Pool
name at an interactive terminal. Non-interactive automation must pass
`--yes`. The CLI sends an explicit `confirmed=true` field; both the RPC
handler and lifecycle backend reject requests without it. This prevents a
direct Unix-socket client or a non-interactive script from accidentally
formatting a LUN by merely issuing the create action.
