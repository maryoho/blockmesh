# P4-1.2.5.24 — Dynamic WAL Automatic Checkpoint

## Behavior

`DynamicSharedCommitter.CommitImages` now retries a transaction once after `ErrJournalFull`:
1. Acquire the distributed AG WAL lock.
2. Open and recover the latest DynamicJournal state under that lock.
3. Attempt the WAL transaction.
4. If the append cannot fit a complete Intent or Commit record, checkpoint the active journal.
5. Retry the transaction in the newly selected empty bank.
6. Release the distributed WAL lock.

The distributed lock remains held across the initial commit, checkpoint and retry, preventing another process from appending against stale journal offsets.

## Uncommitted Intent handling

A full-bank condition while appending the Commit record can leave a durable Intent without a Commit. This is not a committed transaction. `DynamicJournal.Commit` does not poison the journal for this specific no-write `ErrJournalFull` condition. Checkpoint records the last committed TxID and switches to a cleared bank; the unmatched Intent remains in the inactive bank and is ignored.

Actual device I/O failures still poison the in-memory journal and require reopen/recovery.

## Limits

- A transaction larger than an empty bank still returns `ErrJournalFull` after one checkpoint/retry.
- The committer does not split a logical transaction across WAL transactions.
- Checkpoint is triggered on JournalFull; predictive background checkpoint scheduling and telemetry are future work.
- Owner lease/fencing validation remains an outer runtime responsibility and must be held across the complete commit/checkpoint/retry sequence.

## Validation

A shared-committer test performs more writes than one WAL bank can hold, verifies automatic bank rotation, reopens the journal, and validates every committed after-image.
