# P4-1.3.3 Mapping Vector BIO Acceptance

This document defines the repeatable acceptance boundary for P4-1.3.3. It does not claim that a real SAN or dual-node run has already passed.

## Preconditions

- Linux 5.15 host with the BlockMesh DM target and `/dev/blockmesh` module loaded.
- A disposable test LUN formatted and activated through the BMPOOL03 path.
- A single RW Owner with a valid OwnerEpoch; no unfenced second writer.
- A test DM device whose length is within the formatted Pool data range.
- `fio`, `dmsetup`, `dmstats`, `dmesg` available.
- Record device identity, multipath WWID, kernel release, module build ID, Pool UUID, Volume UUID, OwnerEpoch and test start time.

## Mapping Vector invariants

For every successful lookup Completion:

1. `mapping_count` is in `[1, 256]`.
2. `payload_bytes == mapping_count * 24` and the payload remains within the slot's fixed payload window.
3. Entries are ordered and logically contiguous; no hole, overlap or duplicate logical block is accepted.
4. The first logical block equals `request.logical_start` and the last extent ends at `logical_start + block_count`.
5. Each extent is physically contiguous internally. Adjacent logical extents are merged only when their physical ranges are also adjacent.
6. The kernel validates the entire vector and all translated sector ranges before submitting any child BIO.
7. The original DM BIO completes only after all split child BIOs complete. A failed child makes the original BIO fail.

Allocation remains one contiguous physical extent in this increment. The vector is principally used by READ lookup; allocation may return one mapping only.

## Functional matrix

| Case | Workload | Expected result |
|---|---|---|
| 4KiB random write/read | `fio` direct I/O with verify | Data verifies; partial-block COW preserves untouched bytes |
| 4MiB aligned write/read | 4MiB sequential I/O | One logical block maps and completes correctly |
| Cross-block I/O | 8MiB I/O beginning 2MiB into a 4MiB boundary | BIO is split at logical mapping boundaries and reassembled at parent completion |
| Fragmented physical mapping | Construct adjacent logical blocks with non-adjacent physical extents | Completion contains multiple mappings; read reaches each physical extent in order |
| WRITE_ZEROES | aligned and partial zero ranges | Requested bytes read as zero; bytes outside a partial range remain unchanged |
| DISCARD | 4MiB-aligned ranges only | Mapping is retired; no immediate physical reuse before Reader Generation-safe reclaim |
| Partial DISCARD | deliberately unaligned range | Rejected with I/O error; never widened to a whole 4MiB block |
| FLUSH/FUA | write, flush, reopen/read; FUA write/read | Flush reaches DataView and MetadataView; FUA remains on submitted data BIO |
| Unmapped READ | read a never-written logical block | Returns unmapped/error according to the block-device contract; never reads arbitrary physical data |
| Queue restart | stop Metadata Service with outstanding requests, restart and reattach | Old-generation completions are rejected; outstanding original BIOs fail, caller may retry |
| Completion corruption | wrong generation, count/length mismatch, invalid payload offset | Completion rejected; correlated BIO fails; no partial vector submission |
| Child BIO error | inject an underlying I/O error on one segment | Original BIO fails after all chained children drain; no early success |
| Ring pressure | saturate Request/Completion rings | No overwrite; request remains queued/retried or fails closed |

## fio smoke profile

Run only against a disposable test DM device. Replace `/dev/mapper/BM_TEST` with the actual test mapping.

```ini
[global]
filename=/dev/mapper/BM_TEST
ioengine=libaio
direct=1
time_based=1
runtime=60
ramp_time=5
group_reporting=1
verify=crc32c
verify_fatal=1
do_verify=1

[rand-4k]
rw=randwrite
bs=4k
iodepth=16
numjobs=4
size=1G

[seq-cross-boundary]
stonewall
rw=write
bs=8M
offset=2M
size=512M
iodepth=8
numjobs=1
```

Example invocation:

```sh
fio p4-1.3.3-bio-vector.fio
```

For the fragmented-mapping case, the test fixture must deliberately allocate physical extents with gaps while preserving a logically contiguous range. Do not infer fragmentation merely from running random writes.

## Fault-injection procedure

For each failure point, capture the request ID, queue generation, OwnerEpoch, BIO operation, logical range, Completion code and final BIO status:

- kill the Metadata Service after request-ring publication but before completion publication;
- kill it after metadata commit but before completion publication, then retry the same idempotency key;
- restart the service and confirm the new queue generation rejects stale completions;
- force one physical child BIO to return I/O error;
- corrupt mapping count, payload length, payload offset and logical continuity in a test-only harness;
- fill the Completion Ring and confirm the service does not execute a request without reserving completion capacity.

The post-commit retry must resolve through the persistent idempotency record and must not allocate a second physical extent.

## Production acceptance evidence

Attach:

- CI run URLs for Go tests, race tests, vet and Linux 5.15 kernel module build;
- fio output and verify summary;
- `dmsetup table/status`, `dmstats`, multipath status and kernel logs;
- before/after Pool bitmap and Mapping checks;
- Reader Generation and Data Retire Queue state before and after reclaim;
- dual-node fencing and path-failure evidence.

A passing CI build is not a substitute for dual-node SAN power-failure, path-loss, reservation and performance acceptance.
