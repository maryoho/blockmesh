# P3-3.12.3.11 — DM Target OwnerEpoch validation and kernel write admission

## Scope

This phase adds a Linux 5.15 Device Mapper target named `blockmesh` and a Go
`dmsetup message` adapter. The target maps a configured range linearly to an
underlying block device. Every operation except ordinary READ is subject to a
kernel-resident OwnerEpoch gate. Reads remain available while the RW gate is
closed. SCSI PR PREEMPT AND ABORT remains the cross-node fencing authority.

## Kernel state and transitions

Every target starts closed: epoch 0, gate closed, fenced=true, inflight=0.
The fast path uses a spinlock; control messages use a mutex.

- `owner_prepare E`: close and fence the current generation, wait for all
  admitted mutating bios, then install E only if E is strictly newer. Remain
  closed.
- `owner_enable E`: open only the exact prepared epoch, only if it is not
  fenced and no previous write remains in flight.
- `owner_fence E`: reject E older than the kernel epoch; otherwise close,
  fence, advance the local epoch if E is newer, and wait for in-flight writes.
- Go `Drain(E)` is the same epoch-scoped fence. It is deliberately not an
  unscoped message: a delayed old runtime must not close a newer Owner.

The map callback checks the gate and increments the in-flight counter under
the same spinlock. end_io decrements it. A bio is either counted before gate
closure and included in drain, or rejected after closure. All non-READ
operations (write, flush, discard, write-zeroes and unknown opcodes) fail
closed when the gate is closed.

A delayed fence for an older epoch cannot close a newer generation. A delayed
enable cannot open an old or fenced generation. A fenced epoch cannot be
re-enabled; a strictly newer epoch is required.

## Pool runtime wiring

`internal/dmowner.DMSetupGate` sends argv-safe messages through `dmsetup`.
The Pool runtime requires a real `dmowner.Gate` and a
`DMDeviceFor(volumeID)` resolver. RW activation performs:

1. acquire sanlock Owner lease and complete SCSI PR fencing/reservation proof;
2. recover WAL and publish BMDVOL02 OwnerEpoch durably;
3. prepare the kernel target with that epoch while keeping it closed;
4. execute the final synchronous sanlock health guard;
5. enable the exact epoch in the kernel;
6. return to the platform guarded queue-enable hook.

Lease loss closes/fences the kernel target and waits for admitted writes before
external fail-stop and software drain. Normal deactivation also fences the
target before draining and releasing the Owner lease. Gate/drain failure blocks
cleanup and retains resources.

Linux bios do not carry a BlockMesh OwnerEpoch tag. This target therefore does
not claim per-bio epoch metadata validation: it validates epochs on control
transitions and checks the current kernel gate on every mutating bio. A future
per-bio epoch ABI requires explicit propagation from the upper request layer.

## DM table and build

Table syntax:

```text
0 <length-sectors> blockmesh <underlying-device> <start-sector>
```

Example only; use actual geometry and a disposable device:

```bash
cd kernel/dm-blockmesh
make KDIR=/lib/modules/$(uname -r)/build
insmod dm-blockmesh.ko
dmsetup targets | grep blockmesh
dmsetup create bm-vol --table "0 2097152 blockmesh /dev/mapper/mpatha 0"
dmsetup status bm-vol
```

The initial gate is closed. Do not manually enable production volumes; the
Pool runtime owns epoch publication and lease validation. Use a read-only DM
table for RO attachments. Validate mapping, read/write/flush/discard, message
ordering and teardown on a disposable LUN before deployment.

## Qualification boundary

Go CI tests the message adapter and Pool runtime sequencing. It does not
compile the module because runner headers do not match the deployment kernel.
A module build and KUnit/disposable-device tests against exact Linux 5.15.131
remain mandatory. Real SAN dual-node fencing and power-loss qualification are
not claimed by CI.
