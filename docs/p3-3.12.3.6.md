# P3-3.12.3.6 — Real SAN qualification evidence tool

This phase adds `bm-san-qualify`, a read-only evidence collector and PR
registration verifier for a two-node shared-SAN qualification exercise.

## Safety contract

The tool is deliberately read-only. It invokes only:

- `multipath -ll`, `dmsetup info/status`, `lsblk`;
- `sanlock client status`, `sanlock status`;
- `udevadm info`;
- `sg_persist --in read-keys` and `sg_persist --in read-reservation`.

It never invokes `sg_persist --out`, PREEMPT AND ABORT, PR REGISTER/RESERVE,
`sanlock client command`, `dmsetup suspend/resume`, `multipath -f`,
`systemctl stop`, reboot, poweroff, or writes to the SAN LUN. Fault injection
must be performed by an operator or an independently reviewed lab automation
system. This prevents a qualification helper from accidentally fencing a
production host or changing reservation state.

## Build

```bash
go build -o bm-san-qualify ./cmd/bm-san-qualify
```

Runtime dependencies on each node: `multipath-tools`, `device-mapper`,
`sanlock`, `sg3_utils` (`sg_persist`), `udev`, and permission to read the
relevant block-device and sanlock state. Run with sufficient privileges for
read-only SCSI PR queries; do not grant the tool broader privileges than
needed.

## Collect evidence on both nodes

First obtain the exact component paths from `multipath -ll <map>`. Pass every
path explicitly; the collector rejects duplicate paths and validates that
each supplied path is a block device. It compares the explicit list with
component paths parsed from the multipath map and stores raw command output.

On Node A:

```bash
sudo ./bm-san-qualify collect \
  --device /dev/mapper/mpatha \
  --paths /dev/sda,/dev/sdb \
  --volume-id vol-a --node-id node-a --boot-id "$(cat /proc/sys/kernel/random/boot_id)" \
  --output node-a-before.json
```

On Node B, use its local multipath map and component paths and write
`node-b-before.json`. Repeat collection after each scenario, with distinct
output names. Evidence files are created with mode 0600 and `O_EXCL`; existing
files are never overwritten.

The JSON includes command, arguments, timestamps, duration, exit code, raw
output, path WWID, per-path PR keys and reservation response, multipath map
state, DM state, sanlock status, and warnings. A failed command is retained
as evidence and must not be interpreted as an empty result.

## Verify the old Owner PR key is absent

After the new Owner has executed its production Fencing operation, collect a
fresh evidence file from the new Owner node. Then:

```bash
./bm-san-qualify verify-fenced \
  --evidence node-b-after-takeover.json \
  --target-key 0x0123456789abcdef
```

The verifier succeeds only if the old registration key is absent from every
listed component path and every path's PR-key query succeeded. A missing or
failed path query is UNKNOWN and fails closed. This is only a PR registration
absence check; it is not proof that the old host cannot issue I/O, that the
new reservation holder/type is correct, or that the old node's local DM queue
has drained.

## Two-node qualification sequence

Run only on a disposable test LUN with an approved maintenance window and
out-of-band console/power control:

1. Record baseline evidence on both nodes; confirm the same LUN WWID and
   complete path set. Save sanlock status, DM status and PR key/reservation
   output.
2. Verify that each node's local initiator key is registered on every path.
   Record the key-to-(NodeID, BootID) mapping from the trusted key resolver.
3. Start a bounded write workload with monotonically increasing sequence
   numbers and checksums. Record completed writes and flush/FUA behavior.
4. Request RW on Node A. Confirm OwnerRecord identity, BMDVOL02 OwnerEpoch,
   sanlock ownership and DM admission state agree before the workload starts.
5. Trigger one failure at a time using the lab's external controls: hard power
   off Node A; isolate its SAN paths; stop/kill the sanlock helper; or make one
   target path unavailable. Do not combine faults initially.
6. Request takeover on Node B. Capture evidence before and after fencing.
   Confirm the old key is absent on every path, old-owner I/O drain succeeds,
   OwnerRecord and both Volume Descriptor copies publish the new epoch, and
   only then the DM target admits RW.
7. Attempt a controlled write from the old node only after it is safely
   isolated from the test LUN. It must fail. Never reconnect an unfenced old
   initiator to the live test LUN merely to prove failure.
8. Verify data checksums and sequence continuity from the independent test
   client. Repeat with one path unavailable and with Kubernetes API outage.
9. Restore the environment and collect final evidence from both nodes.

A PREEMPT AND ABORT success response is not sufficient: inspect every path
after the operation. If any path is inaccessible, any key query fails, WWIDs
differ, the old key remains, old I/O cannot be drained, or the new epoch is
not durably published, the test result is FAIL/INCONCLUSIVE and RW must remain
disabled.

## Evidence interpretation

- `verify-fenced` PASS: old PR key is absent from all listed, successfully
  queried component paths. It does not establish full fencing by itself.
- FAIL: old key remains on at least one path.
- INCONCLUSIVE: any path is unqueryable or the evidence is incomplete.
- Production takeover PASS additionally requires proof of old-node I/O
  exclusion, sanlock single ownership, DM fail-stop/drain, OwnerRecord CAS,
  WAL recovery, and matching OwnerEpoch in both redundant Volume Descriptor
  copies.

The current automated Go tests use fake command output. No actual SAN device,
sanlock daemon, multipath topology, node power controller, or DM target is
operated by CI. Hardware qualification remains an operator-run acceptance
test and must be attached to the release record.
