# P3-3.12.3.9 — Owner Reservation establishment and verification

This phase closes the Owner-side SCSI Persistent Reservation lifecycle. The
Owner coordinator now requires an `fence.OwnerReservation` implementation;
there is no optional/no-op fallback in the takeover coordinator.

## Takeover ordering

While holding the exclusive sanlock Owner resource, the coordinator performs:

1. Load and validate the authoritative previous OwnerRecord.
2. If a previous Owner exists, issue PREEMPT AND ABORT and verify its target
   registration keys are absent on every configured path.
3. Wait for the old Owner's SAN-side metadata I/O drain barrier.
4. Read the durable BMDVOL02 OwnerEpoch and compute the next epoch.
5. Register the new Owner's path-scoped PR keys on all configured paths. This
   must precede PREEMPT because the new initiator's local key is the reservation
   key used to fence the previous Owner.
6. If a previous Owner exists, fence it on every path and drain its I/O.
7. CAS-publish the new OwnerRecord (node ID, boot ID and next epoch).
8. Issue SCSI PR OUT RESERVE through the first configured path using that
   path's local key and configured reservation type.
9. Read PRIN READ RESERVATION through every component path and require the
   same expected holder key and reservation type.
10. Only then return the monitored Owner lease. The existing runtime must still
   replay WAL, publish the durable BMDVOL02 OwnerEpoch and pass its admission
   gates before enabling DM requests.

The OwnerRecord is published after registration and old-owner fencing, but
before RESERVE. Path registration alone does not establish a reservation or
grant write access; if a process crashes before the OwnerRecord CAS, it may
leave an orphan registration, which is harmless to write exclusion but should
be cleaned up by the deployment's trusted key lifecycle. If RESERVE has an
ambiguous result or the process crashes after the target commits, the next
Owner can discover and fence this identity from the durable record. A failed
reservation attempt leaves that OwnerRecord in place; it is not rolled back to
an older identity.

## Concrete implementation

`fence.SCSIPROwnerReservation`:

- validates a non-empty set of unique component paths and nonzero, unique
  path-scoped LocalKeys;
- registers the local key on each path before old-owner fencing using
  `sg_persist --out --register` with APTPL enabled;
- issues `sg_persist --out --reserve` on the first path;
- always performs all-path PRIN READ RESERVATION after RESERVE, even when the
  command reports an error (the target may have committed before the response
  was lost);
- treats a complete matching observation on every path as success even if the
  RESERVE response was lost;
- fails closed on unreadable paths, absent/ambiguous reservation output,
  mismatched holder key, or mismatched type.

After an ambiguous RESERVE result the implementation intentionally does not
unregister the new keys. A reservation may have committed even when the
initiating command returned an error. Removing registrations could disturb an
active reservation. The durable OwnerRecord makes the identity recoverable by
the next takeover, which must fence it before proceeding.

## Reservation type support

The Owner verifier supports types 1, 3, 5 and 6, which expose a singular
reservation holder key in the output format being validated. Types 7 and 8
(All Registrants) are rejected because a single expected holder-key comparison
is not an adequate verification contract for those reservation types. Type 6
(Exclusive Access, Registrants Only) remains the default.

## Tests

The tests cover:

- successful registration on all paths before fencing, RESERVE and all-path verification;
- ambiguous RESERVE response after target-side commit;
- path read failure and fail-closed behavior without unsafe unregister;
- rejection of All Registrants types;
- parser rejection of absent, unsupported and ambiguous reservation states;
- OwnerRecord publication before reservation mutation;
- reservation failure prevents an Owner lease from being returned and retains
  the durable identity for the next takeover;
- missing reservation manager is rejected by the coordinator constructor.

The integration tests use in-process sanlock, Kubernetes API and reservation
simulators. They do not execute real sg_persist commands or SAN hardware.

## Production qualification boundary

The implementation is a concrete command adapter, not hardware qualification.
Before production RW use, validate the target's sg_persist output and PR
semantics on the actual array, HBA, multipath configuration and kernel. In
particular, confirm that the reservation holder key is consistently visible
through every component path and that APTPL behaves as expected after target
controller failover and power loss.

The Owner reservation being verified is necessary but not sufficient for RW
safety. Sanlock exclusivity, previous-owner PR fencing, old-owner I/O drain,
durable OwnerRecord CAS, WAL recovery, BMDVOL02 OwnerEpoch publication and
synchronous DM fail-stop/admission remain independent mandatory gates.
No hardware-level destructive test is run by CI.
