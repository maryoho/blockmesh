# P3-3.12.3.9 — Owner Reservation establishment and verification

This phase closes the Owner-side SCSI Persistent Reservation lifecycle. The
Owner coordinator requires a concrete `fence.OwnerReservation` implementation;
there is no optional/no-op fallback.

## Takeover ordering

While holding the exclusive sanlock Owner resource, the coordinator performs:

1. Load and validate the previous OwnerRecord from the shared SAN metadata
   device; reject reuse of the same node/boot identity.
2. Register the new Owner's path-scoped PR keys on all configured paths.
3. If a previous Owner exists, issue PREEMPT AND ABORT and verify its target
   registration keys are absent on every configured path.
4. Wait for the old Owner's SAN-side metadata I/O drain barrier.
5. Read the durable BMDVOL02 OwnerEpoch and compute the next epoch.
6. CAS-publish the new identity to the redundant SAN OwnerRecord slots.
7. Issue SCSI PR OUT RESERVE through the first configured path.
8. Read PRIN READ RESERVATION through every component path and require the
   expected holder key and reservation type.
9. Only then return the monitored Owner lease. WAL replay, BMDVOL02 OwnerEpoch
   publication and DM admission gates must still complete before data I/O.

The OwnerRecord is published after registration and old-owner fencing, but
before RESERVE. If RESERVE has an ambiguous result or the process crashes
after the target commits, the next Owner reads this SAN record and fences the
identity before proceeding. A failed reservation attempt leaves the new
OwnerRecord in place; it is not rolled back to an older identity.

## SAN OwnerRecord durability

OwnerRecord is stored in two dedicated, checksummed 4 KiB pages on the shared
Pool metadata device. The inactive copy is written and flushed before CAS
returns. The complete takeover sequence is serialized by the sanlock Owner
resource. The slot offsets must be reserved by Pool provisioning and must not
overlap any existing metadata extent. A process-local mutex is not a
cross-node synchronization primitive.

## Reservation type support

The Owner verifier supports types 1, 3, 5 and 6, which expose a singular
reservation holder key in the output format being validated. Types 7 and 8
(All Registrants) are rejected because a single expected holder-key comparison
is not an adequate verification contract. Type 6 remains the default.

## Tests

The tests cover path-scoped registration, PREEMPT ordering, all-path
reservation verification, ambiguous RESERVE response, path read failure,
rejection of All Registrants types, OwnerRecord publication before reservation
mutation, and failure to return an Owner lease without verified reservation.
The two-node takeover tests use one shared SAN metadata device and a sanlock
simulator; they do not use Kubernetes API simulators.

## Production qualification boundary

Validate sg_persist output and PR semantics on the actual array, HBA,
multipath configuration and kernel. Confirm reservation holder visibility
through every component path and APTPL behavior after target controller
failover and power loss.

The Owner reservation is necessary but not sufficient for RW safety. Sanlock
exclusivity, previous-owner fencing, old-owner I/O drain, durable SAN
OwnerRecord publication, WAL recovery, BMDVOL02 OwnerEpoch publication and
synchronous DM fail-stop/admission remain independent mandatory gates.
