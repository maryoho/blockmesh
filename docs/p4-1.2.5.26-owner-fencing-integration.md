# P4-1.2.5.26 — Owner Lease, SCSI PR Fencing and DM Admission

## Authoritative state

Each Volume has one authoritative SAN OwnerRecord containing VolumeID, NodeID, BootID and monotonically increasing OwnerEpoch. The BMDVOL03 Volume Descriptor carries the OwnerEpoch used by metadata and I/O admission. The shared SAN Owner sanlock resource serializes acquisition and release; a local mutex or heartbeat timeout is not a fencing mechanism.

## Takeover protocol

OwnerCoordinator.AcquireOwner executes the following sequence while holding the exclusive distributed Owner resource:

1. Load and validate the previous durable OwnerRecord.
2. Reject reuse of the same NodeID/BootID identity; the old process may still own local queues.
3. Register the new initiator's path-scoped SCSI PR keys on every configured component path.
4. PREEMPT AND ABORT the previous Owner's registrations through every component path and verify the previous key is absent everywhere.
5. Invoke the platform OwnerIOBarrier. This must prove the previous node's DM target and metadata I/O are quiescent; PR fencing alone is not an inflight-I/O drain proof.
6. Read the durable Volume Descriptor OwnerEpoch and calculate a strictly larger epoch.
7. CAS-publish the new OwnerRecord on the shared SAN metadata store.
8. Issue PR OUT RESERVE and verify the expected holder key and reservation type through every component path, including when the RESERVE command returned an ambiguous error.
9. Keep the exclusive Owner lease alive. The caller must recover all active AG WALs, publish the matching BMDVOL03 OwnerEpoch, and only then open DM RW admission.

NoopFencer is rejected by NewOwnerCoordinator. Missing, malformed, conflicting or unreadable OwnerRecord state fails closed. If fencing, drain, CAS, or reservation verification fails, the coordinator does not return an RW Owner lease.

## Release and reclamation

AcquireVolumeFencing obtains a Volume-scoped fencing lease for the exact VolumeID and OwnerEpoch. DynamicVolumeAllocator.ReleaseVolume requires a DynamicVolumeFencingProof and keeps the reservation pages allocated if proof acquisition or verification fails. The caller must hold this lease until the descriptor-pair clear and Reserved bitmap release transaction is durable, then close it.

## SCSI PR behavior

SCSIPROwnerReservation prepares path-scoped registrations before takeover and establishes a reservation only after preflight confirms the new key on every path. It verifies the reservation holder and type on every path after RESERVE. The parser intentionally supports reservation types with a singular verifiable holder (1, 3, 5 and 6); unsupported or ambiguous PRIN output is rejected.

## Production adapter contract

The core protocol is implemented and unit-tested, but each deployment must supply and qualify concrete adapters:

- Distributed sanlock resource mapping and helper lifetime.
- Durable SAN OwnerRecordStore with cross-node CAS semantics.
- Fencer configured with the exhaustive component paths and stable per-initiator keys.
- OwnerReservation using the array-supported SCSI PR type and sg_persist/toolchain.
- OwnerEpochReader bound to the authoritative BMDVOL03 descriptor.
- OwnerIOBarrier that drains or fences old-node DM and metadata queues.
- DM gate wiring that compares the request OwnerEpoch with the current durable epoch and rejects stale writers.

Do not reclaim a Volume because a heartbeat expired. Reclaim only after all-path fencing and the local I/O barrier succeed while the exclusive sanlock lease is held.

## Validation

OwnerCoordinator tests cover acquisition ordering, stale/missing OwnerRecord rejection, monotonic epoch publication, lease retention, all-path reservation verification, NoopFencer rejection, and fenced Volume release. DM owner-gate tests cover stale epoch admission rejection. Real array behavior remains part of P4-1.2.5.27 SAN qualification.
