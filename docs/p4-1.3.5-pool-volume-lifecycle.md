# P4-1.3.5 — Pool / Volume Lifecycle CLI and Runtime Control Plane

## Goal

The normal operator workflow must be:

```bash
bmctl pool create <name> <device>
bmctl pool list
bmctl pool info <name>

bmctl volume create <pool> <name> <size>
bmctl volume list
bmctl volume info <uuid>
bmctl volume activate <uuid> <rw|ro>
bmctl volume deactivate <uuid>
bmctl volume delete <uuid>
```

The operator must not need to run Bootstrap format, Data initialization, BMPOOL03 format/recovery, edit a per-volume daemon configuration, or restart bm-metad for ordinary lifecycle operations.

## Architecture decision

`bmctl` is a local control-plane client. It sends versioned requests to `bm-metad` over a Unix domain socket (default `/run/blockmesh/control.sock`). The daemon is the single lifecycle authority for pools and volumes on the node. The socket is root-owned and permission-restricted; requests are validated independently of CLI validation.

The daemon must not use a static `volumes[]` configuration as the source of truth. Pool and Volume descriptors persisted on the shared LUN are authoritative. A local registry may cache Pool device paths and host-specific integration settings, but it is rebuildable and must not replace on-device metadata.

## Command semantics

### Pool create

`pool create <name> <device>` performs a guarded, one-time initialization:

1. Resolve and canonicalize the block device; reject partitions/filesystems/signatures or an already formatted BlockMesh device unless an explicit future import/recovery flow is used.
2. Acquire the Pool bootstrap lock and fenced Owner authority.
3. Detect capacity and logical sector size; support multipath, direct iSCSI and local block devices.
4. Calculate Bootstrap, Metadata, initial Data and growth-reserve regions from actual device capacity. No fixed 16 GiB Metadata assumption and no operator-specified metadata size.
5. Initialize Bootstrap metadata, first DataView, BMPOOL03 geometry, dynamic volume allocator and Pool catalog.
6. Publish the final format only after all required metadata is durable. Every stage is restart/recovery safe; interrupted initialization is reported as recoverable, never silently reformatted.
7. Register the Pool with the local daemon and report its UUID and usable capacity.

Pool create is destructive to the selected device. It must display the resolved device, capacity and Pool name and require an explicit confirmation (or a documented non-interactive confirmation flag).

### Volume create

`volume create <pool> <name> <size>` allocates a durable Volume Descriptor and metadata Arena through the existing DynamicVolumeAllocator and cluster-safe WAL transaction. It does not create a DM device and does not activate the Volume.

Size suffixes: K=KiB, M=MiB, G=GiB, T=TiB. Parsing must reject overflow, zero, negative values, unsupported suffixes and sizes not representable by the current allocation geometry. The backend performs the exact capacity/AG feasibility check.

Volume names are unique within a Pool. The Volume UUID is generated by the daemon and persisted in the descriptor/catalog transaction. A failed or uncertain response is resolved by an idempotency token, not by blindly allocating a second descriptor.

### Volume activate

`volume activate <uuid> rw|ro` is node-local and idempotent for the same mode.

- RW: acquire exclusive Owner Lease, establish/verify SCSI PR reservation, fence and drain any previous Owner, recover WAL, publish the current OwnerEpoch, attach the DM target and expose `/dev/mapper/<stable-name>`.
- RO: acquire a shared Reader Lease/slot, register reader identity, validate the consistent online view, attach a read-only DM target and expose the same stable naming scheme.
- A conflicting local activation or incompatible mode change is rejected.
- The DM device is not exposed as ready until Runtime activation and kernel request-gate preparation both succeed.
- On partial failure, unwind in reverse order without releasing fencing authority before the DM gate is closed and pending BIOs are drained.

### Volume deactivate

Close DM request admission, drain/cancel/retry pending BIOs according to the existing cancellation handshake, remove the DM device, then release Reader/Owner state and device handles. If drain or DM removal fails, retain the safety locks and report the Volume as Deactivating/Failed; do not claim successful deactivation.

### Volume delete

Delete is allowed only when the Volume is inactive on this node and has no active Owner/Reader references cluster-wide. Retire mappings and metadata through the existing WAL/retire-generation protocol before releasing the descriptor/Arena reservation. A deleted UUID must not be reused.

### List / info / destroy

Pool and Volume list/info are read-only views over persisted metadata plus local runtime state. Pool destroy is allowed only when it contains no Volumes and no active references on any node; it is a separately confirmed destructive operation.

## Daemon responsibilities

- Discover and open configured Pools without static Volume entries.
- Load Pool geometry and Volume descriptors from the LUN.
- Provide a versioned Unix-socket API for Pool and Volume CRUD/activation.
- Keep a dynamic runtime registry keyed by Pool UUID and Volume UUID.
- Construct per-Volume OwnerRecord/epoch stores from descriptors rather than a preconfigured list.
- Dynamically resolve each Volume's Pool device, DM name, AG and descriptor index.
- Keep the Metadata Service request path available while Volume activation/deactivation occurs; runtime transitions must be serialized per Volume and bounded.
- Recover interrupted Pool format, WAL transactions and Volume lifecycle transitions before declaring readiness.
- Expose daemon health and per-object state for CLI info/list commands.
- On shutdown, stop new lifecycle requests, close DM admission, drain pending BIOs, release Runtime leases, and only then close the global Metadata Service device and process lock.

## Host configuration boundary

A one-time host configuration remains necessary for cluster-specific infrastructure: NodeID, sanlock lockspace/device and resource provisioning, SCSI PR paths/keys, old-owner drain helper, kernel module/device paths and daemon socket. These are node/platform settings, not per-Pool or per-Volume steps.

Pool/Volume commands must not ask operators to hand-author per-object JSON. The daemon derives logical sanlock resource names from Pool/Volume UUIDs. The platform lockspace provisioner must reserve the corresponding lock resources before use or provide an automatic safe provisioning adapter. Missing fencing or lock prerequisites fail closed; there is no local-lock or no-op-fencer fallback.

## Implementation sequence

1. **P4-1.3.5.1 CLI contract and parser** — expose the requested command tree, size parser, stable output and validation.
2. **P4-1.3.5.2 Pool catalog and auto-bootstrap** — persist Pool identity/device geometry and make `pool create` perform the entire safe initialization path.
3. **P4-1.3.5.3 Volume metadata lifecycle** — allocate/list/inspect/delete descriptors transactionally; support UUID/name lookup.
4. **P4-1.3.5.4 bm-metad control socket** — versioned, authenticated local RPC; dynamic Pool discovery and registry.
5. **P4-1.3.5.5 Dynamic Volume activation** — remove static `volumes[]` dependency and wire Owner/Reader/DM runtime by descriptor.
6. **P4-1.3.5.6 Deactivation and crash recovery** — complete reverse-order teardown and restart reconciliation.
7. **P4-1.3.5.7 End-to-end acceptance** — create Pool, create Volume, activate RW/RO, perform I/O, deactivate, restart daemon, re-activate, delete, and inject failures.

## Safety invariants

- No data I/O is admitted before Owner/Reader authorization, WAL recovery and DM gate preparation complete.
- RW ownership remains exclusive across nodes; RO access is shared and uses the existing online-consistent Reader protocol.
- A cancellation or daemon restart never turns an uncertain metadata commit into a duplicate allocation.
- The shared LUN remains the source of truth for Pool and Volume metadata.
- Device expansion is explicit, while the amount of Metadata growth is calculated automatically by BlockMesh.
- Multipath, direct iSCSI and local block devices use the same on-device format and lifecycle logic.
- A failed teardown must fail closed; never release fencing/leases while an old DM device can still submit I/O.
