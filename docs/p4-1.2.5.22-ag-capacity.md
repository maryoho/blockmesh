# P4-1.2.5.22 — AG Capacity Reservation and Dynamic AG Growth

## Geometry

BMPOOL03 now separates:
- `AGCount`: active AG count derived from DataView capacity.
- `AGCapacity`: stable number of reserved AG metadata slots.

A zero `AGCapacity` in a planner request preserves the legacy behavior and defaults to the initial AG count. The value is persisted in the formerly reserved Superblock bytes 224..227. Older BMPOOL03 v3 records with this field zero decode as `AGCapacity == AGCount`.

WAL, Bitmap and Checkpoint region sizes are calculated from AGCapacity, not AGCount. This keeps their offsets stable while new AGs are activated. Checkpoint descriptors are initialized for every reserved slot; inactive Bitmap slots are initialized fully allocated.

## Growth protocol

1. Build the next geometry from the larger DataView while preserving the current AGCapacity and all metadata offsets.
2. Reject growth that requires more AGs than AGCapacity.
3. WAL-commit the newly valid tail bits of the previous final AG.
4. Zero each new AG WAL segment and initialize its Bitmap descriptor, Bitmap and dual Checkpoint descriptors.
5. Sync all new AG metadata.
6. Publish the higher-generation Superblock to the inactive copy and Sync.
7. Mirror the new Superblock to the other copy and Sync.

The newly initialized AGs remain unreachable until the Superblock publishes the larger AGCount. A crash before publication leaves harmless initialized reserved slots; a crash after the first Superblock copy is recoverable by selecting the highest valid generation.

## Safety

- Existing WAL/Bitmap/Mapping/Checkpoint offsets do not move.
- Existing AG slots are not reinitialized.
- A DataView generation mismatch is rejected by the existing view-generation checks.
- Growth beyond AGCapacity is rejected before publication and requires a future offline layout migration or a larger reservation at initial format.
- BMPOOL02 is unchanged.

## Validation

Tests cover geometry reservation, Superblock encode/decode, stable region offsets, activation of a previously reserved AG, Bitmap tail-bit release, new AG initialization, and rejection beyond AGCapacity.
