# P4-1.1 — Thin Provisioning data-path architecture and protocol

## Architecture decision

**Decision: DM Target in kernel + Go metadata service.**

The current `dm-blockmesh` target is a Linear remapper with OwnerEpoch write
admission. It does not perform Mapping lookup, zero reads for unallocated
logical blocks, thin allocation, or thin discard. The existing 4MiB allocator
and metadata transaction code are foundations, not a connected BIO data path.

The Go metadata engine in `internal/metadata/engine.go` currently contains a
JSON state-file/WAL demonstration implementation. It must not be treated as
the production SAN-backed metadata authority. The production path must use the
fixed-LBA Pool Volume Store, COW metadata pages, Volume Descriptor publication,
and SAN-backed WAL/allocator transaction path.

## Data-path responsibilities

### Kernel DM Target

- Keep OwnerEpoch admission, fencing, inflight accounting and drain semantics.
- Translate BIO sector ranges into 4MiB logical-block ranges (8192 sectors per
  block for 512-byte sectors); split requests at block boundaries.
- Maintain a bounded, generation-tagged Mapping Cache.
- Complete reads from unmapped blocks with zeroes; never read stale physical
  media for an unmapped LBA.
- On a Mapping Cache miss, defer the BIO and submit a bounded metadata request.
- Serialize first-write allocation per logical 4MiB block; concurrent writers
  join the same pending allocation rather than allocate duplicate blocks.
- Complete the original BIO only after mapping publication is durable and the
  request can be safely remapped.
- Reject mutating BIOs unless the exact current OwnerEpoch gate is open.
- Treat metadata service loss, protocol mismatch, stale epoch, queue exhaustion
  and timeout as fail-closed conditions. Never fall back to linear mapping.

### Go metadata service

- Be the sole authority for Mapping, Bitmap, Volume Descriptor and WAL state.
- Validate VolumeID, NodeID, BootID, OwnerEpoch/ReaderEpoch and generation on
  every request.
- Batch Mapping lookups and return explicit mapped/unmapped runs.
- Perform allocation under the existing AG/Mapping/Volume Descriptor lock
  hierarchy and durable WAL transaction semantics.
- Provide idempotent mutation handling keyed by the request's 128-bit
  idempotency key. A retry must return the original outcome, not allocate
  another physical block.
- Retain discard blocks in the Retire Queue until Reader Generation advance,
  fencing and metadata I/O drain make reclaim safe.

## Transport decision

Do not issue synchronous Generic Netlink RPC per BIO. Generic Netlink remains
appropriate for control operations, health, events and configuration, but not
for high-frequency miss/allocate traffic.

P4-1.1 chooses a per-target kernel request queue with a character-device
userspace endpoint and bounded shared-memory request/response rings. The
service drains requests in batches and returns completions by request ID.
The final Linux 5.15 UAPI will use fixed-width little-endian fields, explicit
ABI version/size, reserved-zero fields, bounded ring sizes and ioctl/mmap
setup. The Go types in `internal/ioproto` are the transport-independent
semantic contract, not the byte-level UAPI.

A request queue is not an unbounded wait queue. Each target has configured
limits for outstanding requests and pinned BIO bytes. Queue saturation applies
backpressure; cancellation, target removal and service restart must complete
or fail every outstanding request exactly once. A service restart invalidates
the target's cache generation until a fresh handshake and metadata generation
are established.

## Protocol v1 semantic contract

Every request includes:

- protocol version and non-zero request ID;
- operation and VolumeID / NodeID / BootID;
- OwnerEpoch for mutations and RW lookups, or ReaderEpoch + RootGeneration
  for RO lookup;
- logical block start and count (4MiB units);
- 128-bit idempotency key for mutations.

Operations:

| Operation | Purpose | Required semantics |
|---|---|---|
| LOOKUP_BATCH | Resolve up to 256 logical blocks | Return mapped runs and explicit unmapped ranges at a single RootGeneration |
| ALLOCATE_ZERO_PUBLISH | First-write allocation | Idempotent; zero full 4MiB physical block and flush before durable Mapping publication |
| DISCARD | Remove logical mappings | COW/WAL publication; physical blocks enter Retire Queue, not immediate reuse |
| FLUSH | Order prior mutations and data writes | Metadata commit and data-device flush boundaries must be explicit |

Responses carry request ID, status, OwnerEpoch, RootGeneration and zero or more
mapping runs. Non-success responses must not carry mappings. A stale epoch is
not retryable under the old identity; the caller must be fenced and reactivated
through the Owner recovery state machine.

## First-write ordering and crash semantics

For an unmapped logical block, the first write is not allowed to publish a
Mapping before the complete physical block has been initialized to zero.
Otherwise a 4KiB partial write could expose stale bytes from a recycled 4MiB
physical block.

The required transaction sequence is:

1. Validate Owner lease, exact OwnerEpoch and target admission.
2. Reserve a physical block with a durable, recoverable allocation intent.
3. Zero the entire 4MiB physical block; issue and verify the required data
   device flush/FUA ordering.
4. Atomically publish Bitmap allocation + Mapping + Volume Descriptor root
   using the SAN metadata WAL transaction.
5. Invalidate/update Mapping Cache generation and release queued BIOs.
6. Apply the caller's write; complete it only after the underlying BIO ends.

A crash before step 4 must leave an identifiable reservation that recovery can
safely roll back or resume after fencing. A crash after step 4 must recover the
published mapping and the zero-initialized block. The current
`AllocateOneTxn` publishes Bitmap + Mapping + Volume Descriptor together,
but does not yet implement the preceding durable reserve/zero/publish protocol;
P4 must add that protocol before enabling first-write allocation.

## Read and write semantics

- An unmapped read returns zeroes without touching the data LUN.
- A mapped read translates the logical offset within the 4MiB block to the
  physical block and preserves the byte/sector offset.
- A write spanning multiple 4MiB blocks is split and each unmapped block is
  allocated independently or through a batch allocation transaction.
- Partial writes to a new block are safe because the full physical block was
  zeroed before Mapping publication.
- Flush/FUA ordering must preserve Linux block-layer semantics; completion of
  a metadata RPC alone does not imply data BIO durability.

## Discard and reclaim

Discard first removes the logical Mapping through COW/WAL and adds each
physical block to the Retire Queue with its RootGeneration. It does not clear
the Bitmap bit immediately. Reclaim requires all active readers to advance
past the retire generation, stale readers to be SAN-fenced, and old metadata
I/O to be drained. The existing Reader Generation and fencing design remains
authoritative.

## P4 implementation sequence

1. **P4-1.1** Architecture decision and protocol contract (this change).
2. **P4-1.2** Fixed-width kernel/userspace UAPI, queue lifecycle, request
   correlation, cancellation and service restart fencing.
3. **P4-1.3** Production SAN-backed Mapping lookup API and batch cache fill.
4. **P4-1.4** Kernel Mapping Cache, generation invalidation and unmapped reads.
5. **P4-1.5** Durable reserve/zero/publish allocation transaction and
   concurrent first-write coalescing.
6. **P4-1.6** BIO splitting, write/flush/FUA ordering and error propagation.
7. **P4-1.7** Discard, Retire Queue and safe physical reclaim.
8. **P4-1.8** Crash/fault qualification, race tests and performance benchmarks.

No Thin data path is enabled by this architecture document. The current DM
target remains linear until P4-1.2 through P4-1.6 are implemented and qualified.
