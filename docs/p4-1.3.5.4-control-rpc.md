# P4-1.3.5.4 — Lifecycle Unix RPC transport

## Status

The reusable Linux Unix-domain RPC transport and typed lifecycle action router are implemented in `internal/control`. They provide protocol v1 request/response envelopes compatible with `cmd/bmctl/lifecycle.go`, strict per-action argument validation, and a `LifecycleBackend` contract for the privileged storage implementation:

- request: `version`, `id`, `action`, `args`;
- response: `version`, `id`, `ok`, `error`, `result`.

## Transport guarantees

- Unix socket mode defaults to 0660; parent directory is created as 0750.
- Refuses to replace an existing non-socket path or a socket that accepts connections.
- Stale socket cleanup is limited to socket filesystem objects.
- Bounded request size (default 1 MiB, maximum 16 MiB), concurrent connections and request duration.
- Strict JSON decoding rejects unknown envelope fields, invalid action names, unsupported protocol versions, malformed IDs, and non-object arguments.
- Every response echoes the request ID and protocol version.
- Handler calls receive a bounded context; transport shutdown closes active connections.
- Transport is deliberately storage-agnostic. It cannot claim Pool/Volume lifecycle success until a production handler is wired to the SAN-fenced Pool registry and dynamic Volume runtime.

## Current integration gap

The transport and action router are tested, but they are not yet wired into `bm-metad`. The current daemon still has a static `volumes[]` configuration and activates those configured entries at startup. The next integration change must replace that static list with a device/Pool discovery registry and provide real handlers for Pool create/list/info/destroy and Volume create/list/info/delete/activate/deactivate.

No no-op Owner, PR fencing, old-owner drain, Reader-set guard or WAL committer may be used to make the commands appear functional. Pool creation must only report success after BMPOOL03 formatting, the Reserved allocator and persisted Pool Catalog are durable.
