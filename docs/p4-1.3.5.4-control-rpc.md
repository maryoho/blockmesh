# P4-1.3.5.4 — dynamic Volume catalog discovery

`bm-metad` now reads Volume Descriptor pairs from each discovered BMPOOL03 Pool's MetadataView. The path is read-only: parent LUN -> Bootstrap -> MetadataView/DataView -> dynamic Superblock -> Reserved allocator -> descriptor table. Every identity is checked against the Pool Catalog and Superblock, and duplicate Volume UUIDs across configured LUNs fail closed. `volume list` and `volume info` now query persisted descriptors without static `volumes[]` entries.

This does not yet activate Volumes or perform mutations. The discovery backend intentionally opens the LUN read-only. Pool/Volume create, delete, activation and deactivation remain disabled until distributed resource allocation, a production Pool Owner provider, Data Retire integration, and dynamic runtime/DM management are connected.

## Dynamic sanlock resource allocation

BlockMesh now uses sanlock's native Resource Index (RINDEX) for dynamic resource names. The RINDEX atomically allocates and persists resource-name-to-offset mappings under sanlock's internal Paxos lease; it avoids per-Volume offset entries and hash-slot collisions. Configure `sanlock.resource_index_offset` to the preformatted shared RINDEX on the sanlock lock device, and `sanlock.resource_alignment_bytes` to the exact alignment used when formatting the lockspace/RINDEX (1, 2, 4 or 8 MiB). The RINDEX must be formatted once by the administrator with matching sector/alignment flags before bm-metad starts; bm-metad never formats or rebuilds it automatically. If the index is missing, corrupt or unavailable, resource acquisition fails closed.

Example (illustrative; use the actual preformatted RINDEX offset and alignment):

```json
{
  "sanlock": {
    "resource_index_offset": 8388608,
    "resource_alignment_bytes": 1048576
  },
  "discovery_devices": ["/dev/mapper/mpatha"]
}
```
