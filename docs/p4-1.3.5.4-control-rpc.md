# P4-1.3.5.4 — dynamic Volume catalog discovery

`bm-metad` now reads Volume Descriptor pairs from each discovered BMPOOL03 Pool's MetadataView. The path is read-only: parent LUN -> Bootstrap -> MetadataView/DataView -> dynamic Superblock -> Reserved allocator -> descriptor table. Every identity is checked against the Pool Catalog and Superblock, and duplicate Volume UUIDs across configured LUNs fail closed. `volume list` and `volume info` now query persisted descriptors without static `volumes[]` entries.

This does not yet activate Volumes or perform mutations. The discovery backend intentionally opens the LUN read-only. Pool/Volume create, delete, activation and deactivation remain disabled until distributed resource allocation, a production Pool Owner provider, Data Retire integration, and dynamic runtime/DM management are connected.

## Dynamic sanlock resource offsets

To remove per-Volume resource-offset entries, configure a dedicated sanlock lockspace range on the shared lock device using `sanlock.dynamic_resource_base` and `sanlock.dynamic_resource_slots`. The base is a byte offset aligned to 512 bytes; each slot occupies 512 bytes. All cluster nodes must use identical values. Existing explicit `resource_offsets` remain supported for fixed resources, but must not overlap the dynamic range. The resolver hashes the complete resource name deterministically and rejects collisions observed by the daemon. The administrator must reserve this range exclusively for BlockMesh resource records and ensure it fits the lockspace device; it must not overlap lockspace metadata or other applications' resources.

Example daemon configuration (offsets are illustrative; the range must be reserved in your sanlock lockspace device):

```json
{
  "sanlock": {
    "dynamic_resource_base": 1048576,
    "dynamic_resource_slots": 1048576
  },
  "discovery_devices": ["/dev/mapper/mpatha"]
}
```
