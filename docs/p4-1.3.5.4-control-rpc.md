# P4-1.3.5.4 — bm-metad control socket and Pool catalog discovery

## Implemented in this increment

- bm-metad starts the versioned Unix-domain lifecycle RPC server alongside the metadata service.
- The default socket is /run/blockmesh/control.sock; control.socket_path can override it.
- discovery_devices is a list of candidate shared block-device paths. The daemon opens each candidate read-only and reads the persisted BMPOOL03 Pool Catalog from that same LUN.
- pool list and pool info are backed by the persisted catalog, sorted deterministically, and reject duplicate Pool names across candidate devices.
- The daemon no longer requires a static volumes[] list merely to start in catalog-discovery mode.
- Mutating Pool/Volume operations and Volume operations deliberately return an explicit not-available-yet error. No fake success, local-lock fallback, or no-op fencing is introduced.

## Configuration

Add control.socket_path and discovery_devices to /etc/blockmesh/metad.json. Example socket path: /run/blockmesh/control.sock. Candidate devices must be stable local paths for Pool LUNs visible to this node.

## Remaining integration

Pool create still needs a production Pool-level Owner/PR bootstrap provider and collision-safe distributed sanlock resource allocation. Volume operations need dynamic descriptor discovery, concrete Data Retire, and dynamic activation/deactivation runtime management. Until those pieces are complete, only Pool list/info are enabled through this RPC server.
