# P3-3.12.3.18 — Runtime Event Export integrated into Owner Recovery Acceptance

## Scope

The P3.15 acceptance path now requires the P3.17 runtime JSONL journal and
automatically verifies and exports it while generating the Owner Recovery
Acceptance Report. A standalone event export is no longer a manual side step.

The report command performs these checks in one invocation:

1. Verify JSONL sequence, previous-hash links and SHA-256 record hashes;
   reject partial tails, malformed records and corruption.
2. Validate required event presence, uniqueness, success, ordering and Epoch.
3. Match event VolumeID, NodeID, BootID and OwnerEpoch against both the P3.15
   runtime evidence JSON and durable post-recovery SAN metadata snapshot.
4. Exclusively create the verified JSON export, calculate SHA-256 for both
   journal and export, and add both as mandatory report artifacts.
5. Run the P3.15 raw SAN/DM/WAL/data evidence verifier and render the runtime
   event timeline in the same Markdown report.

Missing journal/export arguments, invalid event chain, identity/Epoch mismatch,
duplicate output path, missing raw artifact, or P3.15 failure returns nonzero.
The acceptance script prints PASS only after the integrated report succeeds.

## Acceptance command

The script takes 13 arguments. The JSON export is created at REPORT.md.runtime-events.json:

```bash
scripts/owner-recovery-acceptance.sh \
  ./bm-owner-crash-qualify ./bm-san-qualify ./bm-owner-recovery-report \
  evidence/node-a-before evidence/node-b-after \
  0xOLD_OWNER_KEY 0xNEW_OWNER_KEY 6 node-b NEW_BOOT_ID \
  evidence/runtime-evidence.json \
  evidence/runtime-owner-recovery.jsonl \
  evidence/owner-recovery-report.md
```

The JSONL journal remains the primary raw event evidence; the generated JSON
export is derived. Both are SHA-256 checked and listed in the report. Use a
fresh journal operation ID, journal path, report path and export path per run.

## Report contents and proof boundary

The report retains all P3.15 checks and adds a P3.17 timeline table containing
sequence, UTC time, event type, phase and proof boundary. Runtime events do not
replace independent sanlock status, per-component-path PR readback, old-owner
write exclusion, old-DM queue/inflight evidence, durable descriptor readback,
or application data-integrity artifacts.

## Compatibility and qualification boundary

The P3.15 report command now requires both runtime event flags so the current
acceptance binary cannot silently omit event validation. Update lab automation
to pass the journal path. CI validates Go logic only; it does not execute real
dual-node SAN, sanlock, SCSI PR, multipath, Linux DM, power-loss, HBA or array
failover tests. A software event timeline PASS is not a real SAN acceptance PASS.
