# P4-1.3.5.2 — Pool Catalog 与自动初始化

## 目标

Pool 的身份和容量布局以同一块 LUN 上的 BMPOOL03 Bootstrap 元数据为权威来源。bm-metad 重启后可以重新打开设备并重建内存中的 Pool 注册表，不依赖本地 JSON 文件保存 Pool 的真实状态。

## Pool Catalog

Bootstrap 双副本记录中原有的保留字节用于保存 Pool 名称：

- Pool 名称限制为 1–23 个 ASCII 字符：字母、数字、.、-、_。
- Pool UUID、名称、设备容量、Metadata 容量、Extent Map generation 和逻辑扇区大小均由 Bootstrap CRC32C 保护。
- 旧版未命名 Bootstrap 记录仍可读取，但不会被误报为具备名称的 Catalog 条目。
- poolspace.ReadPoolCatalog 对候选 LUN 只读发现 Pool；未知格式和 BMPOOL02 不会被当作空白设备。

Pool Catalog 条目不是额外的本地数据库。它从 LUN 上的 Bootstrap 记录和 Extent Map 派生，因此本地缓存丢失不会丢失 Pool 身份。

## 自动初始化流程

poolinit.Initialize 在调用方已经取得排他 Owner Lease、SCSI PR fencing 和跨节点初始化锁之后执行：

1. 根据真实设备容量调用 PlanDevice，自动计算 Metadata 区和初始 Data 容量。
2. 对空白 LUN 创建带名称的 BMPOOL03 Bootstrap Catalog；对已初始化的同名 Pool 执行幂等恢复；名称不一致时拒绝接管。
3. 通过 Bootstrap WAL 发布初始 Data Extent Map。MetadataView 与 DataView 仍映射到同一个父 LUN。
4. 根据 MetadataView/DataView 实际容量规划 BMPOOL03 动态几何。
5. 初始化 AG Bitmap、AG Descriptor、Checkpoint 和双 Superblock。
6. 初始化 Reserved Metadata 分配器，为后续 Volume Descriptor、OwnerRecord 和 Reader Table 分配元数据空间。
7. 返回 Pool UUID、容量、generation 和 AG 布局，供控制面注册。

poolinit.Initialize 不接受用户指定 Metadata 容量；PlanDevice 从当前设备容量和 Volume slot 规划参数计算布局。设备扩容后的元数据扩展仍由显式扩容操作触发，扩展量由后端根据用量与增长预测计算。

## 初始化中断恢复

- Bootstrap 首次格式化先写入位于 Bootstrap 保留区末页的持久化 format intent，再发布 Extent Map 和 Bootstrap 主记录，最后清除 intent。
- OpenBootstrap 遇到未清除的 intent 会 fail closed，不把半成品作为 Ready Pool 返回。
- 在排他 Owner Lease 下再次执行同名 poolinit.Initialize 会校验 intent 中的 Pool 名称和设备几何，并继续完成初始化。
- Data Extent Map 使用已有 Bootstrap WAL；BMPOOL03 Superblock 格式化使用独立格式标记；Reserved allocator 也有自己的格式标记。各阶段均按已提交状态识别重试。
- 非空未知设备、BMPOOL02、Pool 名称不匹配、几何不匹配和损坏的 intent 均拒绝格式化。

## 当前边界

本阶段提供持久化 Catalog、只读发现 API 和可重试的 Pool 初始化服务。bmctl pool create/list/info 与 bm-metad RPC Server 的连接属于后续 P4-1.3.5.4；在 RPC Server 完成前，不能把 CLI 的生命周期命令视为可执行的生产操作。真实 SAN 双节点 PR fencing、multipath 故障和掉电恢复仍需在目标环境验收。
