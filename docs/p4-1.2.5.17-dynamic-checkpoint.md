# P4-1.2.5.17 — Dynamic Checkpoint Descriptor and Recovery

BMPOOL03 reserves two 4KiB checkpoint descriptor copies for every active AG. The geometry planner verifies that CheckpointSize can hold AGCount * 2 * PageSize bytes. Each descriptor stores AG index, monotonic generation, checkpointed transaction ID and active WAL bank, protected by CRC32C.

Each per-AG WAL segment is split into two page-aligned banks. On open, the journal validates both descriptors, selects the highest generation, rejects equal-generation conflicts, repairs a stale/corrupt mirror, and replays only the selected bank after the descriptor's checkpoint transaction ID.

Checkpoint ordering:

1. Clear the inactive WAL bank in bounded 1MiB writes and Sync.
2. Write the next-generation descriptor to the inactive descriptor slot and Sync.
3. Mirror that descriptor to the other slot and Sync.
4. Switch the in-memory writer to the new empty bank.

This ordering leaves the previous bank authoritative until the new descriptor is durable. If the first descriptor copy is durable but the mirror is not, reopen selects the higher generation and repairs the mirror. A failed or uncertain checkpoint requires reopening the journal before further writes.

DynamicJournal.Checkpoint only reclaims records after committed after-images have already been applied and synced by Commit. The descriptors do not replace the Pool Owner lease, per-AG distributed lock, or SAN fencing requirements.
