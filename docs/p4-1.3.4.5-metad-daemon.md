# P4-1.3.4.5 — Metadata Service Production Daemon

## Scope

This stage adds the Linux daemon entry point `cmd/bm-metad`, strict JSON configuration, production dependency wiring, and a systemd unit. Startup order is:

1. Parse and validate the complete configuration.
2. Construct the shared sanlock locker, SCSI PR fencing/reservation adapters and durable OwnerRecord repository.
3. Construct BMPOOL03 Backend, distributed Reader coordinator, DM RequestGate and DynamicVolumeRuntimeManager.
4. Activate every configured Volume. RW activation acquires the P3 Owner lease, fences the previous Owner on all configured SAN paths, waits for the configured old-owner I/O drain helper, recovers AG WAL, publishes OwnerEpoch and prepares the DM gate.
5. Construct and start `metaservice.Service`. The service lock is acquired, `/dev/blockmesh` is opened, queues are reconciled and startup recovery completes before ServiceReady.

Shutdown order is the reverse safety order: stop DM admission and drain BIOs through DynamicVolumeRuntimeManager, close Reader/Owner sessions and Runtime views, then close `/dev/blockmesh` and release the process singleton lock.

## Build and install

```bash
go build -o bin/bm-metad ./cmd/bm-metad
install -D -m 0755 bin/bm-metad /usr/sbin/bm-metad
install -D -m 0644 deploy/systemd/bm-metad.service /etc/systemd/system/bm-metad.service
install -d -m 0750 /etc/blockmesh
install -m 0600 deploy/bm-metad.example.json /etc/blockmesh/metad.json
systemctl daemon-reload
```

## Configuration

See `deploy/bm-metad.example.json`. Unknown JSON fields are rejected. The daemon intentionally has no local-lock, NoopFencer, or synthetic OwnerLease fallback.

Important fields:

- `node_id`: stable node identity. `boot_id`: unique Owner-process incarnation ID, not simply `/proc/sys/kernel/random/boot_id`. Generate a fresh value before every daemon start/restart, including a restart within the same OS boot. The P3 OwnerCoordinator deliberately rejects reuse of the same NodeID/BootID after a prior OwnerRecord was published.
- `service.device_path`: normally `/dev/blockmesh`.
- `service.lock_path`: local singleton lock file.
- `sanlock.resource_offsets`: explicit mapping from logical resource name to a pre-provisioned, unique, 512-byte-aligned lockspace offset. Required names include `owner/<volume-id>`, `reader-set/<volume-id>`, `reader/<volume-id>/<slot>`, and `wal/<pool-uuid-hex>/<ag-index>` for every AG used by the Pool.
- `san.paths`: every local component path of the shared LUN/multipath device, with a unique local PR key per path. These local keys must be fresh for each Owner-process incarnation; the platform config generator must rotate them together with `boot_id`. Do not list only the multipath mapper when the PR implementation must verify each component path.
- `san.owner_keys`: previous NodeID/BootID to all registration keys for that initiator. Preserve the previous incarnation's keys here when generating the new config. The mapping must be provisioned by the cluster control plane; missing keys cause takeover to fail closed.
- `san.owner_drain_helper`: mandatory trusted platform helper. It receives `--volume-id`, `--node-id`, `--boot-id`, and `--owner-epoch`. It must not return until the old node's metadata I/O is drained. PR PREEMPT AND ABORT is not treated as a substitute for this barrier.
- `volumes`: explicit Volume to LUN/DM mapping and RW/RO activation mode.

The sanlock resource offsets must refer to resources already provisioned in the configured lockspace. This daemon does not initialize or resize the sanlock lockspace.

## Start and inspect

```bash
systemctl enable --now bm-metad
systemctl status bm-metad
journalctl -u bm-metad -f
```

A successful process start is not by itself proof of data-path readiness. Check logs for each Volume activation and then inspect the kernel target status. The DM target must be enabled only by the integrated Runtime manager; never send `owner_enable` manually.

## Important limitations

- The current daemon configuration is intentionally explicit and uses a single local NodeID/BootID with one or more configured Volumes.
- The daemon does not discover multipath component paths or generate SCSI PR keys. The deployment/control plane must provide them.
- The old-owner drain helper is an external trust boundary and must be implemented by the platform. A no-op helper is unsafe.
- The resource offset map must include every AG WAL resource. Missing entries stop activation before request admission.
- This stage does not claim SAN hardware qualification, vendor Linux 5.15 ABI qualification, or fio end-to-end acceptance. Those remain separate tests.
- Configuration reload and online Volume add/remove are not implemented; restart the daemon after changing configuration.


## Owner identity rotation requirement

The daemon does not generate SCSI PR keys or persist its own process-incarnation identity. Before every daemon start, the platform must atomically render a fresh `boot_id`, fresh `san.paths[].local_key` values, and retain the previous Owner's keys in `san.owner_keys`. Reusing the same NodeID/BootID is rejected by the OwnerCoordinator; reusing the previous PR keys can make the old and new initiator identities indistinguishable and is rejected by the fencer. The sample systemd unit therefore does not automatically restart the daemon. Enable automatic restart only after an `ExecStartPre`/orchestrator identity-and-key rotation hook is installed and tested.
