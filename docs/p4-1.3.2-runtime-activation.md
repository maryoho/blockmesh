# P4-1.3.2 — BMPOOL03 Runtime Activation and Mutation Executor

## Scope

This stage adds a BMPOOL03-native runtime path. It must not route BMPOOL03 through the legacy BMPOOL02 `VolumeRuntimeManager`, `PoolVolumeRuntimeBackend`, `PoolDescriptor`, or fixed-LBA WAL decoder.

The existing `PoolRuntimeProcessor` is a request processor, not yet a complete BMPOOL03 production runtime: it is constructed with the BMPOOL02-oriented `metastore.VolumeRuntimeManager`; its mutation interface is intentionally fail-closed when no executor is supplied. Keep that behavior until the dynamic runtime is wired end to end.

## Required runtime objects

A BMPOOL03 activation owns the following generation-consistent objects:

- Parent LUN device and the Bootstrap extent map.
- MetadataView and DataView opened from the same Bootstrap generation.
- Validated pair of BMPOOL03 DynamicSuperblocks.
- BMDVOL03 Dynamic Volume Descriptor pair and its durable OwnerEpoch.
- Dynamic WAL journal recovery for every AG referenced by the Volume.
- Cluster-safe DynamicSharedCommitter instances and distributed AG locks.
- Persistent Arena and COW B+Tree opened at the descriptor's published root.
- DynamicPoolAllocator bound to the same MetadataView, DataView, Owner lease and distributed locker.
- DM OwnerEpoch gate, queue admission hook, fail-stop hook and metadata-I/O drain hook.

A generation mismatch between Bootstrap Extent Map, MetadataView, DataView and DynamicSuperblock must reject activation.

## Activation protocol

### RW activation

1. Validate the Volume ID, Node ID, Boot ID, requested RW mode and configured parent-LUN identity.
2. Open the parent block device read/write and resolve the Bootstrap Extent Map.
3. Open MetadataView and DataView using exactly the same extent-map generation.
4. Read both BMPOOL03 Superblock copies; reject incomplete format markers, conflicting equal-generation copies and invalid geometry.
5. Acquire the exclusive distributed Owner lease. Acquisition must complete old-owner all-path SCSI PR fencing and the platform I/O barrier before returning.
6. Re-read the authoritative BMDVOL03 descriptor and verify its Volume ID and OwnerEpoch against the Owner lease identity.
7. Recover every active AG Dynamic WAL before opening mutable metadata structures. Any ambiguous WAL outcome fails activation and leaves DM admission closed.
8. Open the Dynamic Pool Volume Store, cluster-safe committer, Persistent Arena and B+Tree from the descriptor's published root.
9. Construct the DynamicPoolAllocator with the DataView and distributed AG locker. Reject local/test lockers, MemoryLease, NoopFencer and missing data-zeroing durability.
10. Publish the newly acquired OwnerEpoch to the BMDVOL03 descriptor using the dynamic descriptor transaction and its WAL guard.
11. Enable the kernel DM OwnerEpoch gate and queue admission only through a final synchronous Owner-lease guard under the DM admission lock.
12. Start lease-loss monitoring. Lease loss must synchronously fail-stop DM admission, drain in-flight data and metadata I/O, and retain resources until cleanup is safe.

### RO activation

1. Perform steps 1–5 with RO identity and a shared/reader lease rather than an RW Owner lease.
2. Recover no mutable state and never publish an OwnerEpoch.
3. Join the durable Reader Generation table and pin a consistent B+Tree root/generation.
4. Open the read-only Dynamic Pool Store and mapping view at that pinned root.
5. Admit only requests carrying the matching ReaderEpoch and RootGeneration.
6. Reclaim a failed reader only after its lease is proven dead and SAN fencing succeeds.

RO must not silently fall back to RW and RW must not silently degrade to RO.

## Dynamic mutation executor

Implement a BMPOOL03-specific `PoolMutationExecutor` backed by `allocator.NewDynamicPoolAllocator` and the live runtime context.

### AllocateZeroPublish

- Require RW runtime, matching Volume ID, Node ID, Boot ID and current OwnerEpoch.
- Validate a non-zero idempotency key and a canonical request fingerprint covering Volume, operation, logical range, byte range and semantic flags.
- Serialize against the relevant AG using the distributed locker.
- Re-read BMDVOL03 and OwnerEpoch after acquiring the AG lock.
- Zero every newly exposed 4 MiB physical allocation unit through DataView and durably flush the DataView before any mapping becomes visible.
- Commit Bitmap, B+Tree Mapping, idempotency index/record and BMDVOL03 root/sequence after-images through one Dynamic WAL transaction.
- Return the same mapping for an identical retry; reject key reuse with a different fingerprint.
- On ambiguous WAL outcome, fence/stop the Volume, recover WAL and reopen the B+Tree before accepting another mutation.

### Existing logical mappings / overwrite

The current one-time allocator rejects an already-mapped logical range. Do not call it directly for ordinary repeated writes. P4-1.3.2 must provide a COW update operation that allocates and zeroes replacement extents, atomically publishes the new mapping/root and retires the previous physical extents. Old extents must not be reused until Reader Generation, fencing and metadata-I/O drain proofs permit reclamation.

### Discard

Discard removes the logical mapping durably and enqueues the old physical extents for retirement. It must not immediately clear allocation bits or issue physical discard. Reclamation is a separate fenced operation gated by all active readers and their generations.

### Flush

A successful FLUSH completion is permitted only after the DataView and Dynamic WAL/metadata device durability barriers required by the request have completed. The ordering contract must be explicit for the same-LUN layout.

## Implementation units and tests

1. `DynamicRuntimeBackend`: BMPOOL03-specific device/view/superblock/descriptor/WAL/Owner wiring. Tests reject BMPOOL02, stale extent-map generations, invalid descriptors, incomplete formatting, missing Owner proof and non-distributed locks.
2. `DynamicVolumeRuntimeManager`: serialized Activate/Deactivate/Shutdown lifecycle with rollback and retryable cleanup. Tests inject failure after every activation step and assert admission remains closed.
3. `DynamicPoolMutationExecutor`: allocate/overwrite/discard/flush operations. Tests cover idempotent replay, conflicting key reuse, stale OwnerEpoch, Owner lease loss while waiting for AG lock, zero-before-publish, ambiguous WAL recovery, COW retirement and no early physical reuse.
4. Request admission: bind the dynamic runtime snapshot to NodeID/BootID, OwnerEpoch or ReaderEpoch, and root generation. Test cross-volume, stale identity and generation rejection.
5. End-to-end CPU tests: format a small BMPOOL03 image, activate RW, issue allocate/write/lookup/overwrite/discard/flush, close/reopen, recover WAL and verify mappings and bitmap state.
6. Hardware boundary tests: verify Linux block device flush behavior and the configured multipath path set. Unit tests must not claim to prove array power-loss semantics.

## Safety invariants

- BMPOOL03 offsets are always MetadataView-relative; Data block IDs are always DataView-relative.
- Metadata and Data views are backed by the same parent LUN and the same Bootstrap generation.
- No request admission before fencing, WAL recovery, descriptor OwnerEpoch publication and guarded DM enable complete.
- No mapping publication before data zeroing and its durability barrier complete.
- No overwrite/discard may release old extents before reader-generation and fencing proofs.
- No ambiguous WAL result may be retried in the same live Store/Tree instance.
- Missing runtime hooks, test adapters or unsupported operations fail closed.

## Exit criteria

P4-1.3.2 is complete only when the BMPOOL03 runtime can activate/deactivate safely and its mutation executor passes the full crash/reopen/idempotency/COW/discard test matrix. A compiling interface or documentation-only adapter is not sufficient.

## Following stages

- P4-1.3.4: daemon lifecycle — configuration validation, startup reconciliation, queue lifecycle, bounded shutdown, health/readiness and metrics.
- P4-1.3.5: concurrency — per-queue workers, per-AG contention analysis, multi-volume load, CPU/NUMA and memory profiling with fixed-host regression thresholds.
- P4-1.3.6: production acceptance — Linux 5.15.131 module load and live BIOs, multipath path loss/recovery, Owner lease loss, power-cut/WAL crash recovery, restart and long-duration soak. Real SAN evidence is mandatory; CI and file-backed tests are not substitutes.
