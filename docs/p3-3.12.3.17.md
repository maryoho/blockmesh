# P3-3.12.3.17 — Runtime Owner recovery events and evidence export

## Scope

This stage adds an optional, durable event sink to the actual Owner takeover and
Pool RW activation paths, plus a verifier/exporter for one recovery operation.
The journal is stored on a local evidence filesystem, never on the SAN metadata
LUN. Every event is appended as one JSONL record, SHA-256 chained to the prior
record, and fsync'd before the call returns. A nonblocking advisory file lock
enforces a single writer. Existing files are verified before append; a corrupt
or partial tail is preserved and rejected rather than truncated.

The journal is a runtime trace, not a replacement for raw hardware evidence.
The event exporter checks identity, hash-chain integrity, required event
presence, ordering, and OwnerEpoch continuity. It cannot independently prove
that an operator-supplied fencer, PR reservation manager, committer, or DM gate
is correctly implemented.

## Instrumented runtime boundaries

\x60volume.OwnerCoordinatorConfig.Events\x60 records:

1. \x60sanlock.owner_lease_acquired\x60 after the distributed locker returns a lease.
2. \x60scsi_pr.registration_prepared\x60 after the new initiator registration hook.
3. \x60scsi_pr.preempt_and_abort\x60 after the old-owner Fencer returns success
   (only when a previous OwnerRecord exists).
4. \x60old_owner.metadata_io_drain\x60 after the old-owner I/O barrier returns
   success (only when a previous OwnerRecord exists).
5. \x60owner_record.durable\x60 after OwnerRecord CAS returns success.
6. \x60scsi_pr.owner_reservation_verified\x60 after the reservation manager returns
   success from its all-path verification contract.

\x60metastore.PoolRuntimeConfig.Events\x60 records:

1. \x60dm.owner_gate.fenced\x60 after the local stale DM gate fence returns success.
2. \x60wal.recovery.completed\x60 after the configured AG recovery callback returns.
3. \x60descriptor.owner_epoch.durable\x60 after \x60Store.AdvanceOwnerEpoch\x60 returns
   through the configured cluster-safe committer.
4. \x60dm.owner_gate.prepared\x60 after DM target preparation returns a nonzero
   table instance.
5. \x60dm.owner_gate.enabled\x60 after the guarded DM enable call returns success.

The two config fields must receive the **same \x60runtimeevents.Journal\x60 instance**
in a process so the full recovery sequence is recorded in one operation. A
journal is scoped to one recovery iteration and one operation ID; use a new
file and operation ID for each retry/fault injection. If an event append fails,
the corresponding takeover/activation step fails closed. If the DM enable
event cannot be persisted after the kernel gate was enabled, the existing
error path fences and drains the gate before returning.

Example wiring in the production service bootstrap:

\x60\x60\x60go
journal, err := runtimeevents.Open(
    "/var/lib/blockmesh/evidence/owner-recovery-iteration-001.jsonl",
    "owner-recovery-iteration-001",
)
if err != nil {
    return err
}
defer journal.Close()

ownerCfg.Events = journal
poolRuntimeCfg.Events = journal
\x60\x60\x60

Use a local filesystem independent of the SAN LUN, restrict access to the
BlockMesh service account, and retain the journal with the raw SAN/DM/sanlock
artifacts. The journal is mode 0600. The event sink is optional for compatibility;
production qualification deployments must configure it in both places.

## Build and export

\x60\x60\x60bash
go test ./...
go test -race ./...
go vet ./...
go build -o bm-owner-event-export ./cmd/bm-owner-event-export
\x60\x60\x60

After a successful RW recovery activation, export and verify the event stream:

\x60\x60\x60bash
bm-owner-event-export \\
  --input /var/lib/blockmesh/evidence/owner-recovery-iteration-001.jsonl \\
  --output /var/lib/blockmesh/evidence/owner-recovery-iteration-001.events.json
\x60\x60\x60

The exporter uses exclusive output creation and refuses to overwrite an
existing file. It returns nonzero for a missing event, failed event, duplicate
event type, identity change, invalid ordering, or OwnerEpoch mismatch. It
accepts the absence of both old-owner fencing and old-owner drain events only
for a first-owner activation where no previous OwnerRecord exists.

The JSON export can be added to the P3-3.12.3.15 evidence artifact list as
\x60runtime-events\x60, with its SHA-256. Keep the original JSONL journal as
the primary raw artifact.

## Event schema and proof semantics

Each event contains schema version, operation ID, Volume/Node/Boot identity,
optional OwnerEpoch, event type, phase, success/failure, proof classification,
detail, and UTC observation time. Each journal record adds a monotonic sequence,
previous-record hash, and current SHA-256 hash.

The \x60proof\x60 field deliberately identifies the boundary observed by the caller:

- \x60sanlock-helper-ready\x60: the configured locker returned its lease-ready
  result; this is not a substitute for independent sanlock status evidence.
- \x60fencer-contract-completed\x60: the configured Fencer returned success; this
  event alone does not contain per-path PR OUT responses or independent
  reservation readback.
- \x60reservation-manager-verification-returned\x60: the reservation manager
  returned success; preserve the all-path PR evidence separately.
- \x60store-cas-returned\x60: OwnerRecord CAS returned after the store's durability
  contract. The production SAN store writes and Syncs its inactive slot; retain
  the post-recovery SAN snapshot independently.
- \x60recover-ag-callback-returned\x60: the AG recovery callback returned success.
  This event does not include a replayed-transaction count.
- \x60advance-owner-epoch-returned\x60: descriptor OwnerEpoch publication returned
  through the configured cluster-safe committer; preserve descriptor readback.
- \x60dm-gate-*\x60: the corresponding DM Gate method returned; preserve DM status,
  queue state and stale-Epoch rejection evidence separately.

No event infers old-node power-off, host fencing, PR path coverage, zero
inflight I/O, application data integrity, or array durability from absence of
errors. The exporter is a timeline validator, not the P3.15 full qualification
PASS oracle. The P3.15 raw artifacts and independent before/after SAN snapshots
remain mandatory.

## Crash and failure behavior

- A complete record is appended and fsync'd before the instrumented operation
  continues to its next phase.
- A process crash during a record may leave a partial final line. The reader
  rejects it; do not truncate or repair the original evidence file.
- A hash mismatch, sequence gap, wrong operation ID or changed identity fails
  closed.
- A failed runtime action emits a failure event where the call site can do so.
  Failed journals are not accepted by the recovery exporter.
- If the event filesystem becomes unavailable, takeover/activation stops at
  the next instrumented boundary. This is intentional for qualification mode.
- Journal events are not written to the SAN LUN and do not participate in the
  OwnerRecord/WAL transaction.

## Qualification boundary

Go unit/race/vet checks validate journal integrity and event ordering logic.
They do not execute real sanlock, SCSI PR PREEMPT AND ABORT, multipath,
Linux 5.15.131 DM target, power loss, HBA reset, controller failover, or
application data-integrity tests. A software event-export PASS is not a real
two-node SAN acceptance PASS.
