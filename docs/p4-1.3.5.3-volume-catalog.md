# P4-1.3.5.3 — 持久化 Volume Catalog

## 目标

在同一 LUN 的 BMPOOL03 MetadataView 上持久化 Volume 的身份和逻辑容量，使 bm-metad 重启后能够重新枚举 Volume，而不依赖本地配置文件或内存缓存。

## Catalog 结构

第一版复用 BMPOOL03 固定 Node Table 中的双副本 Volume Descriptor 槽位，不额外引入外部数据库，也不把目录状态保存在本地文件。

Dynamic Volume Descriptor 升级到版本 5：

| 字段 | 含义 |
|---|---|
| VolumeID | 稳定 UUID |
| VolumeName | Pool 内唯一名称，1–63 个 ASCII 字符，允许字母、数字、点、短横线和下划线 |
| LogicalSizeBytes | Volume 逻辑容量，必须按 4 MiB 对齐，且单 Volume 不超过其绑定 AG 的地址空间 |
| CreateToken | 创建请求幂等令牌，用于服务端超时/响应丢失后的重试判定 |
| Arena/Lifecycle/OwnerRecord/ReaderTable | 现有元数据空间与生命周期结构 |
| Generation/VolumeSequence/MappingSequence/OwnerEpoch | 现有版本和并发控制字段 |

兼容性：

- 版本 3、4 Descriptor 仍可读取；旧 Descriptor 的 VolumeName/LogicalSizeBytes/CreateToken 为空。
- 新建 Volume 使用版本 5 Descriptor。
- CRC32C 覆盖全部新字段；名称编码、保留字节和逻辑容量均校验。
- 未知版本、CRC 错误或非零但不可解码的 Descriptor 槽位会 fail closed，不会被当作空槽。

## 创建事务

`DynamicVolumeAllocator.CreateVolume` 执行：

1. 校验 Volume UUID、名称、4 MiB 对齐的逻辑容量、Arena 预留和 CreateToken。
2. 扫描持久化 Descriptor 表，检查 Pool 内名称/UUID 冲突和 CreateToken 重放。
3. 选择空闲 Descriptor 槽位。
4. 从 Reserved Metadata allocator 分配 Arena、Lifecycle、OwnerRecord 和 ReaderTable 空间。
5. 通过 cluster-safe AG WAL 一次提交 Reserved bitmap、双副本 Descriptor 和分配结果。
6. 只有 WAL 提交成功后才向调用方返回 Volume。

相同 CreateToken、UUID、名称和容量的重试返回原 Descriptor（Replayed=true）；相同 Token 对应不同参数则拒绝。Volume create 只创建元数据，不分配 DataView 物理数据块。

Volume 固定绑定一个 AG，逻辑容量不超过该 AG 的地址空间；多个 Volume 的逻辑容量总和可以超过 Pool 的物理 DataView 容量，物理块仍由首次写入时的精简置备分配器按需分配。

## 查询

- `ListVolumes` 每次从 Descriptor 表读取，不把内存索引作为权威数据。
- `FindVolumeByID`、`FindVolumeByName`、`FindVolumeByCreateToken` 从同一持久化 Catalog 查找。
- 返回稳定排序结果，便于后续 CLI 输出和 daemon 启动时重建 Registry。
- 单个非零损坏槽位会使 Catalog 查询报错，不会静默跳过并继续对外提供不完整目录。

## 删除

生产删除入口为 `DeleteVolume`，要求调用方提供 `DynamicVolumeDeleteProof`。其 `AcquireVolumeDeleteGuard` 必须在整个删除事务期间：

- 阻止新的 Reader 注册；
- 证明本地和远端没有活动 Runtime/Reader 引用；
- 完成旧 Owner 在所有 SAN 路径上的 fencing；
- 持有集群级 guard，直到 Descriptor 和 Reserved bitmap 的 WAL 事务提交完成。

随后必须先在同一个集群删除 guard 下调用 `RetireVolumeData`，将所有 Mapping 通过 Data Retire Queue 回收并确认物理 DataView 块已释放；只有成功后才清除 Descriptor 双副本并释放 Reserved 元数据页。删除 guard 从数据回收到 Descriptor/Bitmap WAL 提交全程保持，不允许 Reader 在两步之间重新注册。单纯获取 Owner lease 或仅在本机检查 DM 设备，不足以作为删除证明。`DeleteVolume` API 强制要求 `DynamicVolumeDeleteProof.RetireVolumeData`；回收失败时 Descriptor 必须保持可见，允许在完成 WAL 恢复后重试。低层 `ReleaseVolume` 保留给内部维护/测试；控制面必须使用具备 Reader-set 协调能力的 DeleteProof。

## bm-metad Volume Create 集成进度

当前 main 已将 `volume create` RPC 接入持久化 Catalog：

1. 按 Pool UUID 获取分布式 `pool-catalog/<uuid>` sanlock 资源，串行化不同节点上的 Descriptor 槽位和 Reserved bitmap 分配。
2. 通过 Pool Bootstrap 打开同一 LUN 的 MetadataView，校验 Pool UUID、ViewGeneration 和 BMPOOL03 Superblock。
3. 以只读方式打开 Catalog 用于 list/info；只读打开不修复双副本 Header，也不允许任何分配/扩容/释放操作。
4. 创建时以可写方式打开 Reserved allocator，通过 AG0 的动态共享 WAL 提交 bitmap 和双副本 Descriptor。
5. 新 Volume 先预留 64 个 4KiB Arena page（256KiB）、8 个 Lifecycle page，以及 OwnerRecord/ReaderTable 页面。Arena 后续由现有扩容接口按需增长；Volume create 不分配 DataView 物理数据块。
6. CreateToken 在获取 Pool 锁后先查 Catalog。相同 Token 且名称/容量一致时返回原 Descriptor；参数不同则返回 Token 冲突，避免超时重试产生第二个 Volume。

服务端仍要求配置 `discovery_devices`，并要求 sanlock RINDEX 或完整静态资源映射。Pool UUID 派生的目录锁资源不依赖本机 `/dev` 路径。

## 本阶段边界

当前已完成 Descriptor v5、Catalog 原语、Unix socket RPC 和 `bmctl volume create` 到 Catalog 的服务端调用。尚未完成：

- `bmctl pool create` 的生产 Pool Owner/SCSI PR 建立和自动初始化闭环；
- 由持久化 Descriptor 动态重建 Pool/Volume Runtime Registry（当前 Runtime 启动路径仍保留旧的静态 Volume 配置兼容路径）；
- 动态 RW/RO 激活时自动创建 DM table，并将其接入 Runtime 的 Gate；
- Deactivate 时 DM remove、BIO drain、Lease release 的完整逆序处理；
- 具备真实 Reader-set guard 和 Data Retire Queue 的生产删除后端；
- 两节点 SAN 故障注入和 P4-1.3.5.7 端到端验收。

因此，当前 `volume create` 仅在已经格式化并配置发现的 BMPOOL03 Pool 上可用；不能据此宣称 Pool 创建、Volume 激活/挂载或生产集群验收已经完成。
