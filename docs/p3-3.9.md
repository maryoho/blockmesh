# P3-3.9 Multi-node failure injection and recovery verification

## Scope

P3-3.9 validates Reader Lease / SAN PR fencing / durable Reader transitions
across independent metadata Store instances and controller restarts. Tests
use a shared in-memory block device and deterministic fakes for the cluster
reader-set lock, sanlock slot lease, PR fencer and WAL commit boundary. These
are protocol/failure-state tests, not SCSI target or multipath qualification.

## Failure matrix

| Injection point | Durable Reader state after restart | Expected recovery |
|---|---|---|
| Slot lease probe cannot be acquired | Active / Leaving | Do not call PR fencer; keep generation pinned |
| PR PREEMPT AND ABORT or path verification fails | Active / Leaving | Retry; never collect |
| WAL fails before ReaderFenced image is durable | Active / Leaving | Re-probe and repeat idempotent fencing |
| WAL image is durable but acknowledgement is lost | Fenced | Do not fence again; retry pending Retire Queue processing |
| Metadata IO drain fails | Fenced | Keep Retire Queue intact; retry drain and collection |
| Controller restarts with pending Retire Queue | Fenced records remain durable | Retry collection without a new fencing event |
| Two controllers recover the same stale slot | One Fenced transition | Slot lease + reader-set barrier serialize; second controller revalidates |

TestP339RecoveryRestartsAfterFenceBeforeDurableReaderState models an error
before the durable ReaderFenced image. SAN fencing is repeated after restart,
so the production fencer must be idempotent: an already-absent target key is
success only after every configured path has been queried and verified.

TestP339RecoveryRestartsAfterDurableReaderStateBeforeAcknowledgement models a
durable state image with a lost acknowledgement. Restart must read Fenced and
must not issue a second fence.

TestP339TwoRecoveryControllersFenceOneReaderOnlyOnce opens two independent
Store / ReaderTable instances over the same shared device and races two
controllers against one stale Reader slot. The fake slot lease and shared
reader-set coordinator model the distributed serialization contracts.

## Safety assertions

- Heartbeat timeout is only a candidate detector.
- Failed slot lease probe or failed PR operation never changes durable Reader
  state to Fenced.
- Reader remains generation-pinning until Fenced or Closed is durable.
- Lost commit acknowledgement is resolved by reopening and reading durable
  metadata, not by assuming the commit failed.
- Retire Queue collection remains gated by global Metadata IO Drain and
  Reader generation calculation.
- Failed or ambiguous drain never frees pages.

## CI and hardware qualification

CI runs go test ./..., go test -race ./..., and go vet ./....

CI does not emulate real SAN SCSI task-abort semantics. Before production
qualification, run on at least three SAN-connected hosts (one RW owner and
two RO readers) with actual sanlock lockspace, SCSI-3 PR reservation,
multipath paths and DM target:

1. Start one RW owner and two RO Reader sessions; continuously issue metadata
   reads from both readers while the owner publishes COW roots.
2. Kill one reader with SIGKILL and verify its slot lease is not considered
   free until sanlock reports release.
3. Make one SAN path inaccessible during PREEMPT AND ABORT. Verify fencing
   fails closed and no retired page is reclaimed.
4. Restore the path, complete PR fencing, then verify target keys are absent
   on every path before ReaderFenced is committed.
5. Kill recovery after the Fenced WAL commit but before collection. Restart it
   and verify collection occurs only after the global metadata IO drain
   provider confirms all relevant DM metadata I/O is drained.
6. Repeat with controller termination before and after WAL commit
   acknowledgement, sanlock daemon restart and multipath failover.
7. Confirm the fenced host cannot issue further metadata reads or reuse its
   old PR key; a rebooted reader must use a new BootID and higher slot Epoch.

Capture sanlock logs, sg_persist --in --read-keys output for every path,
multipath state, controller reports, WAL transaction IDs, Reader Table pages,
Retire Queue generations and DM inflight-I/O counters. Do not mark P3-3.9
hardware-qualified until these artifacts demonstrate the full sequence.

## Current boundary

P3-3.9 adds deterministic multi-instance and restart fault tests. It does not
wire the controller into a daemon lifecycle, implement the production
cluster-wide MetadataIODrainBarrier, provision sanlock resources, or execute
real SAN hardware failure injection. Those remain deployment/integration
work and must not be represented as passing CI tests.
