# P3-3.12.2 — Pool-backed Volume Store

## Scope

This phase moves the fixed-LBA metastore COW B+Tree Store onto the unified BMPOOL02/BMDVOL02 layout. A Volume Store now opens against the whole Pool device and uses its Node Table descriptor to identify that Volume's private metadata extents. It does not create, read, write, or publish a BMMETA01 superblock at Pool LBA 0/1.

## Store API

`metastore.OpenPoolVolume(dev, poolSB, index, expectedVolumeID)`:

1. Validates the Pool Superblock and resolves the two-page Node Table slot.
2. Reads both BMDVOL02 copies, checks CRC/version/identity, and selects the highest valid generation.
3. Validates the descriptor against Pool geometry and the deterministic Reserved sub-range belonging to the selected slot. A descriptor for slot N cannot point into another Volume's Arena/Lifecycle allocation.
4. Builds the existing metastore Store view with absolute Pool page IDs. Arena IDs remain absolute 4 KiB Pool page numbers, so B+Tree, Arena, PersistentArena and Retire Queue code continue to use the same page-ID contract.
5. Exposes `Store.ReaderTableRange()`: the final 128 pages of the Volume's deterministic bootstrap slot are reserved for one durable Reader slot per page. `NewReaderTable` rejects Pool-backed ranges outside this Volume-private extent or overlapping its Arena/Lifecycle. New Volume initialization leaves this tail reserved; older descriptors that consumed the entire slot can still open their Store, but cannot open a ReaderTable until migrated.
6. Refresh reloads the descriptor pair instead of looking for legacy superblocks.

The Store retains the whole Pool device as its I/O target. COW pages are written only inside the descriptor's Arena; lifecycle after-images are accepted only inside its Lifecycle extent. All offsets remain absolute byte offsets in the Pool device.

## Root publication and WAL ordering

For a Pool-backed Store, `CommitPagesAndPublishWithImages` appends the inactive BMDVOL02 page as the final `PageImage`:

- COW B+Tree page after-images first;
- complete Lifecycle checkpoint and multi-page Retire Queue after-images next;
- inactive Volume Descriptor after-image last.

The descriptor generation and Volume Sequence increase together. It carries RootPage and MappingSequence; Pool Superblocks remain immutable. Reader Table slot updates are separate WAL transactions protected by the Reader Set coordinator. The Reader Table extent is derived from the Volume slot geometry (128 pages at the slot tail) rather than stored as an additional descriptor field in BMDVOL02 v2. Volume initialization zeros this region before publishing the descriptor. The existing WAL validator checks that the descriptor is a valid Pool descriptor in the Node Table and is the final after-image. Recovery replays the descriptor idempotently and prevents an older generation from replacing a newer valid copy.

The direct `Publish` method is limited to the initial root publication while the Lifecycle region is still blank. Once persistent lifecycle metadata has been initialized, all root updates must use the WAL-backed PersistentArena path.

`OpenPoolVolume` itself does not acquire sanlock leases or run WAL recovery. Production open ordering remains: acquire the Pool/Volume Owner lease and required AG lease, create/recover the AG Journal, then construct/open the Store and inject the cluster-safe committer and Reader Coordinator. A process-local committer is not safe for a shared SAN device.

## Volume administration commands

Initialize one previously empty Node Table slot (destructive to that slot):

```bash
bm-meta volume-init \
  --device /dev/mapper/mpath-meta \
  --index 3 \
  --volume-id volume-0003 \
  --owner-epoch 1 \
  --lifecycle-pages 32 \
  --confirm-init
```

Inspect one descriptor (read-only):

```bash
bm-meta volume-inspect --device /dev/mapper/mpath-meta --index 3
```

Volume initialization must be performed under an external Pool administration lock after cluster quiesce/fencing. Local O_EXCL only protects the local host; it is not a distributed lock. The bootstrap allocator still partitions Reserved into fixed equal-sized per-slot extents. A future Pool extent allocator may replace this bootstrap policy without changing the Store's page-ID contract.

## Tests

The Pool-backed Store test creates a sparse 16 GiB metadata image, initializes a Pool and Volume descriptor, formats the Lifecycle region, injects a failed WAL commit, retries through PersistentArena, and reopens both Store and Arena. It verifies COW root publication, all Lifecycle after-images, reservation-to-Live transition, durable ReaderTable registration in the reserved tail pages, and that both Pool Superblocks remain decodable and untouched. PersistentArena now holds the Arena mutex from reservation validation through the durable commit, preventing a concurrent Abort/Reserve from recycling pages while their WAL after-images are in flight.

CI is expected to run `go test ./...`, `go test -race ./...`, and `go vet ./...`.

## Not yet production-complete

- This phase supplies the Pool-backed Store API and makes the existing Arena/PersistentArena/ReaderTable/RetireQueue use the Volume-private absolute page ranges. It does not yet wire a complete daemon `VolumeRuntimeBackend` that provisions sanlock resources, obtains Owner/AG/Reader leases, registers SCSI PR keys, fences old owners, drains DM I/O, and opens the Store in the required order.
- WAL recovery must be invoked under the appropriate distributed AG lock before data-path admission. Do not use a plain `wal.Journal` without the required distributed lock on a multi-writer SAN.
- No SAN power-loss, multipath fault, or cross-host fencing qualification has been performed. Filesystem-backed sparse-image tests are not hardware durability tests.
- Legacy `metastore.Format/Open` remain only for historical isolated images/tests. They must not be used on BMPOOL02 Pool devices.


## P3-3.12.3 implementation note — durable Owner Epoch gate

The Runtime activation path now treats the distributed owner lease epoch as
part of the Pool-backed Volume activation protocol:

1. A RW backend acquires the distributed owner lease. Its contract requires
   that acquisition does not return until the previous owner is fenced from
   every SAN path; a timeout or uncertain fencing result must fail activation.
2. The lease exposes its monotonically increasing `Epoch()`.
3. After WAL recovery and Pool-backed Store construction, the backend supplies
   `VolumeRuntimeMetadata.PublishOwnerEpoch`. RuntimeManager requires this
   callback for RW and invokes it before starting recovery supervision or
   enabling requests.
4. `Store.AdvanceOwnerEpoch` refreshes the descriptor, rejects zero/stale
   epochs, increments descriptor generation and VolumeSequence, and publishes
   the new OwnerEpoch as a single final BMDVOL02 after-image through a
   `ClusterSafeCommitter`. It never writes Pool Superblocks.

A backend can wire the callback as
`func(_ context.Context, epoch uint64) error { return store.AdvanceOwnerEpoch(epoch, committer) }`.
The committer must serialize against all other Volume Descriptor publishers
using the same distributed AG/WAL resource.

This is the first P3-3.12.3 integration slice, not a complete production
backend. Concrete sanlock owner-resource provisioning, old-owner SAN PR
PREEMPT AND ABORT verification, owner lease renewal/loss fail-stop, Reader
Session heartbeat lifecycle, request-admission hooks and DM drain integration
remain platform wiring/qualification tasks. A fake lease or callback does not
prove SAN fencing.
