# P4-1.2.5.21 — BMPOOL03 End-to-End Allocation, Recovery and Expansion Acceptance

Adds an integrated acceptance scenario covering:

1. Format one BMPOOL03 logical MetadataView and its AG bitmaps/checkpoints.
2. Open BMDVOL03, initialize PersistentArena lifecycle pages, and create a
   persistent B+Tree using DynamicSharedCommitter.
3. Zero a DataView block, then attempt one transaction that includes bitmap,
   B+Tree Mapping, idempotency record, lifecycle state and Volume root.
4. Inject an I/O failure while applying the first metadata after-image after
   the WAL Commit is durable. The allocation returns an uncertain outcome.
5. Abandon the old in-memory objects, reopen/recover DynamicJournal, reopen
   Store/Tree/Allocator, and verify Mapping, bitmap, idempotency record and
   zeroed data all agree. Repeating the request returns the durable result.
6. Simulate a newer Extent Map generation by exposing additional fragmented
   Metadata and Data extents. Rebuild views, clear newly exposed final-AG
   bitmap padding through the WAL, publish both new superblock copies, and
   allocate from the newly exposed DataView capacity.

This is deterministic device-image fault injection, not a SAN power-cut or
multipath hardware qualification. The test also keeps AGCount unchanged;
online growth that requires another AG is rejected until an explicit
pre-reserved AG capacity/layout migration is implemented.

The acceptance path also relocates the Volume lifecycle pages into the expanded MetadataView, WAL-publishes the enlarged BMDVOL03 Arena range, reopens PersistentArena/B+Tree, and only then resumes allocations. MetadataView and DataView objects created by BootstrapStore now carry the same Extent Map generation; dynamic Store/Allocator opens reject a nonzero mismatched generation.
