# P4-1.2.5.10 — Dynamic Pool acceptance coverage and remaining integration

Automated coverage now includes:
- BMPOOL03 Bootstrap/Extent Map format and reopen.
- CRC and Extent Map validation through the existing codec tests.
- Uncommitted after-image ignored after injected Commit write failure.
- Uncertain Commit Sync outcome recovered by reopen.
- Committed Extent Map corruption fails closed.
- Stale writer rejected after another writer advances Generation.
- Owner lease loss before Commit prevents publication.
- OwnerEpoch is persisted and can advance after a new fenced Owner lease.
- Device growth is persisted as Free extents only; metadata does not grow automatically.
- One parent Device backs the Bootstrap/Metadata/Data extent views.
- Logical sector mismatch and legacy BMPOOL02 format rejection.

GitHub Actions runs the Go tests, race tests, vet and Linux 5.15 DM/kernel build. These tests use sparse regular-file devices and injected I/O faults. They are not a substitute for two-node SAN power-loss testing, multipath path-failure injection, SCSI PR PREEMPT AND ABORT verification, or sanlock/OwnerCoordinator takeover testing.

Important remaining production integration:
1. bmctl mutating commands currently fail closed until a real OwnerCoordinator lease is injected; the CLI does not fake OwnerEpoch from configuration.
2. The metadata usage snapshot must be produced from authoritative runtime counters, not manually guessed.
3. BMPOOL03 must be connected to the per-AG Bitmap/Mapping transaction path so Data allocation, zeroing, mapping publication and Extent Map updates share the required transaction/recovery semantics.
4. BMPOOL02 remains on the existing fixed-layout path. No online in-place migration has been implemented.
5. Full two-node SAN qualification and crash/power-loss testing remain required before production enablement.
