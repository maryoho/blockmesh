# P4-1.3.2.3 — BMPOOL03 Runtime Adapter Integration

## Existing components reused

This stage intentionally reuses the existing production adapters instead of
introducing a second DM gate or Owner adapter:

- `internal/dynamicruntime/owner_adapter.go`: P3 OwnerCoordinator -> BMPOOL03 OwnerLease.
- `internal/dynamicruntime/backend.go`: BMPOOL03 RW/RO Runtime construction on one parent LUN.
- `internal/dynamicruntime/integrated.go`: production dependency validation and manager wiring.
- `internal/dynamicruntime/dm_gate.go`: DM OwnerEpoch / ReaderEpoch target gate.
- `internal/dmowner/gate.go`: dmsetup message transport for kernel target prepare/enable/fence.
- `internal/metastore/reader_session.go`: sanlock Reader lease + SCSI PR registration + durable Reader Table slot.
- `internal/metastore/dynamic_pool_processor.go`: BMPOOL03 request processing using Runtime snapshots.

## Production wiring

`NewIntegratedDynamicVolumeRuntimeManager` is the production constructor.
It rejects a non-Sanlock backend, a different OwnerCoordinator locker, a
mismatched Reader locker, missing Reader resource resolver, missing SCSI PR
ReaderRegistrar, or a ReaderCoordinator that is not the distributed
Reader-set coordinator using the same locker.

The caller supplies a `DMRequestGate` created with:
- `dmowner.DMSetupGate` for OwnerEpoch operations;
- `dmowner.DMSetupGate` as the ReaderGate implementation;
- a Volume ID -> actual DM mapper device resolver.

The same concrete SanlockLocker instance is shared by P3 Owner, BMPOOL03 WAL,
Reader Lease, and distributed Reader-set coordination. Different resource
names still provide independent lock domains.

## Activation and request flow

### RW

1. P3 OwnerCoordinator acquires the exclusive sanlock Owner resource.
2. It loads the authoritative OwnerRecord, fences the previous initiator on
   every SAN path, drains previous-owner metadata I/O, advances OwnerEpoch,
   publishes OwnerRecord, and verifies SCSI PR reservation.
3. BMPOOL03 Backend opens Bootstrap, MetadataView and DataView from the same
   parent LUN and one view generation.
4. It recovers every AG WAL, publishes the BMDVOL03 OwnerEpoch, installs
   OwnerEpoch guards on WAL committers, opens persistent B+Tree and allocator.
5. DMRequestGate prepares the kernel OwnerEpoch gate, performs a final
   synchronous health check, then enables the gate.
6. Every metadata request is validated by DynamicVolumeRuntimeManager against
   the live Owner lease and durable BMDVOL03 OwnerEpoch.

### RO

1. Backend opens the same BMPOOL03 parent LUN and validates Bootstrap,
   Superblock, geometry and view generation without acquiring RW ownership.
2. It recovers the selected AG WAL under the distributed WAL lock, joins the
   distributed Reader-set barrier, acquires the Reader sanlock resource,
   registers local SCSI PR keys, and publishes the durable Reader Table slot.
3. The Reader session pins a specific RootPage / RootGeneration.
4. DMRequestGate prepares and enables the kernel ReaderEpoch + RootGeneration
   gate; it never uses the RW Owner gate.
5. Every metadata request revalidates the Reader sanlock lease and durable
   Reader Table identity and must match the pinned generation.

## Fail-stop and teardown

The kernel `owner_fence` / `reader_fence` command is the synchronous gate and
BIO-drain barrier. StopRequests fences the active gate. DrainRequests then
confirms the same target instance has already been fenced before the manager
releases the Reader session, Runtime views, Owner lease, or parent LUN.

A failed/ambiguous DM fence leaves the Runtime registered and its resources
pinned. A lost Owner or Reader lease never triggers automatic reacquisition.

## Request processor boundary

The BMPOOL03 DynamicPoolRuntimeProcessor now passes the request context into
`ResolveRequest`, so Reader Table snapshot reads are cancellable and bounded
by the request context.

Lookup and Flush are supported by the current processor. Allocate/zero/publish
and Discard are deliberately rejected with `ErrMutationPathUnavailable`
until P4-1.3.3 wires the actual COW mutation executor. No write is redirected
to the BMPOOL02 runtime.

## Validation boundary

The Go adapter tests cover the DM Owner and Reader gate lifecycle, including
health-check failure fencing. Repository tests and Race/Vet must still run in
CI or on the developer workstation after these commits. A real SAN acceptance
is still required to verify all-path PR behavior, sanlock loss, kernel DM
fence/drain behavior, and concurrent RW/RO access on the supported Linux 5.15
kernel. This stage does not claim that hardware acceptance has been completed.
