# P3-3.12.3.16 — Real two-node SAN evidence capture executor

## What this stage automates

This stage adds a read-only node-local capture agent and an SSH coordinator:

- `bm-owner-san-agent capture` runs on each SAN node and records the local
  NodeID/BootID, kernel, multipath path inventory, per-component SCSI PR keys
  and reservation, SAN WWID, durable Pool/Volume Descriptor and OwnerRecord
  snapshot, systemd unit state, DM info/status/table, sanlock status and device
  size.
- Each fixed host probe records command, arguments, start time, duration,
  exit status, output and SHA-256 of the raw command output.
- `scripts/owner-san-two-node-capture.sh` invokes the agent on Node A and Node B
  over SSH, copies both evidence bundles to an independent evidence directory,
  then invokes `verify-pair`.
- `verify-pair` fails closed unless both nodes see the same WWID, Pool UUID,
  Volume ID/index and durable OwnerRecord identity/Epoch, have complete
  multipath component-path coverage, and all required read-only probes succeed.

The agent does not issue SCSI PR OUT, alter sanlock resources, restart services,
inject a fault, change DM admission, or write to the SAN LUN. It is a capture
and cross-node consistency executor, not a fencing implementation.

## Build

Build on a Linux host with Go 1.23. Install both binaries on each node at
stable absolute paths, and keep a local copy of the agent on the coordinator:

```bash
go build -o bm-owner-crash-qualify ./cmd/bm-owner-crash-qualify
go build -o bm-owner-san-agent ./cmd/bm-owner-san-agent
```

The `bm-owner-crash-qualify` binary must be present on each SAN node because
the agent invokes its read-only `snapshot` command locally.

## Baseline capture on both nodes

Run from the coordinator. Supply every component path returned by the
multipath map on each node; do not pass only the multipath map. Node IDs are
the configured BlockMesh identities, not hostnames.

```bash
scripts/owner-san-two-node-capture.sh \
  root@node-a root@node-b \
  /usr/local/sbin/bm-owner-san-agent \
  /usr/local/sbin/bm-owner-crash-qualify \
  11111111-2222-3333-4444-555555555555 \
  node-a node-b \
  /dev/mapper/mpatha /dev/sda,/dev/sdb \
  bm-11111111-2222-3333-4444-555555555555 \
  blockmesh.service 0 \
  ./bm-owner-san-agent evidence/baseline-iteration-001
```

The script validates arguments before constructing remote commands, refuses
to overwrite local bundles, uses SSH to execute only the fixed capture
subcommand, and retains the remote evidence copies under `/var/tmp`. Use
SSH keys and a restricted maintenance account with permission to run the
read-only commands and read the metadata LUN. Do not grant the capture agent
sudo access to mutating commands.

The path list is host-local. Node A and Node B may have different `/dev/sdX`
names, but each list must exhaustively cover the component paths shown by that
node's `multipath -ll` output. The verifier checks that all paths on each node
resolve to one common WWID and that the WWID is the same across nodes.

## Execute a recovery iteration

1. Capture the stable baseline on both nodes and preserve the resulting JSON
   bundles outside the SAN LUN.
2. Review the baseline bundles: same Pool UUID, Volume ID/index, selected
   OwnerRecord, WWID and expected NodeID/BootID; all PR paths and required
   host probes must be readable.
3. Start the deterministic application workload and preserve its acknowledged
   sequence/checksum baseline.
4. Inject the selected fault using the separately reviewed lab procedure.
   The existing `scripts/inject-owner-process-crash.sh` only kills the
   verified BlockMesh service main process after its explicit destructive
   confirmation. It does not simulate host power loss or SAN path failure.
5. Allow the production Owner recovery path on the surviving node to execute.
   Do not use the evidence agent to issue PR OUT, change sanlock or open DM.
6. After recovery, run `bm-owner-san-agent capture` directly on the new Owner
   node, with a new evidence output filename. If the old node is still online
   and safely isolated, capture it too. For a powered-off old node, preserve
   out-of-band power/fencing evidence; do not claim a successful old-node
   capture.
7. Run the P3-3.12.3.14 before/after metadata and SCSI PR verification, then
   feed the independently collected runtime proofs and raw artifacts to the
   P3-3.12.3.15 `bm-owner-recovery-report` acceptance flow.
8. Preserve all bundles, logs, workload checksums, WWID/path inventory,
   kernel/HBA/firmware/array versions and the final report as one immutable
   iteration directory.

## Direct capture on one node

When only the surviving node is reachable after a host-loss test, run:

```bash
bm-owner-san-agent capture \
  --volume-id <volume-id> --node-id node-b \
  --multipath-map /dev/mapper/mpatha \
  --paths /dev/sdc,/dev/sdd \
  --dm-device <blockmesh-dm-name> \
  --systemd-unit blockmesh.service --metadata-index 0 \
  --owner-snapshot-bin /usr/local/sbin/bm-owner-crash-qualify \
  --output evidence/post-node-b.json
```

The command requires an explicit component-path list and uses exclusive
creation with mode 0600. It never overwrites an existing evidence bundle.

## Interpretation and safety boundary

A two-node baseline `verify-pair PASS` proves that the two capture agents
successfully read the same SAN identity and durable OwnerRecord at capture
time. It does **not** prove that a stale initiator has been fenced, that
PREEMPT AND ABORT has completed, that old DM inflight I/O drained, that WAL
recovery completed, or that the new DM queue was opened at the right Epoch.

The command outputs are preserved as raw evidence; the agent intentionally
does not infer sanlock ownership, DM queue state, or application integrity from
unstructured log text. Those recovery claims still require the runtime proof
and data-integrity evidence defined in P3-3.12.3.15. In particular, a missing
old-node capture after power loss is not equivalent to proof of fencing.

All operations in this stage are read-only. Run the destructive fault helper
only against a disposable test LUN on isolated lab nodes. Real PREEMPT AND
ABORT, power loss, HBA reset, path failover and array controller failover
remain real-hardware qualification tasks; GitHub CI cannot validate them.
