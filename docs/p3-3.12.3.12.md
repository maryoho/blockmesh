# P3-3.12.3.12 — DM kernel fault injection and two-node Owner takeover

## Objective

Prove that a stale node cannot continue issuing successful writes after the
new node has completed SAN fencing, and that the new node cannot open its
kernel DM write gate before the OwnerCoordinator has completed the fencing,
drain, OwnerRecord and PR reservation sequence.

This phase adds deterministic state-machine race tests, a two-node takeover
integration test, and a root-only disposable-loop-device qualification script.
The Go tests are software simulations. They are not evidence of real SCSI PR,
multipath, HBA, array-cache, power-loss, or Linux block-layer behavior.

## New tests

### `internal/dmowner/gate_model_test.go`

The test-only `kernelGateModel` mirrors the DM target's admission lock and
in-flight drain contract. It covers:

- writes rejected before prepare and after fence;
- `owner_fence` closes admission and cannot return while an admitted write is
  outstanding;
- stale `prepare`, `enable`, and `fence` messages cannot modify a newer epoch;
- a newly constructed target after table reload starts at epoch 0, closed and
  fenced;
- concurrent write admission racing with fence cannot admit a write after
  fence completion.

This is a model-level test; it does not execute `dm-blockmesh.ko`.

### `internal/volume/dm_owner_takeover_integration_test.go`

The two-node integration tests compose the existing OwnerCoordinator, shared
SAN OwnerRecordStore, exclusive sanlock simulator, path-scoped PR fencer,
old-owner I/O barrier and per-node DM gate models.

The successful handoff deliberately leaves node A's local DM gate open after
its sanlock lease is released. This models a stale process that has not yet
observed lease loss. Node B must fence A through the simulated all-path PR
operation before its OwnerCoordinator can publish the new OwnerRecord and
return a lease. Only after that does node B prepare and enable its higher
OwnerEpoch. The test asserts A rejects writes, B admits writes, and at most
one sanlock Owner is held at a time.

The negative test injects a failure on one multipath path. Node B must not
receive an Owner lease or admit writes. The old gate is intentionally not
reported as fenced: incomplete PR coverage is not a successful takeover.

A third test injects a delayed old-epoch fence after the new epoch is active
and verifies that it cannot close the new gate.

## Disposable Linux DM target qualification

Build against the exact running kernel headers, preferably the deployed
5.15.131 build:

```bash
cd kernel/dm-blockmesh
make KDIR=/lib/modules/$(uname -r)/build
```

Run only on a disposable test host. The script creates a 64 MiB temporary
file-backed loop device and a temporary DM device. It does not touch a SAN LUN:

```bash
sudo scripts/qualify-dm-owner-epoch.sh \
  kernel/dm-blockmesh/dm-blockmesh.ko
```

The script checks:

1. a new target rejects writes but still permits reads;
2. prepare/enable for epoch 41 permits writes;
3. fence 41 rejects new writes and a same-epoch enable;
4. stale epoch 41 messages cannot affect active epoch 42;
5. DM table reload starts closed and does not inherit epoch 42;
6. fencing while `fio` submits writes drains all admitted bios (`inflight=0`);
7. only a strictly newer epoch can reopen the target.

`fio` is optional. Without it, the script still checks the gate and drain
status but skips concurrent submission stress. A successful script run is a
single-host DM target qualification, not a two-node SAN qualification.

## Real two-node SAN procedure

Do not run this against production volumes. Use a dedicated test LUN, two
initiators, known multipath path inventory, and a recovery plan.

1. Build and load the exact same module on both hosts, using the exact
   deployment kernel build and configuration.
2. Create the BlockMesh DM target on node A and activate RW through the Pool
   runtime. Record its OwnerRecord identity, BMDVOL02 OwnerEpoch, PR key and
   reservation holder/type on every path.
3. Generate sustained writes through node A's DM device. Record application
   checksums and block-layer error counters.
4. Stop or isolate the node A sanlock helper while deliberately keeping its
   process and DM table alive. Confirm node A's local lease-loss path closes
   its gate and drains admitted writes. Separately test a hard-crash case where
   the local callback cannot run.
5. Activate node B. Verify it obtains the exclusive sanlock resource, registers
   its path-scoped PR key, issues PREEMPT AND ABORT, and proves the old key is
   absent on every configured path before it proceeds.
6. Verify the old Owner's outstanding I/O barrier, OwnerRecord CAS, PR RESERVE
   holder/type and BMDVOL02 OwnerEpoch publication. Node B must not call
   `owner_enable` before all these checks and the synchronous sanlock guard
   succeed.
7. Confirm node A writes fail after successful PR fencing, node B writes
   succeed, and restored data/checksums are consistent.
8. Repeat with one path unavailable, PREEMPT AND ABORT rejected, reservation
   verification mismatch, sanlock loss immediately before/after enable,
   DM table reload, and delayed old-epoch control messages.

Capture `dmsetup status`, `dmsetup table`, `dmsetup info -c`,
`multipath -ll`, `sg_persist --in --read-keys`,
`sg_persist --in --read-reservation`, sanlock logs, kernel logs, and
application checksums for every run.

## Acceptance criteria

- No two nodes simultaneously pass the OwnerLease + PR proof and open their
  write gates.
- No new Owner write gate opens if any configured PR path is unverified.
- The old Owner cannot complete new writes after successful PREEMPT AND ABORT.
- Every bio admitted before local gate closure is included in the drain barrier.
- A stale epoch message cannot close or reopen a newer Owner gate.
- DM table reload is closed by default and requires a fresh trusted prepare,
  lease guard and enable sequence.
- Any failed fence, drain, or fail-stop retains resources and prevents normal
  Owner release/cleanup.

## CI and qualification boundary

GitHub CI runs:

- `go test ./...`;
- `go test -race ./...`;
- `go vet ./...`.

These cover Go model and simulated two-node sequencing only. CI does not build
or load the kernel module. Before claiming kernel qualification, build and run
the disposable-device script on the exact Linux 5.15.131 kernel. Before
claiming SAN qualification, complete the two-node procedure above with the
actual array, initiators and multipath paths. Neither qualification is
implicitly satisfied by a passing Go test.
