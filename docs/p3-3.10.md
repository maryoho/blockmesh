# P3-3.10 Recovery Controller production lifecycle

## Lifecycle contract

`ReaderRecoverySupervisor` owns one `ReaderRecoveryController` loop per
activated volume. The volume manager must call `Activate(ctx, volumeID)`
after the metadata Store, WAL committer, Reader Table, Persistent Arena,
sanlock coordinator, lease probe, PR fencer and global metadata I/O drain
provider have been opened and validated.

Activation is idempotent for an already-running volume. The factory and
`ValidateProduction` run synchronously; a missing or unsafe dependency
rejects activation before the loop starts.

Deactivation calls cancel and waits for the loop to return. The caller must
not close the Store, Arena, WAL committer, sanlock locker or metadata device
until `Deactivate` returns. Daemon shutdown closes the supervisor,
cancels every volume loop, and joins them before tearing down shared services.

## Production dependency validation

`ReaderRecoveryController.ValidateProduction` requires:

- persistent Arena and a non-nil global MetadataIODrainBarrier;
- a non-Noop SAN fencer;
- `SanlockReaderLeaseProbe` backed by `SanlockLocker`;
- `SanlockReaderCoordinator` using the same locker as the lease probe;
- a cluster-safe WAL committer;
- the Persistent Arena and Reader Table to share the same sanlock reader-set coordinator.

This is a fail-closed validation of dependency types and wiring. It cannot
prove that configured sanlock resources, SCSI PR paths, reservation keys or
the DM drain implementation are correct; deployment health checks and
hardware qualification remain mandatory.

## Shutdown cancellation

The recovery fencing path now uses a context-aware reader-set lock when the
coordinator supports it. `SanlockReaderCoordinator` bounds lock acquisition
by both the caller context and its configured timeout, so deactivation can
interrupt a controller waiting for the distributed reader-set barrier.

Other Reader Table operations retain the existing non-context coordinator
contract for API compatibility. They must be stopped by their owning volume
session before metadata resources are closed.

## Required integration order

1. Open the shared metadata device and recover the WAL.
2. Acquire/validate the volume's owner or reader admission lease as applicable.
3. Construct the Reader Table and Persistent Arena with the cluster-safe WAL
   committer and the same SanlockReaderCoordinator instance.
4. Construct SanlockReaderLeaseProbe with the same sanlock locker.
5. Construct and validate the real SCSI PR fencer and the cluster-wide
   MetadataIODrainBarrier.
6. Activate the volume recovery loop.
7. On deactivate: stop new volume work, call Deactivate and wait, then close
   Reader sessions, Arena, WAL and device resources in dependency order.
8. On daemon shutdown: call Shutdown and wait before closing shared services.

## Scope boundary

P3-3.10 supplies the lifecycle supervisor and production dependency guard.
The existing `cmd/bm-meta` binary remains a local JSON/WAL demonstrator and
does not yet open the fixed-LBA shared SAN metadata device or own a real
Volume activation manager. Therefore the supervisor is ready for that manager
to call, but automatic recovery is not yet wired into the demo CLI. No real
SAN or DM integration is claimed by these tests.
