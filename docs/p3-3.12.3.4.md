# P3-3.12.3.4 — SAN OwnerRecord storage and Pool layout integration

Kubernetes Lease OwnerRecord support has been removed. BlockMesh does not
require Kubernetes API, etcd, ServiceAccount tokens, RBAC, or an orchestration
control plane for Owner acquisition and recovery.

## Pool-reserved on-disk layout

Every bootstrap Volume slot in the BMPOOL02 Reserved region now has four
non-overlapping subregions, in page order:

1. **OwnerRecord A/B:** first two 4 KiB pages, dedicated to redundant SAN
   OwnerRecord copies.
2. **Arena:** begins immediately after the two OwnerRecord pages.
3. **Lifecycle:** follows the Arena and contains lifecycle/retire metadata.
4. **Reader Table:** final `format.ReaderTablePages` (128) pages of the slot.

The slot size is derived from
`(MetadataSize - ReservedOffset) / MaxVolumeDescriptors`, rounded down to a
4 KiB boundary. The OwnerRecord pages are not part of the Arena and cannot be
allocated by COW metadata, Lifecycle or Reader Table code.

`metadata.InitVolume` clears both OwnerRecord pages, Lifecycle and Reader
Table before publishing the redundant BMDVOL02 descriptors. Descriptor
validation rejects Arena/Lifecycle extents that overlap the OwnerRecord pages
or Reader Table. `metastore.OpenPoolVolume` independently validates the same
slot boundaries before exposing the Volume.

## Runtime wiring

After opening a Pool-backed Volume:

```go
ownerA, ownerB, err := store.OwnerRecordRange()
if err != nil {
    return err
}
records, err := volume.NewSANOwnerRecordStore(volume.SANOwnerRecordStoreConfig{
    Device: store.Device(),
    VolumeID: store.Superblock().VolumeID,
    SlotAOffset: ownerA,
    SlotBOffset: ownerB,
})
if err != nil {
    return err
}
```

`OwnerRecordRange` returns byte offsets relative to the Pool metadata device.
The same offsets are reported by `bm-meta volume-init` and
`bm-meta volume-inspect` as `owner_record_slot_a_offset_bytes` and
`owner_record_slot_b_offset_bytes`. No caller-selected or guessed offsets
are needed.

The two pages contain format version, monotonically increasing record
generation, VolumeID, NodeID, BootID, OwnerEpoch and CRC32C. Updates write the
inactive page and call device Sync before reporting success. Torn writes leave
the previous valid copy available; a failed Sync is ambiguous and must cause
the caller to abort activation. The next Owner reloads both pages and fences
whichever identity is durably present.

## Cross-node correctness

The OwnerRecord pages are a durable identity record, not a distributed lock.
The caller must hold the exclusive sanlock Owner resource for the entire
Load/fence/drain/CAS/RESERVE sequence. sanlock provides cross-node
serialization; SCSI PR provides actual initiator fencing. A process-local
mutex inside the store is not a distributed lock.

## Layout compatibility

Volumes initialized with the earlier bootstrap layout placed the Arena at the
first page of the slot and therefore overlap the newly reserved OwnerRecord
extent. Such descriptors are now rejected by Pool-backed open/slot validation.
Do not attach an old Volume using the new code and do not write OwnerRecord
pages into an existing Arena. Existing test images and disposable Pools must be
reformatted/reinitialized; production data requires an explicit offline
migration procedure before upgrading.

## Qualification boundary

CI verifies layout calculation, initialization clearing, range isolation,
SAN OwnerRecord round trips, checksums, torn writes and ambiguous Sync
outcomes using file-backed devices. It does not prove array cache persistence,
real SAN Flush semantics, sanlock daemon behavior, multipath fencing or
power-loss recovery. Those remain mandatory hardware qualification items.
