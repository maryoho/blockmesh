# P3-3.12.3.4 — SAN OwnerRecord storage (Kubernetes adapter removed)

The earlier Kubernetes Lease-backed OwnerRecord adapter has been removed.
BlockMesh does not require Kubernetes API, etcd, ServiceAccount tokens, RBAC,
or any other orchestration control-plane resource to acquire or recover a SAN
Volume Owner.

## Current responsibility split

- **sanlock Owner resource:** serializes Owner acquisition across hosts.
- **SAN OwnerRecord:** stores the last Owner's VolumeID, NodeID, BootID and
  epoch in two dedicated, checksummed 4 KiB metadata slots on the shared Pool
  metadata device.
- **SCSI Persistent Reservation:** fences the previous initiator with PREEMPT
  AND ABORT and verifies the result through every configured multipath path.
- **Owner I/O barrier:** proves old-owner metadata I/O is quiescent before a
  new Owner identity is published.
- **BMDVOL02 OwnerEpoch:** records the current fencing epoch in the redundant
  Volume Descriptor pair through the AG WAL.

## On-disk OwnerRecord slots

`volume.SANOwnerRecordStore` is a generic block-device adapter. Each Volume
is provisioned with two distinct, 4 KiB-aligned metadata pages. The pages must
be reserved exclusively for OwnerRecord and must not overlap Pool Superblocks,
Volume Descriptors, WAL, bitmap, mapping, Arena, lifecycle, or Reader Table
regions.

Each page contains a format version, monotonically increasing record
generation, VolumeID, NodeID, BootID, OwnerEpoch and CRC32C. A CAS update writes
the inactive slot and flushes it. A torn write leaves the previously valid
slot available. Reads select the valid copy with the highest generation;
equal-generation disagreement or two nonzero invalid copies fail closed.

The slot offsets are explicit constructor inputs because the current BMPOOL02
layout does not yet allocate a dedicated OwnerRecord extent. Production
provisioning must reserve and validate these pages before enabling the
coordinator; do not choose arbitrary offsets or overlap existing metadata.

## Concurrency and safety

`CompareAndSwap` is intentionally not a distributed lock. The caller MUST
hold the exclusive sanlock Owner resource for the Volume for the complete
Load/fence/drain/CAS/RESERVE sequence. The sanlock resource provides
cross-node serialization; dual slots provide durable crash-safe publication.
A process-local mutex only protects concurrent calls through one adapter
instance and is not a substitute for sanlock.

If a write or flush reports an ambiguous error, the caller aborts activation
and releases sanlock if still valid. The next Owner reloads both slots and
fences whichever identity is durably present before publishing its own record.
Never assume a failed WriteAt/Sync means the target did not persist the page.

## Kubernetes integration

Kubernetes and KubeVirt may host BlockMesh processes, but they are optional
deployment environments. They are not part of the Owner correctness protocol.
No Kubernetes-specific code, API calls, ServiceAccount mounts, or RBAC
manifests are required by this package.
