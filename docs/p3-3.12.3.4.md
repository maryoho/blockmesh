# P3-3.12.3.4 — Kubernetes Lease OwnerRecordStore

This phase provides a standard-library-only Kubernetes API adapter for the
`volume.OwnerRecordStore` contract. No client-go dependency is added.

## Responsibility split

- **sanlock Owner resource:** exclusive shared-SAN ownership serialization.
- **Kubernetes Lease:** durable authoritative last-Owner identity record and
  linearizable compare-and-swap publication.
- **SCSI Persistent Reservation:** actual old-initiator fencing with
  PREEMPT AND ABORT and verification across every configured multipath path.
- **Owner I/O barrier:** proves old-owner metadata I/O is quiescent before the
  next owner may publish its identity.

The Kubernetes Lease is deliberately NOT used as a time-based lock. The
adapter does not inspect or rely on `leaseDurationSeconds`, `renewTime`,
`acquireTime`, or expiry to decide that a SAN Owner is dead. Expiration of a
Kubernetes Lease must never substitute for sanlock plus SAN fencing.

## Object layout

Each Volume maps to one deterministic Lease name:

`blockmesh-owner-<full 64 hex chars of SHA-256(VolumeID)>`

The object is in the configured namespace, API group
`coordination.k8s.io/v1`, kind `Lease`. The adapter stores:

| Field | Value |
|---|---|
| `metadata.annotations["blockmesh.io/owner-volume-id"]` | Volume ID |
| `metadata.annotations["blockmesh.io/owner-node-id"]` | Owner Node ID |
| `metadata.annotations["blockmesh.io/owner-boot-id"]` | Owner Boot ID |
| `metadata.annotations["blockmesh.io/owner-epoch"]` | Decimal uint64 epoch |
| `spec.holderIdentity` | `NodeID/BootID` |
| `metadata.resourceVersion` | Kubernetes API CAS token |

The record annotations are validated on every Load. Missing, malformed, or
cross-Volume identity data is an error; it is not treated as an absent record.

## CAS semantics

- Initial publication uses POST. An API 409 maps to
  `volume.ErrOwnerRecordConflict`.
- Update performs GET, validates the complete expected OwnerRecord, retains
  the object's metadata and unknown fields, then PUTs with the observed
  `metadata.resourceVersion`.
- The API server atomically rejects a concurrent update with HTTP 409; this
  also maps to `ErrOwnerRecordConflict`.
- An update without a resourceVersion is rejected locally.
- A missing Lease returns `exists=false` from Load. A malformed existing
  Lease never returns `exists=false`.

The coordinator already holds the distributed sanlock Owner resource while
calling this CAS. A conflict aborts takeover; it is not retried with a guessed
expected value.

## Construction

Inside a Kubernetes Pod, use the projected ServiceAccount identity and API
CA:

```go
records, err := volume.NewInClusterKubernetesOwnerRecordStore()
if err != nil {
    return err
}
ownerCoordinator, err := volume.NewOwnerCoordinator(volume.OwnerCoordinatorConfig{
    Locker:          sanlockLocker,
    ResourceFor:     ownerResourceForVolume,
    Records:         records,
    Fencer:          scsiPRFencer,
    ReadEpoch:       readPoolVolumeOwnerEpoch,
    DrainOldOwner:   drainPreviousOwnerMetadataIO,
})
if err != nil {
    return err
}
```

The in-cluster constructor reads the namespace, token, and CA from the
standard ServiceAccount mount. The token file is re-read for every API request
so projected token rotation is honored. TLS certificate verification is
enabled and pinned to the mounted ServiceAccount CA.

For tests or an externally managed API client, use
`NewKubernetesOwnerRecordStore(KubernetesOwnerRecordStoreConfig{...})`.
A plain HTTP endpoint is accepted only on loopback; production endpoints must
use HTTPS. A custom HTTP client may be injected for tests or controlled
transport configuration.

## RBAC

Apply [owner-record-lease.yaml](../deploy/rbac/owner-record-lease.yaml) and
bind the Role to the BlockMesh ServiceAccount in the same namespace. The
adapter needs only `get`, `create`, and `update` on
`coordination.k8s.io/leases`; it does not need delete, patch, or cluster-wide
permissions. The example manifest assumes namespace
`blockmesh-system` and ServiceAccount `blockmesh`; adjust both to match the
deployment.

## Tests and qualification

Unit tests use an HTTP test server to verify first-record creation, Load,
resourceVersion update, stale expected-record rejection, API 409 conflict,
authorization header, namespace, holderIdentity, malformed annotations, and
refusal of unencrypted non-loopback API endpoints.

These tests validate adapter semantics, not Kubernetes API-server behavior or
HA control-plane availability. Before production rollout, qualify:
- RBAC and projected ServiceAccount token rotation on the target Kubernetes
  version;
- Lease create/update under API-server leader changes and etcd failover;
- API timeout after a successful server-side write (the caller must abort and
  reload the authoritative record on a later attempt; never assume the write
  failed);
- API unavailability during takeover (RW admission remains closed);
- backup/restore and retention of OwnerRecord Leases across Volume lifecycle.

A Lease API timeout after the server committed a PUT is an ambiguous outcome.
The current call returns an error; the OwnerCoordinator releases sanlock if
still held. A later takeover must reload the record and fence whichever
identity is durably recorded before proceeding.
