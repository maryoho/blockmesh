# P4-1.3.5.7 — Single-node RW thin Volume acceptance

This is the first-release hardware acceptance procedure. It is intentionally
single-node and RW-only. It must be run on a disposable test LUN; Pool create
initializes on-disk metadata and is destructive to existing contents.

## Preconditions

- The test LUN is blank, visible to the host, and has a stable WWID.
- `discovery_devices` contains the exact device path used by `pool create`.
- `san.paths` lists every local SCSI PR component path for that LUN. Each path
  must resolve to the same WWID as the configured discovery device.
- The sanlock lockspace and its native Resource Index have already been
  formatted with the matching lockspace offset, Resource Index offset and
  alignment. The daemon never formats the lockspace/RINDEX automatically.
- `node_id`, `boot_id`, sanlock configuration, SCSI PR local keys, owner-key
  resolution, and the old-owner drain helper are configured.
- The BlockMesh kernel target/global queue module is built and loaded;
  `/dev/blockmesh` exists; `bm-metad` is running and its control socket is
  available.
- No foreign SCSI PR registration or reservation exists on the new LUN.

## Create Pool and Volume

Run interactively (the CLI asks you to type the Pool name):

```bash
bmctl pool create pool0 /dev/mapper/mpatha
```

For automation, explicitly acknowledge the destructive initialization:

```bash
bmctl pool create pool0 /dev/mapper/mpatha --yes
```

Verify the dynamically planned geometry and catalog:

```bash
bmctl pool list
bmctl pool info pool0
```

Create a metadata-only logical Volume. The logical size may exceed current
physical DataView capacity; physical blocks are allocated on first write:

```bash
bmctl volume create pool0 vol0 10T
bmctl volume list
```

Record the returned `volume_id`, then activate it RW:

```bash
bmctl volume activate <volume-uuid> rw
```

The response contains the exact device path, normally
`/dev/mapper/bm-<volume-uuid>`. Do not construct a mapper name by hand; use
the `device` value returned by `bm-metad`.

## I/O acceptance

Replace `<device>` with the returned path. Run the following in order:

```bash
# Newly unmapped logical blocks must read as zero.
dd if=<device> of=/tmp/blockmesh-zero.bin bs=4M count=4 iflag=direct status=progress
od -An -tx1 -N64 /tmp/blockmesh-zero.bin

# First-write allocation and overwrite/read verification.
fio --name=bm-first-write --filename=<device> --direct=1 --ioengine=libaio \
  --rw=write --bs=4k --size=1G --iodepth=16 --verify=crc32c --do_verify=1

# Random overwrite and mixed read/write.
fio --name=bm-randrw --filename=<device> --direct=1 --ioengine=libaio \
  --rw=randrw --rwmixread=70 --bs=4k --size=4G --iodepth=32 --runtime=120 \
  --time_based --verify=crc32c --do_verify=1

# Discard must retire old physical blocks without exposing stale data.
blkdiscard <device>
dd if=<device> of=/tmp/blockmesh-after-discard.bin bs=4M count=4 iflag=direct
od -An -tx1 -N64 /tmp/blockmesh-after-discard.bin
```

Acceptance conditions:

1. First reads of never-written logical blocks return zero.
2. First writes allocate physical blocks and complete without I/O errors.
3. FIO verification reports no data mismatch.
4. Repeated overwrites preserve data correctness.
5. Discard completes; reads from discarded logical ranges return zero.
6. Pool/Volume metadata remains readable after the I/O workload.

## Deactivate and daemon restart

```bash
bmctl volume deactivate <volume-uuid>
```

Verify that the Volume target is removed and that no BlockMesh DM target
remains for the Volume. Then restart `bm-metad` using the deployment's
service manager. The daemon must reconcile the kernel queue, fence/remove
stale local BlockMesh DM tables, start the Metadata Service request loop, and
only then expose the lifecycle socket.

Reactivate and verify previously committed data:

```bash
bmctl volume activate <volume-uuid> rw
fio --name=bm-reopen-verify --filename=<device> --direct=1 --ioengine=libaio \
  --rw=read --bs=4k --size=4G --iodepth=16 --verify=crc32c --verify_only
bmctl volume deactivate <volume-uuid>
```

## Results to record

Record the Pool WWID, device type (multipath/direct iSCSI/local), logical
sector size, Metadata/Data geometry, AG count, Volume UUID/size, kernel
version, BlockMesh module build, fio command/output, discard result, daemon
restart result, and all SCSI PR/sanlock logs.

## Explicitly out of scope for this acceptance

- Cross-node concurrent RW or RO.
- Cross-node recovery of an interrupted Pool bootstrap that leaves a foreign
  PR registration. The current implementation fails closed in this case.
- `volume delete`, `pool destroy`, and dynamic RO activation; their
  production lifecycle backends are not yet complete.
- SAN path loss, reservation preemption and host fencing qualification.
  These require dedicated multi-node fault-injection tests.

CI passing is not a substitute for running this procedure on the target
multipath/direct-iSCSI hardware and kernel.
