# P3-3.12.3.5 — Two-node SAN Owner takeover integration tests

This phase exercises two independent OwnerCoordinator instances against one
shared SAN metadata device and one shared distributed-lock test service. The
test path has no Kubernetes API, etcd, ServiceAccount or network control-plane
dependency.

## Scenarios

### 1. Simultaneous two-node acquisition and serialized takeover

Two node coordinators start at the same time for one Volume. The test verifies:

1. The shared sanlock resource admits only one Owner lease at a time.
2. The first coordinator durably publishes OwnerRecord epoch 2 to the shared
   SAN metadata slots.
3. The second coordinator cannot enter takeover while the first lease remains
   held.
4. After the first lease is released (simulated helper/process teardown), the
   second node reads the OwnerRecord from the same SAN device.
5. The second node fences the old NodeID/BootID on every modeled multipath
   path, executes the old-owner I/O barrier, and publishes epoch 3.
6. The maximum observed number of simultaneous Owner leases is exactly one.

The winner is intentionally nondeterministic; both orderings are valid.

### 2. Partial multipath fencing failure

A two-path fencer reports failure on the second path. The test verifies that
the new Owner is not published, the old-owner I/O drain is not called, the
original SAN OwnerRecord remains unchanged, and sanlock is released.

### 3. Ambiguous SAN metadata flush

The simulated SAN device persists the new OwnerRecord page but reports a
flush error. The first coordinator aborts and releases sanlock. The next node
reloads the durable identity from the shared device, fences it, and proceeds
at the next epoch. This prevents treating an ambiguous storage error as proof
that a record write did not commit.

## Test implementation boundary

The tests use a shared in-memory block device as the SAN metadata LUN and an
in-process distributed-lock service as a sanlock simulator. They validate
dual-slot persistence, checksums, CAS ordering, concurrent Owner acquisition,
fencing order, and ambiguous flush recovery. They do NOT prove actual sanlock
daemon behavior, SCSI target semantics, multipath path coverage, host
power-loss behavior, storage-controller cache guarantees, or the DM target's
hardware fail-stop implementation.

## Production qualification matrix

Before enabling RW on a shared SAN, qualify with the actual components:

| Fault / event | Required observation |
|---|---|
| Both nodes request RW simultaneously | At most one sanlock Owner resource holder |
| Owner host power loss | New Owner fences previous PR key on every path before RW |
| One multipath path unavailable | Takeover rejected; old record retained |
| PREEMPT AND ABORT reports success but a path still has old key | Verification fails; no RW admission |
| Old metadata I/O cannot be drained | No new Owner admission |
| SAN metadata WriteAt/Sync returns an ambiguous error | Next Owner reloads both slots and fences the persisted identity |
| sanlock helper exits after admission | Local DM path synchronously fail-stops; no further writes |
| DM suspend or I/O drain fails | Runtime resources remain pinned; operator recovery required |
| Node restarts with same NodeID and BootID | Automatic self-preemption rejected; platform recovery must prove old local path stopped |

Capture sanlock resource state, both OwnerRecord slots and CRC/generation,
PR registrations and reservations from every multipath path, kernel block I/O
traces, DM suspend state, and OwnerEpoch from both Volume Descriptor copies.
Verify the old node cannot complete a SAN write after the new node reaches RW
admission.

A simulator pass is necessary but not sufficient for production. CI does not
run destructive SAN hardware qualification.
