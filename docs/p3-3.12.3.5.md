# P3-3.12.3.5 — Two-node Owner takeover integration tests

This phase adds deterministic, API-backed integration scenarios for the Owner
takeover path. The tests run two independent OwnerCoordinator instances against
one shared Kubernetes Lease API and one shared distributed-lock test service.

## Scenarios

### 1. Simultaneous two-node acquisition and serialized takeover

Two node coordinators start at the same time for one Volume. The test verifies:

1. The shared sanlock resource admits only one Owner lease at a time.
2. The first coordinator publishes OwnerRecord epoch 2.
3. The other coordinator cannot enter takeover while that lease remains held.
4. Once the first node's lease is released (simulated process/helper teardown),
   the second coordinator reads its identity from Kubernetes.
5. The second coordinator fences the old NodeID/BootID on every modeled
   multipath path, runs the old-owner I/O barrier, and publishes epoch 3.
6. The maximum observed number of simultaneous Owner leases is exactly one.

The winner is intentionally nondeterministic; both orderings are valid.

### 2. Partial multipath fencing failure

A two-path fencer reports failure on the second path. The test verifies that:

- the new Owner is not published;
- old-owner I/O drain is not called;
- the original Kubernetes OwnerRecord remains unchanged; and
- the sanlock resource is released after the failed attempt.

### 3. Kubernetes API unavailable

The Lease API returns HTTP 503. The coordinator must fail acquisition and
release sanlock. It cannot enable a read-write runtime without a durable
OwnerRecord.

### 4. Ambiguous create outcome

The API server commits the initial OwnerRecord but delays its response beyond
the client's HTTP timeout. The first coordinator therefore receives an
error and releases sanlock, while the committed record remains durable. A
subsequent node reloads that record, fences the recorded first identity, and
takes over at the next epoch. The test explicitly guards against assuming
that a timed-out write did not commit.

## Test implementation boundary

The tests use `httptest.Server` as a Kubernetes Lease API contract simulator
and a shared in-process lock implementation as a two-node sanlock simulator.
They exercise real HTTP serialization, authentication headers,
resourceVersion updates, coordinator ordering, and fail-closed behavior.
They do NOT prove Kubernetes API-server/etcd failover, sanlock daemon behavior,
SCSI target semantics, multipath path coverage, host power-loss behavior, or
the DM target's hardware fail-stop implementation.

## Production qualification matrix

Before enabling RW on a shared SAN, run the same scenarios in a disposable
two-node environment with the actual components:

| Fault / event | Required observation |
|---|---|
| Both nodes request RW simultaneously | At most one sanlock Owner resource holder |
| Owner host power loss | New Owner fences previous PR key on every path before RW |
| One multipath path unavailable | Takeover rejected; old record retained |
| PREEMPT AND ABORT reports success but a path still has old key | Verification fails; no RW admission |
| Old metadata I/O cannot be drained | No OwnerRecord publication / no RW admission |
| Kubernetes API unavailable | No new Owner admission |
| API write times out after server commit | Next attempt reloads and fences committed identity |
| sanlock helper exits after admission | Local DM path synchronously fail-stops; no further writes |
| DM suspend or I/O drain fails | Runtime resources remain pinned; operator recovery required |
| Node restarts with same NodeID and BootID | Automatic self-preemption rejected; platform recovery must prove old local path stopped |

For each run, capture sanlock resource state, Kubernetes Lease
resourceVersion and annotations, PR registrations/keys from every multipath
path, kernel block I/O traces, DM suspend state, and OwnerEpoch from both
Volume Descriptor copies. Verify the old node cannot complete a SAN write
after the new node reaches RW admission.

A test simulator pass is necessary but not sufficient for production. Do not
interpret these tests as SAN hardware qualification.
