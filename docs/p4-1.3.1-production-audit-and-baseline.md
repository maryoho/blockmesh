# P4-1.3.1 — Production Integration Audit and Performance Baseline

## Baseline findings

The repository contains the Linux DM target, node-wide `/dev/blockmesh`, Go SPSC ring consumer, Pool Runtime Processor, BMPOOL03 metadata/allocator components, and Owner/Fencing primitives. Kernel compilation and Go unit tests do not prove a production end-to-end data path.

Implementation gates identified by source review:

1. `PoolRuntimeProcessor` accepts `PoolMutationExecutor`, but there is no BMPOOL03 implementation binding request processing to the live Owner lease, Dynamic Volume Descriptor, Dynamic WAL, persistent B+Tree, `PoolAllocator`, and DataView.
2. `VolumeRuntimeManager` and `PoolVolumeRuntimeBackend` are currently BMPOOL02-oriented (`format.Superblock` and `PoolDescriptor`). BMPOOL03 needs a first-class runtime activation path; it must not be opened through the BMPOOL02 decoder.
3. DM write BIOs currently request `ALLOCATE_ZERO_PUBLISH`; the allocator's one-time allocation rejects already-mapped logical blocks. Repeated writes, overwrite/COW semantics and partial-block writes must be implemented and tested before normal RW use.
4. Completion currently accepts one contiguous mapping per BIO. Fragmented mappings, BIO splitting/reissue, `max_sectors_kb`, `max_io_len`, discard, write-zeroes and flush need explicit semantics and kernel tests.
5. The service has a queue Run loop, but needs production daemon lifecycle: startup/config validation, runtime activation ordering, bounded shutdown, health, metrics and restart behavior.
6. CI compiles the module and tests Go code; it does not load the module, create a DM target, execute real BIOs, test multipath or measure SAN latency.

These are implementation gates, not documentation-only caveats. Unsupported mutation modes must remain fail-closed.

## Work delivered

- `BenchmarkQueueMemoryDrain`: CPU-only SPSC request-consumer/completion-producer benchmark at 16, 64, 256 and 1024 requests per drain.
- `BenchmarkLookupContiguous`: cached contiguous mapping lookup at 1, 4, 16, 64 and 256 blocks.
- Both benchmarks report allocations and intentionally exclude SAN latency.

Run on the target host:

```bash
go test ./internal/metaservice -run '^$' -bench 'Benchmark(QueueMemoryDrain|LookupContiguous)$' -benchmem -count=5
go test ./internal/metaservice -run '^$' -bench 'Benchmark(QueueMemoryDrain|LookupContiguous)$' -benchmem -count=5 > p4-1.3-baseline.txt
```

Record CPU, kernel/Go versions, NUMA placement, CPU governor, ring order, concurrency and device type. Compare only runs from the same host and setup.

## Required metrics

Collect BIO IOPS/throughput; p50/p95/p99 latency; DM map-to-request, queue wait, service processing, WAL commit, zeroing, completion-to-submit and backing-device latency; ring occupancy/high-watermark; requeue/error counts; per-AG lock wait; checkpoint duration; CPU and allocations per request; memory per queue; recovery time.

Do not tune ring order or batch size from CPU-only benchmarks. The production path is constrained by metadata transaction latency, data zeroing, SAN flush/FUA semantics and physical I/O. Measure each separately.

## Safety invariants

- No linear-I/O fallback when service or metadata is unavailable.
- No Mapping publication before zeroing and its durability barrier complete.
- No write admission without a verified Owner lease and matching durable OwnerEpoch.
- No physical block reuse until reader-generation and fencing proofs permit reclamation.
- CI compilation and in-memory benchmarks are not production qualification.
