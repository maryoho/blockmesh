# BlockMesh P4-1.3.4 基本功能测试操作指南

> 文档状态：基于 `main` 分支当前代码编写（2026-11-11）。
>
> **重要结论：当前可以执行 Go 功能测试、构建/加载 Linux 5.15 DM 模块、验证 DM Target 注册与安全门状态，也可以在专用空 LUN 上验证 Bootstrap 格式化和只读检查。但目前还不能通过一套完整的命令行流程完成真实的 DM → Metadata Service → BMPOOL03 → Data LUN 读写闭环。请不要把本指南中的编译/控制面检查当作真实 I/O 验收。**

## 1. 当前可测试范围

| 功能 | 当前状态 | 建议测试方式 |
|---|---|---|
| Go 代码、Allocator、WAL、B+Tree、幂等、恢复 | 已有自动化测试 | `go test ./...` |
| Go 并发安全 | 已有 Race 测试 | `go test -race ./...` |
| Linux 5.15 DM 模块编译 | CI 已通过 | 在目标主机使用其实际内核 headers 重编 |
| DM Target / `/dev/blockmesh` 注册 | 可现场验证 | 加载模块、检查 dmsetup targets 和字符设备 |
| DM Target 创建/销毁、默认 fenced 状态 | 可现场验证 | 创建一个不承载业务的测试 DM 设备并检查 status |
| BMPOOL03 Bootstrap 格式化/检查 | 有 bmctl 命令 | 仅对专用、确认无数据的测试 LUN 执行 |
| BMPOOL03 首次 DataView 初始化 | **命令行初始化流程尚不完整** | 当前不能按完整运维流程完成 |
| Metadata Service 作为独立守护进程运行 | **尚无 cmd 入口 / systemd unit** | 只能通过 Go 包和测试覆盖 |
| 真实 DM BIO 经 Service 分配、清零、映射并读写 | **尚未形成可操作的端到端部署闭环** | 暂不运行 fio、mkfs 或业务 I/O |
| CANCEL / 重试 / 服务崩溃后的真实 SAN 故障注入 | 尚未完成硬件验收 | 后续 P4-1.3.4.5 专项验收 |
| 双节点 Owner takeover、SCSI PR all-path fencing | 需要真实 SAN 与可信 Owner helper | 单独做双节点故障注入 |

### 1.1 当前阻塞端到端测试的两个缺口

1. **Metadata Service 没有可执行入口。** 当前有 `internal/metaservice.Service`、`DynamicPoolRuntimeProcessor` 和 BMPOOL03 Runtime 组件，但 `cmd/` 下还没有负责构造生产依赖、激活 Volume 并运行 Service 的 daemon 命令，也没有对应 systemd unit。仅有 `/dev/blockmesh` 并不代表有用户态进程消费 Request Ring。
2. **首次 DataView 分配缺少 bmctl 引导命令。** `bmctl pool format` 创建 Bootstrap，并按容量规划初始 Metadata 区和 Free 区；初始 Extent Map 中没有 Data Extent。可是 `dynamic-format` 要求 DataView 已经存在，而当前 `data-expand` 又要求已有 BMPOOL03 Superblock。也就是说，首次分配 Data Extent 的 CLI 引导步骤还没有闭环。

因此当前不能声称“已经可以用 fio 验证真实精简置备读写”。后续应先补齐 Data Extent bootstrap 命令和 Metadata Service daemon/runtime 配置入口，再开展真实 BIO 测试。

## 2. 测试环境与安全要求

建议先使用单台 Linux 5.15 测试主机、一个专用测试 LUN、一个测试 Volume。优先使用独立测试 LUN；如果使用 multipath，必须将 multipath mapper 作为唯一设备入口。

必备工具：

- Go（版本以仓库 `go.mod` 和 CI 配置为准）
- 与当前运行内核完全匹配的 kernel-devel / kernel headers
- `make`、`gcc`、`dmsetup`、`dm_mod`
- `multipath-tools`（仅 multipath 场景）
- `sanlock` 及项目部署所需的可信 Owner lease helper（执行 bmctl 写操作时）
- `fio`、`dmesg`、`lsblk`、`blockdev`（后续 I/O 验收阶段使用）

先记录环境：

```bash
uname -a
uname -r
go version
dmsetup version
lsblk -o NAME,KNAME,TYPE,SIZE,RO,WWN,FSTYPE,MOUNTPOINTS
multipath -ll
```

确定唯一测试设备路径，例如：

```bash
TEST_LUN=/dev/mapper/mpathX
readlink -f "$TEST_LUN"
blockdev --getsize64 "$TEST_LUN"
blockdev --getss "$TEST_LUN"
lsblk -f "$TEST_LUN"
```

**禁止事项：**

- 不要把有业务数据、已挂载文件系统、LVM PV、生产 SAN LUN 用作格式化测试设备。
- 同一个共享 LUN 在格式化、恢复、扩容期间必须确保其他节点没有访问或写入。
- 不要在两台主机同时执行 Pool 格式化、恢复或扩容。
- 不要手动向 DM Target 发送 `owner_enable` 来绕过 OwnerCoordinator / SCSI PR fencing。
- 不要在没有 Metadata Service 的情况下对测试 DM 设备运行 `fio`、`dd`、`mkfs` 或文件系统挂载。
- `bm-meta format` 是旧 BMPOOL02 格式工具，不要将它与 BMPOOL03 的 `bmctl pool format` / `dynamic-format` 混用。

## 3. 获取代码与运行 Go 测试

```bash
git clone git@github.com:maryoho/blockmesh.git
cd blockmesh
git checkout main
git pull --ff-only
git rev-parse HEAD
```

执行完整测试：

```bash
go test ./...
go test -race ./...
go vet ./...
```

也可以先单独测试本阶段关键包：

```bash
go test ./internal/uapi ./internal/metaservice ./internal/dynamicruntime
go test -race ./internal/metaservice ./internal/dynamicruntime
```

构建当前 CLI：

```bash
mkdir -p bin
go build -o bin/bmctl ./cmd/bmctl
go build -o bin/bm-meta ./cmd/bm-meta
go build -o bin/bm-lock-helper ./cmd/bm-lock-helper
```

注意：当前没有 `bm-metad` / `blockmesh-metadata-service` 可执行程序。不要自行假设 `internal/metaservice.Service` 可以通过上述 CLI 命令启动。

## 4. 构建 Linux 5.15 内核模块

在准备加载模块的目标主机上执行。必须使用目标主机当前运行内核的 headers：

```bash
KDIR="/lib/modules/$(uname -r)/build"
test -e "$KDIR/Makefile" || {
    echo "找不到当前内核 headers: $KDIR"
    exit 1
}

make -C kernel/dm-blockmesh KDIR="$KDIR"
```

检查构建产物：

```bash
file kernel/dm-blockmesh/dm-blockmesh.ko
modinfo kernel/dm-blockmesh/dm-blockmesh.ko
```

如果目标系统是厂商定制内核（例如 RHEL/CentOS 兼容内核），必须使用该内核对应的 devel 包构建。GitHub Actions 的通用 Linux 5.15 编译成功不能代替厂商内核 ABI 兼容性验证。

## 5. 加载模块并检查内核接口

先确认没有同名模块或旧测试实例：

```bash
lsmod | grep -E 'dm_blockmesh|dm-blockmesh' || true
test ! -e /dev/blockmesh || ls -l /dev/blockmesh
```

加载：

```bash
modprobe dm_mod
insmod kernel/dm-blockmesh/dm-blockmesh.ko
```

检查：

```bash
ls -l /dev/blockmesh
stat /dev/blockmesh
dmsetup targets | grep -w blockmesh
dmesg | tail -n 100
```

预期：

- 出现字符设备 `/dev/blockmesh`，设备权限由内核 misc device 设置为 `0600`。
- `dmsetup targets` 中出现 `blockmesh`。
- 内核日志没有模块初始化失败、ABI 结构断言失败或 DM Target 注册错误。

如果字符设备不存在，先检查模块加载错误和 udev 状态；不要继续创建 DM Target。

## 6. 创建一个默认 fenced 的 DM Target（只验证控制面）

本步骤只检查 Target 构造、队列注册、状态查询和销毁，不执行数据 I/O。

选择一个不会被其他程序使用的测试设备映射名和三个 32 位十六进制 UUID。UUID 必须各自独立且符合实际 Volume / Node / Boot 身份规划：

```bash
VOL_UUID=00112233445566778899aabbccddeeff
NODE_UUID=102132435465768798a9bacbdcedfe0f
BOOT_UUID=ffeeddccbbaa99887766554433221100
```

确认底层测试设备容量，并选取不超过设备容量的目标长度。以下示例把目标长度设为 1 GiB：

```bash
SECTORS=$((1024 * 1024 * 1024 / 512))
dmsetup create bm-control-test --table \
  "0 $SECTORS blockmesh $TEST_LUN 0 $VOL_UUID $NODE_UUID $BOOT_UUID"
```

检查：

```bash
dmsetup table bm-control-test
dmsetup status bm-control-test
dmsetup info -c bm-control-test
```

刚创建时应看到类似状态字段：

```text
gate=0 fenced=1 inflight=0 queue=<非零队列ID>
```

其中 instance、queue cookie 等字段由内核随机生成，以实际输出为准。默认 gate 关闭且 fenced 是预期安全状态，不是故障。

删除测试 Target：

```bash
dmsetup remove bm-control-test
```

如果设备忙，不要使用强制删除绕过未完成 BIO；先确认没有 I/O 和队列引用，再正常删除。

## 7. BMPOOL03 Bootstrap 命令的可用范围

### 7.1 bmctl 配置文件

`bmctl` 默认读取：

```text
/etc/blockmesh/pools/<pool-id>.json
```

配置字段来自 `cmd/bmctl/main.go` 的 `poolConfig`。最小结构示例（请替换为真实环境参数）：

```json
{
  "device_path": "/dev/mapper/mpathX",
  "volume_slots": 16,
  "logical_sector_bytes": 512,
  "lockspace": "blockmesh-test",
  "lock_device": "/dev/mapper/sanlock-lockspace",
  "lock_offset_bytes": 1048576,
  "sanlock_binary": "/usr/sbin/sanlock",
  "lock_helper_binary": "/usr/local/sbin/bm-lock-helper",
  "ready_dir": "/run/blockmesh/sanlock",
  "owner_lease_helper": "/usr/local/sbin/blockmesh-owner-lease-helper",
  "ag_size_bytes": 1099511627776,
  "ag_capacity": 8,
  "wal_segment_bytes": 4194304,
  "mapping_bytes": 8388608,
  "lifecycle_pages": 8
}
```

说明：

- `device_path` 必须是同一父 LUN 的唯一稳定设备路径；multipath 场景使用 multipath mapper，不要混用 mapper 与 component path。
- `lockspace`、`lock_device`、`lock_offset_bytes` 必须对应已经正确配置的 sanlock 资源，且不能与其他 Pool / 服务冲突。
- `owner_lease_helper` 必须是真正执行 Owner 获取、旧 Owner all-path SCSI PR fencing、reservation 验证、OwnerRecord CAS 和 I/O drain 的 helper。不能用只打印固定 epoch 的脚本代替。
- `logical_sector_bytes` 可省略，由设备自动检测；如果指定，必须与设备一致。
- 以上配置仅展示字段格式，不代表这些路径、锁参数或 helper 已在你的环境中存在。

保护配置权限：

```bash
install -d -m 0750 /etc/blockmesh/pools
chmod 0600 /etc/blockmesh/pools/test-pool.json
```

### 7.2 当前可执行的 Bootstrap 检查

**仅在专用、全空测试 LUN 上执行一次：**

```bash
bin/bmctl pool format --pool test-pool
```

该命令要求配置中的 sanlock 锁可用，会建立 Bootstrap 记录和初始 Metadata / Free extent 规划。它是破坏性初始化，不要对已有 Pool 重复执行。

只读查看 Bootstrap：

```bash
bin/bmctl pool metadata-expand-status --pool test-pool
```

输出中的 `pool_uuid`、`generation`、`device_bytes`、`metadata_bytes`、`free_bytes`、`data_bytes` 可用于核对 Bootstrap 状态。首次格式化后当前规划应有 Metadata 和 Free 空间；此时 DataBytes 可能为 0。

### 7.3 当前不要继续执行的命令

虽然 CLI 已列出以下命令，但首次初始化路径还未闭环：

```bash
bin/bmctl pool dynamic-format --pool test-pool --confirm-format
bin/bmctl pool dynamic-status --pool test-pool
bin/bmctl pool dynamic-recover --pool test-pool
bin/bmctl pool data-expand --pool test-pool
bin/bmctl pool metadata-expand --pool test-pool
```

原因：

- `dynamic-format` 明确要求 DataView 已经有容量。
- 当前 Bootstrap 初始规划没有分配 Data Extent 的命令。
- `data-expand` 需要先打开已有 BMPOOL03 Superblock。
- `metadata-expand` 同样要求 DataView 和已有 BMPOOL03 Superblock，并要求 metadata usage telemetry 文件。

因此这些命令不是首次初始化的替代步骤。不要通过手工修改 Extent Map、Superblock 或直接写 LUN 来绕过此限制。

## 8. 当前阶段的测试记录模板

每次测试至少保存：

```bash
date -Is
uname -a
git rev-parse HEAD
go version
dmsetup targets
dmsetup status
ls -l /dev/blockmesh
lsblk -o NAME,KNAME,TYPE,SIZE,RO,WWN,FSTYPE,MOUNTPOINTS
multipath -ll
dmesg --ctime | tail -n 300
```

记录以下字段：

| 字段 | 记录内容 |
|---|---|
| Git commit | 实际测试的 commit SHA |
| Kernel | `uname -r` 和发行版 |
| Device | 测试 LUN 路径、WWID、容量、逻辑扇区大小 |
| Module | 模块文件、modinfo、加载结果 |
| DM Target | table、status、创建/销毁结果 |
| Pool | Pool UUID、Bootstrap generation、extent 状态 |
| Test result | 命令、退出码、日志和异常 |

## 9. 何时可以开始真实 fio / 数据读写测试

必须同时满足以下条件后，才进入真实 BIO 测试：

- [ ] 有可重复的首次 Data Extent 初始化命令，并能从 Bootstrap 创建 DataView。
- [ ] BMPOOL03 `dynamic-format`、`dynamic-status`、`dynamic-recover` 在专用 LUN 上通过。
- [ ] 有可执行的 Metadata Service daemon，能构造真实 `DynamicVolumeRuntimeManager`、Owner / fencing / WAL / allocator 依赖。
- [ ] Service 能打开 `/dev/blockmesh`、attach queue、消费 Request Ring 并发布 Completion。
- [ ] 通过受控 RW Owner 激活 DM Gate，而不是手工绕过 fencing。
- [ ] 首次写入验证完整 4MiB 清零、数据写入、Mapping 持久化、读取校验。
- [ ] 重复写入验证 COW 和旧块 Retire；Discard 不提前复用物理块。
- [ ] Flush / FUA、跨 4MiB 边界 I/O、Queue 满、Service 重启和 WAL 恢复通过。
- [ ] 至少完成单节点故障注入；双节点场景另行验证 sanlock、SCSI PR 和所有路径 fencing。

推荐的后续验收顺序：

1. **P4-1.3.4.5 前置工作：** 补齐 Data Extent bootstrap CLI 和 Metadata Service daemon 启动入口。
2. 单机、单 Pool、单 Volume、RW 模式的 4KiB / 4MiB read-write-verify。
3. 4MiB 边界跨块 I/O、部分块 COW、Discard、Flush。
4. Service kill/restart、Request timeout/cancel、提交前后故障注入。
5. 多队列、多 Volume 和压力测试。
6. 双节点 SAN fencing、Owner takeover、路径故障和性能验收。

**生产准入原则：** Go 测试、内核编译、DM Target 创建成功，只能证明对应的软件层和控制面检查通过；只有真实 SAN 上的端到端数据一致性、故障恢复和 fencing 验收全部完成，才可以考虑承载生产数据。
