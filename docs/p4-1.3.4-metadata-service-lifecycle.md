# P4-1.3.4 — Metadata Service Production Lifecycle

## Goal

Make the Metadata Service a recoverable, observable, long-running Linux userspace service. This phase does not change the BMPOOL03 on-disk format, the Kernel Request/Completion Ring ABI, or the existing COW/WAL transaction semantics. It remains independent of Kubernetes.

The acceptance invariant is stronger than process availability: after any service crash/restart, no already-committed metadata mutation may execute twice, no stale Queue Generation may publish a Completion, and every in-flight kernel BIO must either complete exactly once or fail within a bounded recovery window.

## Existing baseline

- `internal/metaservice.Device` opens `/dev/blockmesh`, discovers queues, mmaps each queue, drains requests and kicks completions.
- `QueueMemory.Drain` reserves Completion Ring capacity before invoking the Processor and publishes Completion before advancing Request head.
- `uapi.QueueManager.OpenService/CloseService` changes Queue Generation on service attach/detach.
- `DynamicPoolRuntimeProcessor` resolves the active BMPOOL03 runtime and Owner/Reader epoch before dispatching lookup, allocate-zero-publish, discard and flush.
- Allocation and discard use persistent idempotency records in the BMPOOL03 transaction path. The request fingerprint intentionally excludes transport RequestID and Queue Generation so a retry can replay after service restart or Owner takeover.

## Work breakdown

### P4-1.3.4.1 — Service lifecycle state machine and singleton ownership

Implement an explicit service state machine:

`Created -> Opening -> Recovering -> Ready -> Draining -> Closed`

Any unrecoverable device/ABI/ring error transitions to `Failed`. No queue is serviced before ABI validation, device setup, queue reconciliation and runtime recovery complete. Only one process may own the service device; use a process lock (flock) on a dedicated runtime lock file, not an in-memory singleton. Lock ownership is not a SAN Owner lease and must never be used as fencing evidence.

Acceptance:
- duplicate daemon start fails without disturbing the active daemon;
- readiness is false until every required startup check succeeds;
- partial startup failure unmaps all regions, closes descriptors and releases the process lock;
- state transitions are race-tested.

### P4-1.3.4.2 — Queue Generation reconciliation and stale queue cleanup

Treat `(QueueID, QueueGeneration)` as the identity of a mapped queue, not QueueID alone. On every discovery/reconciliation:
- a missing QueueID is unmapped;
- a changed Generation invalidates and unmaps the old mapping before setting up the new generation;
- a newly discovered QueueID is set up and validated;
- no request or Completion from an old generation is allowed to be published;
- queue removal during scan/kick is handled as an expected race, while malformed ABI or memory layout remains fatal.

A service process restart must discover only the kernel's current generations. Generation mismatch is not repaired by editing userspace memory.

Acceptance:
- same QueueID with incremented Generation replaces the mapping;
- queue destroy/recreate during scan does not panic or leak mmap regions;
- stale Completion and stale Request are rejected;
- repeated attach/detach leaves no mapped regions or file descriptors behind.

### P4-1.3.4.3 — Request deadline, cancellation and idempotent retry

Add bounded per-request execution deadlines and classify outcomes:
- definitely-not-started / retryable;
- committed and replayable;
- outcome-unknown (must poison and drain the affected Volume runtime before reopening).

Do not blindly retry an allocation/discard after timeout. A retry must reuse the same durable idempotency key and identical operation fingerprint. A timeout after a transaction may have committed is resolved by looking up the persistent idempotency record after runtime recovery; it must never allocate a second physical extent.

Acceptance:
- cancellation before transaction start performs no mutation;
- timeout during a transaction cannot produce a second allocation on retry;
- idempotency-key/fingerprint conflict fails closed;
- ambiguous commit poisons the runtime and prevents further mutations until recovery.

### P4-1.3.4.4 — Lost Completion recovery

Close the crash window between metadata commit and Completion publication. Recovery must distinguish:
1. request not consumed;
2. request consumed but transaction not committed;
3. transaction committed but Completion not published;
4. Completion published but Request head not advanced.

Use the persistent idempotency record as the authoritative mutation outcome. The transport ring is not a durable transaction log. A restart may invalidate the old queue generation and fail the old BIO; a caller retry with the same idempotency identity must replay the committed result. Never synthesize success solely from an old shared-memory Completion slot.

Acceptance:
- kill the service at each of the four boundaries;
- after restart, committed operations replay their original mapping;
- no duplicate physical allocation, duplicate discard or stale Completion;
- every outstanding BIO reaches a bounded terminal status.

### P4-1.3.4.5 — Multi-Pool / Multi-Volume scheduler

Introduce bounded scheduling across queues and Volumes without violating per-Volume mutation serialization or AG transaction locks. Lookup may use independent read concurrency; mutations remain serialized at the existing per-Volume mutation boundary and distributed AG lock. Apply queue-level fairness and backpressure so a busy Volume cannot starve another Volume. Keep queue memory ownership and Completion reservation local to the originating queue.

Acceptance:
- multiple Volumes progress concurrently;
- a hot Volume cannot starve a quiet Volume;
- per-Volume mutation order and OwnerEpoch admission remain correct;
- bounded worker count and bounded pending work under ring saturation.

### P4-1.3.4.6 — Graceful shutdown and Runtime Drain

On SIGTERM/SIGINT:
1. mark service unready and stop discovering/accepting new work;
2. stop dequeuing new requests while preserving already-published ring state;
3. allow in-flight Processor calls to finish within a configured drain deadline;
4. flush DataView and MetadataView for completed mutations;
5. fence/stop DM admission for Volumes whose requests cannot drain safely;
6. invalidate/close queue mappings and device descriptors;
7. release singleton lock only after cleanup.

If the deadline expires, do not claim successful completion for ambiguous mutations. Fail closed and rely on the persistent idempotency recovery path after restart.

Acceptance:
- clean shutdown with empty queues;
- shutdown under load with bounded drain;
- forced termination during mutation recovers without duplicate allocation;
- repeated start/stop does not leak fd, mmap or goroutines.

### P4-1.3.4.7 — Health, metrics, diagnostics and service packaging

Expose a local Unix control/health endpoint and Prometheus-compatible metrics without adding a network listener by default. Required signals:
- service state, uptime, last successful queue scan, device/ABI identity;
- queue count, Queue Generation, request/completion occupancy and high-water marks;
- request counts/latency by operation and result code;
- timeout, retry, stale-generation, malformed-ring and processor failure counters;
- per-Pool/Volume active runtime, mode, OwnerEpoch/ReaderEpoch and drain state (never expose secrets);
- mmap/fd/worker counts and last fatal error.

Provide systemd unit, hardened runtime directory/permissions, restart policy, startup timeout and shutdown timeout. systemd restart is process supervision only; it does not replace BMPOOL03 recovery or SAN fencing.

Acceptance:
- metrics are scrapeable and stable under concurrent load;
- health is not Ready during recovery/drain/failure;
- systemd restart recovers service without reformatting or changing Pool metadata;
- logs include RequestID, QueueID, QueueGeneration, Pool/Volume identity and result code.

## Global invariants

1. The BMPOOL03 disk format and Kernel UAPI remain backward compatible in this phase.
2. A process lock is local daemon exclusivity only; SAN Owner Lease, SCSI PR and OwnerEpoch remain the only write-authority/fencing chain.
3. Request/Completion rings are volatile transport, not durable transaction state.
4. Persistent idempotency records decide whether a mutation already committed.
5. Queue Generation gates transport validity; OwnerEpoch/ReaderEpoch gates storage authority/visibility. They are independent and both must be checked.
6. Never retry an ambiguous mutation with a new idempotency key.
7. Never free Data Retire entries based only on daemon liveness or heartbeat timeout.
8. All code changes require Go tests, `go test -race ./...`, `go vet ./...`, benchmark smoke, and Linux 5.15 kernel module build. Hardware/SAN acceptance is tracked separately and must not be claimed from CI alone.

## Implementation order

Implement and test 4.1 and 4.2 first, then 4.3 and 4.4 (the crash/idempotency safety core), then 4.5, 4.6 and 4.7. Do not add scheduler concurrency before queue generation and lost-completion semantics are closed.
