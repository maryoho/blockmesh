# P3-3.12.3.10 — Unified Owner activation state machine

This phase makes the Pool RW activation path an explicit monotonic state
machine. The runtime cannot admit DM requests by merely possessing a sanlock
lease: it must hold the complete Owner proof, recover WAL, open fixed-LBA
metadata, publish the matching BMDVOL02 OwnerEpoch, start recovery supervision,
and only then cross the request-admission boundary.

## State model

`metastore.OwnerRuntimeState` is tracked atomically per runtime:

| State | Meaning |
|---|---|
| `created` | No activation resources have been established |
| `device-ready` | Metadata block device is open |
| `owner-lease-ready` | Exclusive sanlock Owner Lease and complete Owner proof acquired |
| `wal-recovered` | Volume AG WAL replay completed under cluster-safe coordination |
| `metadata-ready` | Pool Volume Store, Reader Table and PersistentArena opened |
| `owner-epoch-published` | BMDVOL02 OwnerEpoch durably advanced to this lease epoch |
| `reader-joined` | RO Reader Session registered and heartbeat started |
| `recovery-ready` | Reader recovery supervisor is running |
| `requests-admitted` | DM request admission hook completed successfully |
| `owner-lease-lost` | Owner sanlock lease monitor reported loss; terminal for this activation |
| `stopping` | Request admission is being closed and resources drained |
| `stopped` | Resources released after drain |
| `failed` | Activation failed before cleanup |

Allowed RW path:

`created -> device-ready -> owner-lease-ready -> wal-recovered -> metadata-ready -> owner-epoch-published -> recovery-ready -> requests-admitted`

Allowed RO path:

`created -> device-ready -> metadata-ready -> reader-joined -> recovery-ready -> requests-admitted`

Any live RW state from `owner-lease-ready` onward may transition to
`owner-lease-lost`. No transition from lease-lost, stopping, stopped or failed
can re-enter request admission. Illegal or skipped transitions return
`ErrOwnerStateTransition`.

## Owner proof at the Pool boundary

The Pool backend no longer accepts an arbitrary lease with only a nonzero
Epoch. Before returning an RW Owner Lease, the provider must expose:

- the durable `OwnerRecord` (VolumeID, NodeID, BootID, Epoch);
- `ReservationVerified() == true`, which is set only after the concrete
  SCSI PR adapter has verified the expected holder and reservation type on
  every configured multipath component path;
- a synchronously queryable sanlock lease health check plus an asynchronous loss channel.

The Pool backend checks that all identity fields match the requested runtime
spec and that OwnerRecord.Epoch equals the lease epoch. Invalid proof causes
the lease to be closed and RW activation to fail. The standard
`PoolOwnerCoordinator` returns this proof only after its ordered sequence:
prepare new path keys -> fence/drain old Owner -> CAS OwnerRecord -> RESERVE
and all-path reservation verification.

## Admission sequence

1. Open the metadata device.
2. For RW, acquire the attested Owner Lease and immediately start lease-loss
   monitoring.
3. Replay the Volume AG WAL.
4. Open and validate the Pool Volume Store, Reader Table and PersistentArena.
5. For RW, publish the exact Owner Lease epoch into BMDVOL02 using the
   cluster-safe WAL committer. A stale or failed epoch publication blocks
   admission.
6. For RO, join the durable Reader Session instead.
7. Start the Reader Recovery Supervisor.
8. Recheck Owner Lease health and transition to `recovery-ready`.
9. Recheck sanlock lease validity synchronously.
10. Invoke `EnableRequestsGuarded`; the platform must call the supplied Owner health guard while holding the DM admission serialization lock immediately before making the queue live. A failed guard must leave admission closed.
11. Transition to `requests-admitted` only after the guarded hook returns success.

If admission partially succeeds and then returns an error, the full teardown
path is used: stop requests, stop recovery, drain metadata I/O, close reader
session/metadata, release Owner Lease and close the device.

## Owner Lease loss

The lease-loss watcher and synchronous health checks share an idempotent fail-stop path. Health is checked after WAL replay, before/after OwnerEpoch publication, before recovery readiness, and inside the final DM admission gate. The lease-loss watcher atomically marks the runtime as
`owner-lease-lost`, makes it disappear from `ActiveVolumes()`, and invokes
the backend's synchronous fail-stop handler. The Pool handler performs the
platform fail-stop callback, request stop and metadata I/O drain. If any part
of fail-stop fails, the runtime retains its metadata device and lease resources
for operator recovery; normal cleanup must not falsely release a possibly
active data path.

`RuntimeState(volumeID)` exposes the current state for diagnostics.
`ActiveVolumes()` now reports only runtimes whose state is exactly
`requests-admitted` and whose Owner Lease has not been lost.

## Tests

- RW and RO legal transition sequences.
- Illegal skipped transitions and attempts to re-enter admission after lease
  loss or stop.
- Runtime activation reaches `requests-admitted` only after all prerequisites.
- Lease loss changes the runtime state and removes it from active volumes.
- Pool backend rejects missing, mismatched or unverified OwnerRecord/PR proof and leases without synchronous health.
- A sanlock lease lost during WAL replay is caught synchronously before metadata open or OwnerEpoch publication.
- The final guarded admission hook rejects a lease that becomes invalid immediately before queue enable.
- Existing failure-injection tests continue to cover WAL, drain, request
  admission, lease loss and cleanup failures.

CI tests exercise in-process adapters. Real SAN PR semantics, sanlock helper
failure, kernel DM fail-stop, and actual I/O admission remain subject to
two-node hardware qualification.
