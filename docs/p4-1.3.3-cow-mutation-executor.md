# P4-1.3.3 — BMPOOL03 COW Mutation Executor

## Request path

`DynamicPoolRuntimeProcessor` handles `OpAllocateZeroPublish` after `DynamicVolumeRuntimeManager.ResolveRequest` has verified the active runtime identity and OwnerEpoch. The executor then requires a live RW Owner lease, the BMPOOL03 `PoolAllocator`, and the persistent B+Tree.

The mutation path is:

1. Serialize mutations per Volume, revalidate that the exact Runtime instance is still active/unpoisoned, then validate the RW mode, OwnerEpoch and live Owner lease.
2. Derive a stable SHA-256 fingerprint from Volume UUID, operation, logical start and block count. Transport request ID, queue generation and the current Owner identity/epoch are excluded so a retry after Owner takeover can replay the same durable operation.
3. Call `PoolAllocator.AllocateZeroPublishTxn`. It serializes on the distributed AG lock, checks the idempotency index, snapshots any existing logical-to-physical mappings, plans a fresh physical range, and reserves the immutable idempotency record page.
4. Zero the newly allocated 4MiB physical blocks. For each already-mapped logical block, copy the complete old 4MiB physical block into its new physical block through the DataView, preserving sectors not covered by the incoming BIO. Call `DataView.Sync` after both zeroing and copying, before metadata publication. The original BIO is then submitted by the kernel against the new physical mapping.
5. Publish bitmap images, logical-to-physical mappings, idempotency record/index and the new B+Tree root through the cluster-safe AG WAL transaction.
6. Return the committed logical-to-physical mapping and the new root generation to the DM completion path.

Metadata and data continue to use the same parent LUN through the Bootstrap MetadataView/DataView layout. The executor does not introduce a separate metadata device or Kubernetes dependency. Arena expansion also relocates the complete auxiliary tail (Lifecycle, OwnerRecord and ReaderTable) before publishing the expanded descriptor; the Reserved allocator now reserves and relocates ReaderTable pages when the metadata geometry permits RO access.

## Failure handling

- A stale/missing Owner proof rejects the mutation.
- An already-mapped logical range is handled as full-block COW: old data is copied to a fresh extent and the new Mapping is published atomically. Unmapped blocks in a mixed range remain zero-filled.
- A matching idempotency key replays its original mapping. Reusing the key for a different fingerprint is rejected.
- If the WAL commit outcome is ambiguous, the executor atomically poisons the Runtime and synchronously stops DM admission, then schedules drain/deactivation asynchronously. This avoids deadlocking while the current BIO is still waiting for its completion. Queued mutations revalidate the Runtime after taking the per-Volume mutation mutex and are rejected. The next activation must recover the AG WAL and resolve the idempotency record before accepting another mutation.
- Owner loss after publication is not reported as success under the stale epoch; the Runtime is fenced and drained.

## Data Retire Queue and physical reclamation

COW and Discard now append persistent Data Retire records in the same root/WAL transaction that changes the logical Mapping:

- Each record stores the retired AG, physical start block, block count and the old Mapping root generation.
- Records are immutable external Arena pages indexed by B+Tree keys in the stable reserved interval `[2^62, 2^63)`. DynamicGeometry rejects a logical DataView block range that overlaps this interval, and the interval does not move when the Pool expands. Logical Mapping keys remain below `TotalBlocks`; idempotency indexes remain in the high-bit namespace. This keeps the three key spaces disjoint across online expansion.
- A record is visible only after the Mapping root and record page are committed together. Recovery resolves the external pages and reconstructs pending records from the committed root; uncommitted record pages are unreachable COW reservations and are reusable after recovery.
- Physical ranges are coalesced and checked against the remaining mappings in the same Volume before being retired. A physical extent still referenced by another logical key in that Volume is not queued.

`PoolAllocator.CollectDataRetired` is the allocator-level collector. Production maintenance uses `DynamicVolumeRuntimeManager.CollectDataRetired`: it serializes against request resolution, closes DM admission, calls the kernel Fence/Drain path (which waits for all in-flight BIOs), runs the collector while retaining the RW Owner lease, and re-enables DM admission only after a final Owner health check. The runtime flushes DataView before collection. Collection fails closed unless the Owner lease/epoch matches and the same Volume's coordinated Reader Table is supplied.

The collector obtains the Volume's distributed AG lock, computes the minimum generation pinned by all `Active` and `Leaving` Readers, and collects only records for which `SafeGeneration > RetireGeneration`. A heartbeat timeout alone never removes a Reader: the Reader must have advanced after draining old-generation I/O, closed after drain, or been durably marked `Fenced` after the SAN fencing workflow.

For each eligible set, the collector creates Bitmap after-images and removes the corresponding Data Retire index entries through `DeleteBatchWithImagesRetireExternal`. Bitmap bit clearing, queue-index deletion, external-page retirement and B+Tree root publication are one AG WAL transaction. Recovery therefore sees either the pending queue with allocated bits or the committed deletion with cleared bits, never a queue-less allocated/free split. The now-unreachable Data Retire record pages themselves enter the existing PersistentArena metadata Retire Queue and are reclaimed only after the metadata Reader-generation proof.

The current implementation intentionally rejects cross-AG retired extents because BMPOOL03 journals are AG-scoped and there is no multi-AG atomic commit protocol. The Volume allocator currently assigns each Volume to one AG, and the collector verifies this invariant. It also assumes physical extents are not shared across different Volume mapping roots; clone/snapshot deduplication must add a Pool-wide reference-count mechanism before it can share physical blocks.

## Remaining acceptance boundary

The code path now implements COW, logical Discard, persistent Data Retire enqueue/recovery, Reader-generation gating, and atomic Bitmap release. The production manager collector obtains the local I/O-drain proof itself by stopping and draining the DM target; the lower-level allocator API remains guarded by an explicit proof parameter and must not be called directly without that barrier. Production SAN dual-node fault injection, multipath path-loss/recovery, collector crash injection at each WAL phase, kernel BIO end-to-end qualification, and performance acceptance remain required before declaring the whole P4-1.3.3 stage production-accepted.
