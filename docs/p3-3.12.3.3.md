# P3-3.12.3.3 — Owner Lease takeover and fencing closed loop

This slice adds the Owner-side counterpart to the Reader recovery protocol.
It preserves the BMDVOL02 v2 on-disk format: that descriptor stores OwnerEpoch,
but does not store the previous Owner NodeID/BootID. Previous-owner identity
therefore comes from a separately configured, authoritative cluster record
with linearizable read and compare-and-swap semantics.

## Takeover protocol

`internal/volume.OwnerCoordinator` implements the exclusive takeover path:

1. Acquire the per-Volume distributed sanlock Owner resource. A local
   FileLocker or MemoryLease is not accepted as a distributed locker.
2. Read and validate the authoritative previous OwnerRecord
   (VolumeID/NodeID/BootID/Epoch).
3. If a previous Owner exists, invoke the configured Fencer with its exact
   NodeID and BootID. The production SCSIPRFencer executes PREEMPT AND ABORT
   for the resolved old registration keys on every configured multipath
   device and verifies that old keys are absent on every path.
4. Invoke the required old-owner I/O barrier. This must establish that
   metadata I/O issued by the old Owner is quiescent; PR verification by
   itself is not a local DM drain proof.
5. Read the durable BMDVOL02 OwnerEpoch and allocate
   `max(OwnerRecord.Epoch, VolumeDescriptor.OwnerEpoch)+1`. Overflow,
   missing/invalid identities, a failed fence, failed drain, or failed CAS
   aborts takeover. No best-effort continuation is allowed.
6. Durably CAS-publish the new authoritative OwnerRecord while still holding
   sanlock. A CAS conflict aborts; the coordinator never guesses which record
   won.
7. Return a monitored OwnerLease. The runtime then replays the AG WAL, opens
   metadata, publishes the same epoch through `Store.AdvanceOwnerEpoch` and
   only then enables RW requests.

The new record is intentionally published before WAL replay. If the process
crashes in that interval, the sanlock lease is released and the next owner
will treat this identity as the previous owner and fence it before proceeding.
The metadata descriptor epoch is not advanced until WAL recovery has completed.

## Active Owner Lease loss

The sanlock helper process is monitored by `volume.OwnerLease`. If the helper
exits, the lease's `Lost()` channel reports a terminal error; it never silently
reacquires the resource. `VolumeRuntimeManager` watches this channel. The
Pool backend synchronously invokes the mandatory `OnOwnerLeaseLost` hardware
fail-stop hook, closes software request admission, and waits for the metadata
I/O drain before normal teardown can release the Owner lease or device.

The fail-stop hook must be idempotent and safe when invoked concurrently with
normal Deactivate. It must actually suspend/fail-stop the local DM/data path;
a log message or best-effort queue stop is insufficient. Stop/drain hooks must
also be idempotent because the lease-loss handler and Deactivate can overlap.

## Wiring

Use `metastore.PoolOwnerCoordinator{Coordinator: ...}` as the
`PoolRuntimeConfig.Owner` adapter. Construct `volume.OwnerCoordinator` with:

- the same distributed sanlock locker used by the runtime;
- a stable per-Volume Owner resource resolver;
- an authoritative `OwnerRecordStore` implementation with linearizable
  Load + durable CompareAndSwap (for example, a Kubernetes Lease adapter
  using resourceVersion CAS);
- `fence.SCSIPRFencer` with a trusted key resolver and the complete set of
  multipath paths;
- a `ReadEpoch` callback reading the selected Volume Descriptor;
- a `DrainOldOwner` callback that verifies old-owner metadata I/O quiescence.

The Owner record store is an explicit platform adapter, not an in-process map
or a local file. Its CAS must remain authoritative across all nodes. The
SCSI PR key resolver must map the exact NodeID/BootID incarnation to every
registered initiator key. Unknown keys and any path error are fatal.

## Safety notes and remaining qualification

- Reusing the exact same NodeID/BootID is rejected. The system must not
  PREEMPT its own initiator key; a same-boot daemon restart needs a separate
  platform recovery path that proves the previous local data path is stopped.
- A successful sanlock acquisition does not itself prove SAN I/O fencing.
  The coordinator does not return until the configured PR fencer and old-owner
  I/O barrier both succeed.
- BMDVOL02 v2 remains unchanged. The authoritative OwnerRecord is external
  cluster state; it must be provisioned and backed up consistently with the
  Pool. If that store is unavailable or ambiguous, RW activation fails closed.
- CI fault tests cover fence failure, drain failure, same-identity rejection,
  epoch overflow, monotonic epoch selection, and active sanlock lease loss.
  They do not emulate multipath hardware, SAN controller behavior, real
  sanlock daemon failure timing, or power-loss ordering.
- Production acceptance still requires testing with the target SAN: PR
  PREEMPT AND ABORT through every path, path-loss/error injection, helper
  termination, DM suspend and in-flight I/O drain, node power-off, and
  crash/restart during every takeover phase.

This is a complete software takeover state machine with explicit platform
adapters. It is not a claim that an unconfigured deployment is production
ready; missing/failed adapters prevent RW admission.
