# P4-1.2.5.22 — AG Capacity Reservation and Dynamic AG Growth

## Geometry contract

BMPOOL03 separates the active allocation-group count (AGCount) from the fixed number of per-AG metadata slots reserved at format time (AGCapacity).

- AGCount is derived from current DataView capacity and is the only count visible to allocators and WAL open paths.
- AGCapacity reserves stable per-AG WAL segments, Bitmap descriptors/bitmaps, and two Checkpoint descriptors.
- Metadata offsets and strides are derived from AGCapacity, not AGCount; activating another AG does not move existing metadata.
- A geometry update may increase AGCount only up to AGCapacity. Growth beyond that limit fails before metadata publication.

## AG activation protocol

PublishDynamicGeometry performs the transition while new AGs remain unreachable through the old Superblock:

1. Validate Pool UUID, generation, monotonic Data/Metadata capacity, stable AG size/capacity, and unchanged metadata-region offsets.
2. Commit newly exposed bits in the previous final AG through Dynamic WAL. Bits that were padding in the old geometry are never valid allocations; already-cleared bits are treated as an earlier durable attempt so retry is idempotent.
3. Zero each newly activated AG WAL segment.
4. Initialize its Bitmap with free bits for valid blocks and allocated bits for padding, then publish the checksummed AG Bitmap descriptor.
5. Initialize both Checkpoint descriptors for the AG.
6. Sync all newly initialized AG metadata.
7. Publish the higher-generation Superblock to the inactive copy and Sync; mirror it to the other copy and Sync.

The old Superblock remains authoritative until step 7. A crash during AG initialization leaves new AGs unreachable. A retry may safely reinitialize them. If the final-AG bitmap WAL commit completed before the crash, retry recognizes those bits as already initialized.

## Locking and ownership

PublishDynamicGeometryUnderLease requires a live fenced Pool Owner lease and distributed AG locker. It holds the previous final AG lock across the bitmap transition and both Superblock publications, checking the lease before each durable publication boundary. New AG slots are not accessible to allocators until the Superblock publishes the increased AGCount.

The caller must supply a cluster-safe Dynamic WAL committer for the previous final AG when its valid block count grows.

## Compatibility and limits

- Existing BMPOOL03 pools remain readable; AGCapacity is persisted in the Superblock.
- BMPOOL02 layout and decoding are unchanged.
- AGCapacity is fixed at format time. Growth beyond reserved slots still requires a future metadata layout migration.
- This phase does not grow the Mapping region or increase AG size; it activates already-reserved AG slots and exposes newly added DataView capacity.
- A new AG is recovered through its own DynamicJournal after the new Superblock is visible.

## Validation

TestDynamicAGGrowthRetryAfterBitmapCommit injects a failure after the previous final AG bitmap transaction is durable but before the new AG WAL slot is initialized. It verifies that the old Superblock remains active, retry is idempotent, and AGCount is published only after new AG metadata is durable. Existing tests cover reserved-capacity rejection, stable metadata offsets, bitmap padding, and dual-Superblock publication.
