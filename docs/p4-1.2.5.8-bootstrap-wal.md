# P4-1.2.5.8 — Bootstrap Extent-Map WAL

BMPOOL03 uses a dedicated two-page redo record in its reserved Bootstrap region:

1. Write the inactive Extent Map slot and sync it.
2. Write the checksummed WAL Intent naming the inactive Bootstrap record and its after-image CRC; sync.
3. Write the inactive Bootstrap record; sync.
4. Write the matching WAL Commit; sync.
5. Recovery ignores the target record when an Intent has no matching Commit. A matching Commit validates the exact after-image and referenced Extent Map before the new generation can win.

The fixed Intent/Commit pages are reused serially. A new Intent cannot accidentally pair with the preceding Commit because the transaction generation and intent CRC must both match. An uncertain commit write is resolved by reopening and validating the record.

Every online update requires a BootstrapLocker that reports Distributed() == true. A host-local flock implementation is not accepted. The caller supplies a SAN-backed distributed lock, and the code rechecks the on-device generation under that lock to reject stale writers.

This is a Pool Bootstrap transaction WAL, not yet a replacement for per-AG mapping/bitmap WAL. The production caller must bind the locker to the Pool's fenced Owner lease/epoch; the current BMPOOL02 AG Journal remains format-specific.
