# P4-1.2.5.8 — Bootstrap Extent-Map WAL and Owner fencing

BMPOOL03 uses a dedicated two-page redo record in its reserved Bootstrap region:

1. Write the inactive Extent Map slot and sync it.
2. Write the checksummed WAL Intent naming the inactive Bootstrap record and its after-image CRC; sync.
3. Write the inactive Bootstrap record; sync.
4. Write the matching WAL Commit; sync.
5. Recovery ignores the target record when an Intent has no matching Commit. A matching Commit validates the exact after-image and referenced Extent Map before the new generation can win.

The fixed Intent/Commit pages are reused serially. A new Intent cannot accidentally pair with the preceding Commit because transaction generation and intent CRC must both match. An uncertain commit write is resolved by reopening and validating the record.

Online publication requires both a distributed SAN Bootstrap lock and a live fenced Pool Owner lease. The lease must expose a non-zero epoch; that epoch is persisted in the Bootstrap record and checked before Intent, after-image and Commit. A local flock or a lease-less administrative caller is rejected. The caller must use the OwnerCoordinator takeover path (SCSI PR fencing, all-path reservation verification, OwnerRecord and I/O drain) before passing the lease.

This is a Pool Bootstrap transaction WAL, not yet a replacement for per-AG mapping/bitmap WAL. Existing BMPOOL02 AG Journal remains format-specific.
